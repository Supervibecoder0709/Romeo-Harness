# PM Harness 운영 메모

## 결론과 추천

**추천: 이 저장소는 ‘디자인 실행기’로 직접 신뢰하지 말고, 각 작업에 한 개씩 붙이는 버전 고정 프롬프트 계약으로 사용하세요.** 기본 선택은 마케팅 페이지·포트폴리오·가벼운 리디자인에는 `design-taste-frontend` v2를 사용하되, 항상 해당 SKILL 파일의 commit SHA와 실제 변경 결과를 함께 기록하는 방식입니다.

이유는 간단하다. v2는 brief 해석, 디자인 시스템 선택, 리디자인 안전선, 사전 점검표까지 가장 넓은 작업 계약을 제공한다. 반면 v2는 experimental이고, 이 저장소에는 실행기·테스트·CI·로그·rollback이 없다. 즉, “스킬을 넣었다”는 것은 완료 증거가 아니라 에이전트에게 지시를 전달한 것뿐이다. [E07][E09][E12][E30]

`image-to-code`는 시각 결과가 의사결정의 중심이고 이미지 생성 품질을 사람이 검토할 수 있을 때만 추가한다. 이미지마다 비용·시간이 늘고, 참조 이미지가 어긋나면 그 어긋남을 충실히 코드화할 위험이 있기 때문이다. `redesign-existing-projects`는 기존 코드·브랜드·분석 이벤트를 보존하는 제한적 개선일 때, `stitch-design-taste`는 코드가 아니라 승인 가능한 디자인 규칙 문서가 필요할 때 쓴다. [E15][E19][E24]

## 확인된 사실 / 현재 가정 / 추천

| 구분 | 내용 |
| --- | --- |
| 확인된 사실 | 13개 스킬은 Markdown 지시문이며, `skill.sh`는 이름에 대응하는 경로를 출력한다. 저장소 트리에는 이 저장소 자체의 package manifest, test, CI workflow가 없다. [E05][E30] |
| 현재 가정 | 실제로는 호환 에이전트/CLI가 `SKILL.md`를 읽고 대상 프로젝트에서 코드를 바꾸거나 이미지 생성 도구를 호출한다. 이 실행 환경은 저장소 밖이다. [E03][E08] |
| 추천 | Harness는 스킬 텍스트, 모델 실행, 프로젝트 변경, 검증을 분리해 각각의 증거를 남긴다. 스킬의 선언만으로 품질·보안·배포 완료를 판정하지 않는다. |

## 입력 계약: 작업 시작 전에 잠글 것

에이전트에 “예쁜 페이지 만들어줘”만 주면 v2가 의도한 Design Read도 모호해진다. 아래 입력을 task card에 고정하는 것이 좋다.

1. **작업 유형과 성공 기준**: 신규 랜딩 / 기존 페이지 preserve 리디자인 / 이미지 참조만 / 이미지→코드 중 하나, 전환 목표와 핵심 사용자.
2. **변경 범위**: 대상 route·컴포넌트·assets와 수정 금지 항목. 기존 리디자인이면 URL, nav label, 폼 필드 이름·순서, logo, 법률·동의 문구는 별도 승인 항목으로 둔다. 이는 v2의 안전선과 일치한다. [E12]
3. **디자인 입력**: 로고·색·폰트 라이선스·참조 이미지/URL·접근성/규제/다크 모드 요구. 없으면 에이전트가 가정한 Design Read를 첫 산출물로 보여주게 한다. [E09]
4. **기술 입력**: 실제 `package.json`, 프레임워크, Tailwind 버전, 이미 설치된 라이브러리, 테스트 명령. v2도 import 전 의존성 확인을 요구하지만 저장소 자체가 이 검사를 실행하지는 않는다. [E10]
5. **재현 정보**: `Leonxlnx/taste-skill@72e299530e2eb31ed8da06181bc19f6c18a00821`, 사용한 스킬 frontmatter name, 실행 모델/도구 버전, 입력 prompt의 버전.

## 사람 승인 지점

스킬 원문은 리디자인에서 URL/주 메뉴/폼/로고/법률·동의 문구의 무단 변경을 금지한다. Harness는 이를 넓혀 다음 지점에서 사람 승인을 요구하는 편이 안전하다. [E12]

- **시각 방향 승인**: Design Read, 다이얼 값, reference image 세트. 이 단계는 아직 코드/운영 데이터를 바꾸지 않는다.
- **변경 계획 승인**: 대상 파일, 신규 dependency, 폰트/이미지 출처, 동작·정보구조 변경 여부. 새 패키지·유료 이미지·외부 API는 비용/권한/공급망 영향을 확인한다.
- **병합/배포 승인**: diff, 테스트, 모바일·다크모드·reduced-motion 증거, 라이선스 확인이 나온 뒤에만 한다. 이 저장소의 pre-flight는 좋은 체크리스트이지만 CI gate가 아니다. [E11][E12]
- **이미지 생성 비용 승인**: `image-to-code`, web, mobile은 섹션/화면 수만큼 이미지를 요구한다. 예산 상한과 생성 개수, 저장 위치를 먼저 고정한다. [E15][E16][E17]

## 실행 단위와 관찰 가능한 완료 증거

권장 실행 단위는 “한 페이지/한 흐름 + 하나의 고정 스킬 + 하나의 PR 또는 diff”다. 이미지 전용은 “섹션 또는 화면 하나당 이미지 한 장”이고, 모바일은 논리적 흐름 전체를 하나의 review batch로 취급한다. [E16][E17]

완료 판정에는 다음 증거를 묶는다.

| 단계 | 최소 증거 | 왜 필요한가 |
| --- | --- | --- |
| 지시 적용 | SHA, SKILL frontmatter name, prompt, Design Read/다이얼 | 어떤 계약을 실행했는지 재현 |
| 이미지 | 원본 생성 이미지 경로, 섹션/화면 수, 사람의 승인 여부 | “이미지 우선”이 실제로 수행됐는지 확인 |
| 코드 | 변경 파일 목록과 diff, 새 dependency의 manifest 변경 | 스킬 지시와 실제 상태를 분리 |
| 기능 | build/test 로그, 핵심 사용자 흐름의 스크린샷/영상 | 코드가 존재하는 것과 작동하는 것을 분리 |
| 품질 | 375/768/1440 등 화면 증거, 키보드·contrast·reduced-motion, Lighthouse 결과 | 원문이 요구하는 반응형·접근성·성능을 관찰 |
| 출시 | 배포 URL, 배포된 SHA, 실제 readback | draft/로컬 결과를 라이브 완료로 오인하지 않음 |

표의 build/테스트/배포 증거는 **추천**이다. 저장소가 제공하는 실행/로그 기능이 아니며, `taste-skill` 본문은 최소한 의존성 확인·Lighthouse·reduced motion을 요구한다. [E10][E11]

## 재시도·복구

이 저장소의 정의는 이미지가 불명확할 때 새 상세 이미지를 만들고, 긴 응답은 clean breakpoint에서 pause/continue로 나누라고 한다. 반면 작업 ID, 이미지 seed, 자동 retry, retry budget, rollback은 제공하지 않는다. [E15][E26]

따라서 Harness에 다음을 추가하는 것을 권한다.

- 실패를 `INPUT_GAP`, `REFERENCE_UNCLEAR`, `DEPENDENCY_MISSING`, `VISUAL_QA_FAIL`, `BUILD_FAIL`, `LIVE_UNVERIFIED`로 분류한다.
- 재실행 전 마지막 승인 이미지와 file diff를 보관하고, 실제 코드 변경은 git commit/PR 또는 patch artifact로 되돌릴 수 있게 한다.
- 이미지 생성은 seed/프롬프트/모델/개수를 기록해 비용과 재현성을 관리한다. 스킬 원문은 이 메타데이터를 요구하지 않으므로 Harness가 추가해야 한다.
- 기존 서비스 리디자인은 visual pass와 function/SEO/analytics pass를 분리한다. 원문도 SEO와 분석 이벤트 보존을 강조한다. [E12]

## 보안·비용·이전 가능성

**보안:** 스킬은 코드·이미지 생성 지시문일 뿐, secret 처리, 데이터 접근, 권한 분리, sandbox, 외부 URL allowlist를 정의하지 않는다. Harness가 secrets를 prompt, Git, 이미지 메타데이터, 로그에 남기지 않도록 차단해야 한다. 외부 패키지·폰트·이미지 추가는 dependency와 라이선스 검토를 별도 gate로 둔다.

**비용:** 기본 텍스트 스킬은 저비용이지만 이미지 계열은 섹션/화면 수에 비례해 이미지 호출을 늘리도록 명시한다. 비용을 통제하려면 “승인된 2개 방향 × 섹션 N개” 같은 상한을 task contract에 둔다. [E16][E17]

**이전 가능성:** 파일은 보통의 `SKILL.md`와 Markdown이므로 특정 런타임에 강하게 묶인 코드는 없다. 다만 결과의 일관성은 에이전트가 이 형식을 실제로 읽는지와 이미지 도구 능력에 좌우된다. 동일 SHA의 SKILL을 보관하면 프롬프트 계약은 옮길 수 있지만 생성 결과의 재현은 보장되지 않는다.

## 확장 판단

다음 순서가 가장 안전하다.

1. 1개 내부용 랜딩 페이지에 v2를 적용하고 위 완료 증거를 수집한다.
2. 품질이 부족한 지점만 `image-to-code`를 추가해 이미지 비용과 visual fidelity를 비교한다.
3. 재사용이 확인된 후에만 Harness wrapper를 만들어 SHA pin, 입력 스키마, 체크리스트, artifact 저장, human approval을 자동화한다.

바로 여러 스킬을 동시 적용하거나 자동 배포로 연결하는 것은 추천하지 않는다. 이 레포는 우선순위 조정과 검증을 위한 prompt contract이지, 권한·상태·검증을 통제하는 운영 플랫폼은 아니기 때문이다.
