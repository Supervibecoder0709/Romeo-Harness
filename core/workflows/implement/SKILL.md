# romeo:implement — 승인 확인 → 작업 계약 → 구현 → 증거 → 결과 계약

승인 없이 시작하지 않는다(D-27). 이 절차는 진입점이 아니다 — 스스로 켜지지 않고, 라우터가 계산한
단위·모드·영역·깊이가 켤 때만 쓴다(K-60). 규율은 부품이 제공하고, 무엇을 언제 켜는가는 이 절차가 정한다(D-50·D-54).

## 역할 분담 (D-68)

| 단계 | 누가 | 무엇 |
| --- | --- | --- |
| 계약 | 하네스 | 승인된 Tech Spec 과 라우터 출력에서 작업 계약을 계산한다. 같은 입력이면 같은 계약 |
| 실행 | 구현자 런타임 | 계약의 `allowed_paths` 안에서만 쓰고 `required_checks` 를 문자열 그대로 실행한다 |
| 판정 | 증거 | 완료는 증거로만 선언한다. 실행했다는 주장은 판정이 아니다(K-51) |

## 절차

1. **승인 확인.** `docs/work/<id>/spec.md` 의 `status: active` 와 `approved_at` 을 본다. 하나라도 없으면 구현하지 않고
   `BLOCKED_APPROVAL` 로 끝낸다. 확인란에 `NEEDS_INPUT` 이 남아 있으면 승인 자체가 성립하지 않는다(D-60).
   위임된 작업 공간은 **커밋된 것만** 본다 — 승인 표시가 커밋되지 않았으면 그 안에서는 승인이 보이지 않는다.
   그래서 작업 계약은 승인된 Tech Spec 이 들어 있는 커밋에서만 만들어지고, 계약이 있다는 것이 그 커밋 시점에
   승인이 있었다는 뜻이다(D-a).
2. **작업 계약 생성.** 계약은 손으로 쓰지 않는다 — 하네스가 계산한다.
   `romeo envelope build --unit <id> --role implementer --base-sha <승인 커밋 SHA> --run <run>` 로 만들고,
   결과는 `docs/work/<id>/task/<run>-implementer.json` — **자기 작업 루트 기준 상대 경로**다.
   위임 실행이면 그 자리에 이미 있을 수 있다: 있으면 읽고, 없으면 같은 명령으로 만든다 —
   계약은 결정적이라 어느 쪽이 만들어도 같은 파일이다. 필드는 새로 정하지 않고 원본에서 온다 —
   `spec_ref` 는 그 커밋의 Tech Spec 과 그 해시, `base_sha` 는 그 커밋, `allowed_paths` 는 역할 계약의 범위,
   `guards` 와 `required_checks` 는 라우터 출력과 Tech Spec 의 검증 계획, `workspace` 는 라우터의 격리 값이다.
   같은 입력이면 바이트까지 같은 계약이 나온다. 격리가 `none` 이면 문서 패키지가 없다는 뜻이라 계약을 만들지 않고
   1번의 `BLOCKED_DOCS` 로 끝낸다. 명령이 거부하면 그 메시지가 무엇이 빠졌는지(승인·승인 커밋) 알려준다.
3. **규율 부품.** 라우터 출력 `parts` 의 **각 항목 `status` 를 본다. `active` 인 것만 켠다.**
   라우터는 이 저장소의 부착 상태(`.harness/romeo.project.yaml` 의 `modules`)로 부품 레지스트리의 기본값을 덮는다 —
   채택 게이트를 통과한 부품은 거기서 `active` 로 선언돼 있고, 부착 파일이 없으면 레지스트리 기본값(대개 `pending_gate`)이 남는다.
   부품은 *무엇이 제대로 된 개발인가* 만 제공하고
   *누가 언제 실행하는가* 는 이 절차가 정한다(D-50). 원문과 아래 규칙이 충돌하면 **아래 규칙을 따른다.**
   - 코드를 쓰기 전 → `sp-test-driven-development`. 테스트보다 먼저 쓴 코드를 발견해도 **지우지 않는다** —
     무엇을 왜 지우는지 보이고 승인을 받은 뒤에만 지운다. 미커밋 코드는 복구할 수 없다(K-66).
   - 버그·검사 실패·예상 밖 동작 → `sp-systematic-debugging`. 원인을 찾기 전에 고치지 않는다.
   - 완료를 주장하기 전 → `sp-verification-before-completion`.
   - 격리가 필요할 때 → `sp-using-git-worktrees`. 작업 공간은 override 가 지정한 명령으로만 만든다.
   - 통합 단계 → `sp-finishing-a-development-branch`. 메뉴 제시까지만 하고 실행은 사람의 승인 뒤에 한다.
   - `status` 가 `active` 가 아닌 부품은 쓰지 않는다. 그 목록이 `PART_PENDING_GATE` 경고의 `detail` 이다 —
     경고가 떴다는 것과 이 절의 부품이 꺼졌다는 것은 다르다. 경고에는 다른 부품이 실려 있을 수 있으므로
     항상 `detail` 의 id 를 보고 판단한다.
4. **작업 공간.** 계약의 `workspace` 값대로 연다. 작업 공간은 코드만 분리한다 — 데이터·배포 환경·외부 서비스는
   분리되지 않으므로 Tech Spec 의 환경 계획 절이 담당한다.
5. **구현.** `allowed_paths` 밖에 쓰지 않는다. 산출물은 작업 단위 폴더 안에 두거나 frontmatter 의 `inputs:`/`evidence:`
   로 등록한다. 부품의 기본 출력 경로를 그대로 쓰지 않는다 — 등록되지 않은 산출물은 종료 검사가 인정하지 않는다(K-62).
6. **가드.** 계약의 `guards` 에 실린 행동은 영향 범위·사전 백업·복구 방법·확인할 내용을 설명하고
   `romeo evidence approve --unit <id> --guard <가드> --by <승인자> --note "<영향 범위·복구 방법>" --run <run>` 으로
   승인 기록을 남긴 뒤에만 한다. **이 명령은 선행 실행이 없어도 동작한다** — 그 run 이 없으면 `commands: []` 인
   승인 전용 레코드를 만들고, 승인 시점에 실행한 명령이 0건이라는 사실 자체가 '승인 전 상태 변경 0건' 의 증거가 된다.
   그래서 6번이 7번보다 앞에 있어도 실행 가능하다. 기록이 없으면 `BLOCKED_APPROVAL` 로 끝낸다(K-50·K-66).
7. **증거.** `romeo evidence run --unit <id> --run <run> -- <명령>` 과 `romeo evidence checks --unit <id> --run <run>` 으로만
   만든다. 손으로 쓰지 않는다(K-51). `--run` 은 6번과 같은 값을 쓴다 — 승인과 실행이 한 레코드에 모인다.
   위임 실행이면 `--task-id`·`--dispatch-id` 로 위임 식별자를 같은 run 에 남긴다. 한 run 은 한 위임에 속하므로
   다른 값이 들어오면 기록이 거부된다. **위임 식별자 중 일부는 위임이 시작된 뒤에야 정해진다** — 받기 전에는 증거 기록을
   시작하지 않는다. 비어 있는 자리는 나중 실행이 채울 수 있지만, 이미 다른 값이 적힌 자리는 덮어쓰지 못한다.
   `required_checks` 는 문자열 그대로 실행한다 — 종료 검사가 대조하는 명령과 정확히 같아야 한다.

   **종료 검사는 기록을 믿지 않는다 — 그 명령을 다시 실행해 기록과 대조한다.** 기록은 이 기계를 쓰는 사람이 고칠 수 있고,
   고친 기록끼리는 언제나 앞뒤가 맞기 때문이다. 고칠 수 없는 것은 명령을 다시 돌린 결과뿐이다(AGENTS.core §4).
   그래서 `required_checks` 에 넣는 명령에는 조건이 셋 붙는다 — **다시 실행해도 같은 결론이 날 것**,
   **작업 트리를 바꾸지 않을 것**(바꾸면 재실행 대조가 성립하지 않는다), **상한 시간 안에 끝날 것**.
   조건을 못 맞추는 검사는 숨기지 않고 **검증 계획에서 `rerun: false` 로 선언하고 이유를 적는다**.
   그러면 그 검사는 통과로 세지 않고 "재실행으로 확인되지 않았다 (그 이유)" 로 인쇄되며 완료가 서지 않는다 —
   막지 않고 드러내는 쪽이 낫다. 고쳐야 할 것은 그 선언이 아니라 **그런 검사에 완료를 의존하게 만든 검증 계획**이다.
   되돌리기 어려운 단계는 애초에 검증 계획이 아니라 6번의 가드 승인과 증거로 남긴다.

   **검증 계획 자체는 실행 중에 바꾸지 않는다.** 종료 검사는 지금 읽는 `required_checks` 를 **커밋된 계획**과 대조한다 —
   실패하는 검사를 지우거나 무해한 것으로 바꾸면 기록도 재실행도 전부 맞아떨어지지만, 그때 고쳐진 것은 증거가 아니라
   **주장 자체**다. 검사를 바꿔야 한다면 승인을 다시 받는다(D-27). 수용 기준 체크박스를 채우는 것은 여기 해당하지 않는다.
8. **결과 계약.** `core/schemas/result-envelope.json` 형식으로 낸다. `checks` 는 이 실행이 주장하는 값이고
   **증거가 권위다** — 어긋나면 증거를 따른다. 그 증거조차 종료 검사가 다시 실행해 대조하므로,
   실행하지 않은 검사를 `checks` 에 적는 것은 기록을 하나 더 만드는 일일 뿐 통과를 만들지 않는다. `evidence_ref` 에 증거 파일 경로를 채운다. 명령을 하나도 실행하기 전에
   차단된 경우에만 `evidence_ref` 가 비어 있을 수 있고, 그때는 `blocked_reason` 이 반드시 채워져 있다.
   실행하는 역할이 `gate_verdict: PASS` 를 내려면 `checks` 가 1건 이상이고 `evidence_ref` 가 채워져 있어야 한다 —
   스키마가 그것을 거부한다. 실행 없이 통과를 주장할 수 없다(K-51).
   결과는 `docs/work/<id>/result/<run>-implementer.json` 에 **스스로** 쓴다 — 검토자 판정이 `docs/work/<id>/review/` 에
   놓이는 것과 같은 이유이고, 이 역할에는 쓰기가 있어 회수해 주는 쪽이 없다(K-62). 봉투에 적는 경로
   (`task_envelope_ref.path` · `evidence_ref`)는 전부 **자기 작업 루트 기준 상대 경로**다 —
   종료 검사는 자기 체크아웃 밖의 절대 경로를 앵커로 인정하지 않는다.

## 하지 않는 것

- 기획을 다시 만드는 것. 누락·모순은 새 문서를 쓰지 말고 질문한다(K-61).
- 작업 계약을 손으로 쓰는 것. 계약은 하네스가 계산한다 — 손으로 쓰면 같은 입력에 같은 계약이 나온다는 보장이 없다.
- 승인 표시를 커밋하지 않은 채 위임하는 것. 그 작업 공간에서는 승인이 보이지 않는다(D-a).
- 자기 산출물을 스스로 검토했다고 선언하는 것. 검토는 검토자 역할의 몫이다(C-D3).
- 진행 상태를 자체 기록해 완료 판정에 쓰는 것. 완료는 증거와 종료 검사가 판정한다(K-63).
- 다시 실행할 수 없는 명령을 그 사실을 숨긴 채 검증 계획에 넣는 것. 재실행 대조가 성립하지 않는 검사는 `rerun: false` 로 선언한다 — 선언하지 않아도 통과가 되지는 않지만, 왜 확인되지 않는지가 사라진다.
- 실패하는 검사를 검증 계획에서 지우거나 바꿔 통과를 만드는 것. 그것은 증거가 아니라 주장을 바꾸는 것이고, 커밋된 계획과의 대조가 잡는다.
- 기록을 고쳐 검사를 통과시키는 것. 종료 코드·로그·해시를 앞뒤 맞게 고쳐도 재실행 결과는 고칠 수 없다(AGENTS.core §4).
- 부품 원문이 지시하더라도 저장소 밖 상태를 바꾸는 것. override 가 원문보다 우선한다(K-66).

## 실패 처리

실패는 정상 경로다. 실패한 검사 이름과 출력을 그대로 보여주고 통과한 척하지 않는다.

- `BLOCKED_APPROVAL` — 승인이 없거나 가드 승인 기록이 없다.
- `BLOCKED_CAPABILITY` — 필요한 능력이 없다. 가능한 척 우회하지 않고 자동 설치도 하지 않는다.
- `BLOCKED_DOCS` — 기획 원본이 없거나 확인란이 비어 있다.
