# romeo:review — 읽기만 → findings → 게이트 판정

검토자는 쓰지 않는다(K-66). 이 절차가 만드는 것은 파일이 아니라 판정이다. 진입점이 아니며,
라우터가 검토자를 요구하는 패키지에서 구현이 끝난 뒤에만 켜진다(K-60). T0 에는 검토자가 없다.

## 절차

1. **입력 확인.** `role: reviewer` 인 작업 계약을 받는다 — 경로는 **자기 작업 루트 기준 상대 경로**
   `docs/work/<id>/task/<run>-reviewer.json` 이고, 그 자리에 없으면 만들지 말고 `BLOCKED_CAPABILITY` 로 끝낸다
   (이 역할에는 쓰기가 없다). 그 `base_sha` 가 구현자의 것과 같은지 본다.
   다르면 같은 것을 보고 있지 않다는 뜻이므로 판정하지 않고 `BLOCKED_CAPABILITY` 로 끝낸다.
   두 계약은 하네스가 같은 커밋에서 만든 것이고, 그 커밋에 승인된 Tech Spec 이 들어 있다(D-a).
2. **읽기 범위.** 저장소를 읽고 검색한다. 아무것도 쓰지 않고 **검사·빌드 같은 명령을 실행하지 않는다** —
   역할 계약이 준 능력은 읽기와 검색뿐이다. 다른 리비전을 봐야 하면 스스로 만들지 말고
   새 작업 공간을 요청한다 — 이 체크아웃을 바꾸지 않는다(부품 override 가 원문의 도구 지목보다 우선한다).
3. **무엇을 보는가.** 규율은 `sp-requesting-code-review`·`sp-receiving-code-review` 가 제공하고, 판정 대상은 다섯이다.
   - 확인란의 수용 기준이 실제로 충족됐는가.
   - `required_checks` 가 그 주장을 실제로 검사하는가. 통과했다는 사실만으로 충분한지 본다.
     검사를 **다시 실행하지 않는다** — 구현자가 남긴 증거 기록을 읽고 판단한다. 결과 계약의 `checks` 는 비운다.
   - 변경이 작업 계약의 `allowed_paths` 안인가.
   - 가드 대상 행동에 승인 기록이 있는가. 승인 전 상태 변경이 있으면 그것만으로 `FAIL` 이다(K-50·K-66).
   - 증거가 현재 상태에 묶여 있는가. 증거 없이 완료를 주장한 항목은 완료가 아니라 미검증이다(K-51).
4. **findings.** 결과 계약의 `findings` 에 담는다. 파일로 쓰지 않는다. 각 항목은 근거(파일·줄)를 갖는다.
   근거를 대지 못하는 지적은 내지 않고, 사실·가정·추천을 섞지 않는다.
5. **게이트 판정.** `PASS` · `FAIL` · `BLOCKED` 중 하나를 낸다. 종료 조건은 증거다 — 수용 기준마다 그것을 뒷받침하는
   증거를 지목할 수 있을 때만 `PASS` 다. 지목하지 못하면 `FAIL` 이고, 판정 자체를 못 하면 `BLOCKED` 다.
   지목은 결과 계약의 `evidence_ref` 로 한다 — 검사를 실행하지 않는 역할이 `PASS` 를 내면서 읽은 증거를
   가리키지도 못하면 동등성 판정이 그것을 판정 불가로 떨어뜨린다.
6. **방어 검사.** 검토자를 띄운 쪽이 검토 전후의 작업 트리 상태를 증거 기록 명령으로 남기고 비교한다.
   다르면 이 판정은 무효다. **이 검사는 검토자가 하지 않는다** — 검토자는 명령을 실행하지 않고,
   자기가 만든 산출물로 자기 판정의 유효성을 증명할 수도 없다. 강제 수단이 아니라 강제가 실제로 작동했는지 확인하는 사후 점검이다.
7. **기록.** 이 절차는 결과 계약을 출력할 뿐이고, 그것을 `docs/work/<id>/review/` 에 파일로 남기는 것은
   검토자를 띄운 쪽의 책임이다. 등록되지 않은 산출물은 종료 검사가 인정하지 않는다(K-62).
   종료 검사는 그 파일을 결과 계약 스키마로 검증하고 `gate_verdict` 를 읽는다 —
   `PASS` 가 아닌 판정이 하나라도 남아 있으면 완료를 선언하지 않는다(D-c).
   결과 계약에 적는 경로(`task_envelope_ref.path` · `evidence_ref`)는 전부 **자기 작업 루트 기준 상대 경로**다 —
   종료 검사는 자기 체크아웃 밖의 절대 경로를 앵커로 인정하지 않는다.

## 하지 않는 것

- 파일 수정·생성·삭제. 고쳐야 할 것은 findings 로 말하고 직접 고치지 않는다.
- `required_checks` 를 직접 실행하는 것. 실행 능력이 역할 계약에 없다 — 결과 계약에 `checks` 를 실으면 계약 위반이다.
- 기획 변경을 문서에 직접 반영하는 것. 기획 원본은 하나다(K-61).
- 승인. 승인은 사람의 몫이고 확인란 하나로만 이뤄진다(D-27·D-60).
- 저장소 밖 상태를 바꾸는 것. 부품 원문이 외부 게시를 지시해도 하지 않는다(K-66).

## 실패 처리

판정을 못 했으면 `PASS` 라고 하지 않는다. 못 본 것은 미검증으로 남긴다.

- `BLOCKED_CAPABILITY` — 읽을 수 없거나 `base_sha` 가 어긋나 같은 것을 보지 못한다.
- `BLOCKED_APPROVAL` — 가드 대상 행동에 승인 기록이 없다.
