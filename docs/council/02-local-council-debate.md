## Round 1: 독립 관점 (blind)

## 🗳️ Scalability Architect

### Position

이 하네스의 스케일 병목은 문서 저장량이 아니라 **호출당 컨텍스트 토큰, 인덱스 일관성, 그리고 여러 프로젝트에 걸친 스키마 진화**다. GPT 안에서 manifest-first와 current/work/archive 생명주기 분리는 스케일 관점에서 정확하므로 유지하되, 7종 타입의 구조 분기·수기 catalog.yaml·순차 ID는 성장 시 반드시 무너지는 안티패턴이므로 **"3-tier 구조 + 파생 인덱스 + 결정적 검증 파이프라인"**으로 재설계할 것을 권한다.

### Key points

- **Manifest는 쿼리 플랜이다 — 이 부분은 GPT 안을 강하게 지지한다.** 비싼 실행(문서 생성) 전에 싼 계획(분류 manifest)을 산출하고 거기서 멈춰 승인받는 구조는, 토큰 비용을 작업 크기에 비례하게 만드는 유일한 방법이다. 구현은 Claude Code 스킬의 progressive disclosure와 정확히 일치시켜라: `/plan` 1단계는 분류 rubric(~2K 토큰)만 로드해 manifest 파일을 쓰고, 2단계는 manifest에 지정된 템플릿 파일만 `references/`에서 로드해 문서를 하나씩 생성한다. 전체 템플릿·overlay를 매 호출에 로드하면 Change 한 줄에도 Initiative급 고정비를 낸다. 단계 경계를 디스크의 파일(manifest → docs → validation report → plan)로 두면 파이프라인이 체크포인트화되어 어느 단계든 재실행 가능하다.
- **구조 분기는 3-tier로 줄이고, 7개 객체 타입은 라벨로 강등하라.** 폴더 구조·문서 중첩·필수 산출물이 달라지는 "구조적 코드패스"가 7개면, 유지보수 비용과 분류 프롬프트 비용이 타입 수에 비례해 커진다(조기 샤딩과 같다). T0 Change(단일 Brief 파일) / T1 Feature(PRD+Spec) / T2 Initiative(Charter+하위 문서 트리)의 3개 구조만 두고, Experiment/Strategy/GTM/Platform은 tier 위에 얹히는 라벨+overlay 모듈로 처리하라. 라벨은 싸고 구조는 비싸다 — 실제 볼륨이 필요를 증명할 때만 구조를 쪼개면 된다.
- **Frontmatter가 SSOT, catalog.yaml은 파생 인덱스다.** GPT 안의 `_system/catalog.yaml`을 수기로 유지하면 문서 수가 수십 개를 넘는 순간 frontmatter와 drift한다. DB의 materialized view처럼 결정적 스크립트(`/plan-index`)가 frontmatter를 스캔해 재빌드하고, 수기 편집은 금지하라. 재빌드니까 머지 충돌도 "다시 생성"으로 해결된다. 같은 이유로 순차 ID(`FEAT-014`)는 중앙 시퀀스라 위험하다 — 이 사용자 환경은 `race` 스킬로 codex·claude를 병렬 워크트리에서 실제로 동시에 돌리므로 ID 충돌은 가정이 아니라 예정이다. `feat-20260812-email-auth` 같은 타입-날짜-슬러그 ID로 바꿔라.
- **LLM은 제안, 결정적 규칙은 강제 — 이 경계가 검증 비용의 스케일을 결정한다.** LLM에 맡길 것: 분류 제안, Hard Gate *탐지*(결제·법무 관련 여부 판단), 문서 내용 생성. 결정적 규칙으로 강제할 것: gate→필수 overlay 매핑(payment면 rollback overlay 누락 시 실패), doc_status/work_status 상태 머신 전이, frontmatter 스키마 검증, 링크 무결성, tier별 문서 길이 예산(Brief ≤ 1페이지). 이 validator들을 훅/슬래시 커맨드 스크립트로 두면 문서가 300개가 되어도 검증이 토큰 0원에 O(문서수)로 돌고, LLM이 게이트를 조용히 건너뛰는 사고를 구조적으로 막는다.
- **current/work/evidence/archive 분리는 hot/cold tiering으로서 옳다 — 단, 승격은 compaction 작업으로 자동화 대상이다.** 이 구조의 진짜 가치는 "지금 무엇이 사실인가"를 읽는 비용을 전체 이력 O(history)가 아닌 O(current)로 묶는 것이다. 다만 승격이 사람 규율에만 의존하면 반드시 부식되므로, release 마감 시 결정적 체크리스트(승격 후보 diff 제시 → 승인)로 커맨드화하라. 다중 프로젝트 재사용은 스키마 진화 문제로 다뤄라: frontmatter에 `schema_version`을 박고 additive-only 변경 원칙을 지키며, 하네스는 전역 스킬/플러그인 한 곳에 두고 각 프로젝트에는 산출물+얇은 설정 파일만 남겨라. GPT가 언급한 중앙 Product Docs 저장소 분리는 1인 개발에는 YAGNI다.

### Risks & blind spots

- **재분류(reshard) 경로가 설계에 없다.** Change로 시작한 작업이 구현 중 Feature로 자라는 경우가 가장 흔한 실패 모드인데, GPT 안은 최초 분류가 옳다고 가정한다. manifest를 버전업하고 기존 Brief를 PRD로 승격하는 `/plan-reclassify` 커맨드를 1급 시민으로 설계해야 한다.
- **manifest의 `create_after_validation`은 강제 장치가 없으면 죽은 약속이 된다.** `work_status: released`인데 measured가 아닌 문서, promotion_conditions 미충족 문서를 뽑는 결정적 "open loops" 리포트가 없으면 지연 산출물은 아무도 다시 안 본다.
- **current/의 무한 성장.** hot tier가 커지면 tiering의 이점이 사라진다. current/ 파일 수·크기에 린트 예산을 걸어 경고해야 한다.
- **반대 방향의 과설계 경고 — 내 렌즈에서 정직하게 말하면, 1인 규모에서 문서 개수 자체는 병목이 아니다.** 수백 개 파일은 grep으로 충분하다. 그래프 DB, 관계 질의 엔진, 저장소 분리 같은 스케일아웃 장치는 만들지 마라. 이 시스템의 진짜 스케일 축은 두 개뿐이다: 호출당 토큰과 유지보수하는 사람 손. 다른 렌즈들은 분류 정확도나 문서 품질을 볼 텐데, 하네스가 죽는 실제 원인은 대개 "매 호출이 비싸고 인덱스가 썩어서 안 쓰게 되는 것"이다.
- 새 프로젝트마다 전체 폴더 트리를 미리 생성하는 콜드스타트 고정비도 불필요하다 — 디렉터리는 첫 사용 시 lazy 생성이면 된다.

### Confidence

`high` — 파생 인덱스·결정적 검증·hot/cold tiering은 규모 불문 검증된 패턴이고, 병렬 워크트리 충돌은 이 사용자의 현재 도구 구성(race, Orca)에서 이미 실재하는 시나리오이기 때문이다.

## 🗳️ Maintainability Advocate

### Position

GPT 제안의 뼈대(객체 분류 → 5축 → Core+Overlay → current/work 분리 → Manifest)는 개념적으로 옳지만, 제안된 규모 그대로는 1인 개발자가 유지보수할 수 없는 온톨로지다 — 7개 객체 유형, 12개 frontmatter 필드, 8단계 work_status, 6개 저장 영역은 그 자체가 썩는 코드다. 나는 **"얇은 결정론적 척추(thin deterministic spine)" v1**을 권장한다: 3계층 planning unit + 결정론적 라우팅 테이블 + 검증 스크립트 1개 + 생성형(generated) 인덱스, 그리고 "기계적 소비자(consumer) 없는 메타데이터 필드는 금지"라는 단일 원칙.

### Key points

- **권장 아키텍처 (하나를 고른다):** planning unit은 **Change / Feature / Initiative 3개만**. Discovery는 유닛이 아니라 *모드*(uncertainty=high → PRD 대신 discovery brief로 라우팅), Strategy/GTM은 워크플로우 산출물이 아니라 `current/`의 상시 문서, Platform/Migration은 GPT 스스로도 "Change Brief 또는 Initiative Charter"로 매핑했으므로 별도 유형이 아니라 `migration` 오버레이다. 워크플로우는 4개 슬래시 커맨드가 유일한 상태 변경 경로: `/plan`(분류→Manifest→사용자 1회 확인) → `/plan-docs`(라우팅 테이블 기반 생성) → `/plan-validate`(스크립트) → `/plan-close`(동결·승격·아카이브). 로직은 `.claude/` 설정이 아닌 도구 중립적 markdown 규칙 파일 + 스크립트에 두고 Claude Code/Codex 각각 얇은 어댑터(SKILL.md / AGENTS.md)만 얹는다 — 이래야 벤더 교체 시 하네스가 살아남는다.
- **결정론 vs LLM의 경계 = 디버깅 가능성의 경계.** 5축 *판정*(불확실성이 높은가)은 본질적으로 LLM 몫이지만 반드시 Manifest에 축별 1줄 근거와 함께 기록해 감사 가능하게 만들고, 판정 *결과의 귀결*(어떤 오버레이·문서가 붙는가)은 `routing.md`의 결정론적 조회 테이블로, Hard Gate는 고정 체크리스트에 항목별 명시적 yes/no로, 스키마·ID 유일성·링크 해석·문서 예산 검사는 순수 스크립트로 처리한다. 이 분리가 있어야 "잘못된 패키지가 나왔을 때 분류가 틀렸는지(LLM) 라우팅이 틀렸는지(테이블)"를 구분해 고칠 수 있다. 여기에 골든 픽스처 10건(요청문 → 기대 Manifest)을 두고 규칙 수정 때마다 재실행하면 하네스 자체가 회귀 테스트를 갖는다 — 오분류가 나올 때마다 픽스처에 추가.
- **메타데이터 부패 방지 원칙: 소비자 없는 필드 금지.** GPT frontmatter의 `informed_by`, `last_reviewed`, `related_specs`는 검증기가 읽거나 커맨드가 자동 갱신하지 않는 한 3개월 안에 거짓말이 된다. `doc_status`/`work_status` 이중 상태는 팀에겐 옳지만 1인 환경에선 work_status의 SSOT가 git/이슈/현실 그 자체이므로, 문서에는 최소 상태(draft/active/superseded)만 두고 상태 전이는 커맨드로만 일어나게 한다. `catalog.yaml`은 frontmatter에서 **생성되는 파생 인덱스**여야 하며 절대 손으로 병행 관리하지 않는다. 링크는 경로가 아닌 ID로만(파일 이동·아카이브 시 링크가 살아남는 유일한 방법, grep으로 해석 가능). GPT 제안에 빠진 치명적 필드가 하나 있다: **`schema_version`** — 여러 프로젝트에 걸쳐 재사용하려면 프로젝트가 하네스 스키마 버전을 고정(pin)할 수 있어야 하네스 업그레이드가 구 프로젝트 검증을 깨지 않는다.
- **Core+Overlay는 GPT 제안 중 유지보수 관점에서 가장 옳은 부분이나, 오버레이는 파일이 아니라 섹션이어야 한다.** 공통 코어 수정이 한 곳에서 일어나는 DRY 구조는 강력 지지. 단 Change/Feature 계층에서는 오버레이를 **한 파일 안에 병합되는 섹션**으로 두고(Change=1파일 1페이지 이내, Feature=PRD+Tech Spec 2파일), 폴더는 Initiative에만 허용한다. 파일 수 폭발은 사람과 LLM 양쪽의 검색성을 죽이는 제1의 유지보수 킬러다.
- **과잉 문서화는 토큰 문제이기 전에 컨텍스트 위생 문제다.** 생성된 모든 문서는 미래 세션이 읽어야 할 부채이며, 낡은 문서는 미래 LLM 컨텍스트를 오염시킨다. 방어선은 (1) `work/` 종료 후 동결 — 동결된 문서는 "역사"로 명시되어 현재 사실로 오독되지 않는 GPT 제안 최고의 방부제, (2) 공통 사실만 `current/`로 승격, (3) 계층별 문서 예산을 검증기가 강제, (4) Manifest의 `omitted` 목록으로 "안 쓴 이유"를 싸게 기록. 저장 구조는 v1에서 `current/`·`work/`·`decisions/` 3개만 만들고 `evidence/`·`releases/`·`archive/`는 첫 필요 시 추가한다 — 폴더 추가는 링크를 깨지 않는 안전한 성장이지만, 빈 스캐폴딩은 방치의 신호가 되는 안티패턴이다.

### Risks & blind spots

- **최대 리스크는 설계 결함이 아니라 이탈(adoption failure)이다.** Change 한 건 처리에 5분 이상 걸리면 사용자는 하네스를 우회해 그냥 코딩하기 시작하고, 그 순간부터 문서는 현실과 어긋난다 — 오도하는 문서는 문서 없음보다 나쁘다. GPT 제안은 온톨로지 완결성을 최적화했지 filing cost를 최적화하지 않았다. Change 경로는 질문 0~1개, 산출물 1파일로 끝나야 한다.
- **분류 재현성:** 같은 요청이 세션마다 다르게 분류될 수 있다(LLM 분산). Manifest의 축별 근거 기록 + `/plan`의 사용자 1회 확인 게이트가 완충하지만, 완전한 해결은 아니므로 오분류 픽스처 축적이 유일한 장기 교정 수단이다.
- **소스 문서 자체가 불완전하다:** 이 파일에는 빈 코드펜스가 7곳 있다(203-205, 238-241, 326-328, 362-365, 426-428, 442-444, 469-471행 부근) — GPT가 언급한 "전략·리서치·기술의 비계층 관계 다이어그램" 등이 붙여넣기 과정에서 유실됐다. 이 문서를 완전한 스펙으로 취급해 구현하면 안 되고, 유실 부분은 재구성이 필요하다.
- **크로스 프로젝트 드리프트:** 프로젝트별로 라우팅 규칙·템플릿을 조금씩 다르게 쓰고 싶어지는 순간이 반드시 온다. 템플릿 포크는 금지하고, 프로젝트 루트에 명시적 override 파일 하나(`planning-config.yaml` 등)만 허용해야 하네스 코어가 하나로 유지된다.
- 다른 관점들이 놓칠 것: 이 하네스의 진짜 산출물은 문서가 아니라 **6개월 뒤의 자신(그리고 미래의 LLM 세션)이 신뢰하고 읽을 수 있는 상태**다. "설계가 얼마나 정교한가"보다 "규칙 파일을 고쳤을 때 무엇이 깨졌는지 알 수 있는가"(픽스처), "필드가 거짓말하는지 기계가 잡아주는가"(검증기)가 이 시스템의 수명을 결정한다.

### Confidence

`high` — 지적한 실패 모드(메타데이터 부패, 수동 상태 필드의 진부화, 택소노미 과성장, 파생 인덱스의 수동 병행 관리)는 문서 시스템에서 반복 검증된 패턴이고, 리포지토리가 그린필드(초기 커밋뿐)라는 사실과 1인 환경이라는 제약이 축소-후-증축 전략을 직접적으로 뒷받침한다.

## 🗳️ Simplicity Champion

### Position

GPT 제안은 다인(多人) 조직의 PM 관료제를 — 승인자·법무팀·이해관계자가 존재한다는 전제 그대로 — 1인 개발자의 LLM 하네스에 이식한 과잉 설계다. 살릴 아이디어는 3개(hard gate, current/work 분리, append-only decisions)뿐이고, 나머지는 3-tier + 게이트 체크리스트 + 템플릿 3개 + `/plan` 슬래시 커맨드 1개로 대체하는 것이 옳다.

### Key points

- **개념 수를 세어보면 답이 나온다.** 파일 속 제안을 합산하면: 객체 유형 7 + 평가축 5 + 보조값 2 + hard gate 8 + 코어 섹션 9 + 오버레이 모듈 10 + 저장 영역 7 + 루트 파일 5 + frontmatter 필드 13 + doc_status 5 + work_status 8 + 종결 상태 4 + 하네스 디렉토리 6 ≈ **80개 이상의 구분 개념**이다. 이 관료제의 운영자는 사람이 아니라 세션마다 리셋되는 LLM인데, LLM이 가장 못하는 것이 바로 "세션 간 일관된 분류·상태 갱신"이다. 유지되지 않을 체계는 설계하지 않은 것만 못하다. 내 안은 tier 3 + gate ~6 + 템플릿 3 + 상태 4 + frontmatter 5필드 + 저장 위치 3 ≈ 25개다.
- **GPT의 "S/M/L 반대" 논리는 1인 환경에서 무너진다.** 객체 유형 7개 중 대부분이 같은 문서로 수렴한다: Experiment는 "AC가 질문인 Feature brief"고, Platform/Migration은 "migration/rollback 섹션이 있는 Feature"이며(GPT 스스로 "얇은 Product Brief + Tech Spec"이라 인정), Strategy·GTM은 분류기가 라우팅할 문서 유형이 아니라 `current/`에 놓인 살아있는 파일 1~2개다. 5축도 마찬가지: Coordination은 1인이라 상수, Scope·Impact는 "blast radius" 하나로 수렴, Risk는 hard-gate 체크리스트가 이미 결정론적으로 처리한다. 남는 실질 질문은 딱 2개 — **"영향 범위가 얼마나 넓은가"와 "무엇을 만들지 아는가"** — 이고, 이건 5축 평가 양식이 아니라 두 줄짜리 판단이다.
- **권장 아키텍처: `/plan` 커맨드 1개 + 3 tier + 결정론적 escalator.** Tier 0(Quick): 문서 0개, 대화 내 5줄 계획 후 바로 기술 스펙 워크플로우로(사용자가 이미 기술 스펙은 별도 고정 워크플로우라고 못박았으므로 기획 하네스의 출구는 여기다). Tier 1(Brief): 파일 1개, 템플릿 1개 — 문제/결과/범위·비범위/AC/열린 질문/실행계획 + "해당 없으면 삭제"하는 optional 섹션들(hypothesis, migration, measurement). 오버레이 "모듈 시스템"이 아니라 **한 템플릿 안의 선택 섹션**이면 충분하다. Tier 2(Charter): charter 1개 + 자식 brief들 — 계층이 존재하는 유일한 tier이며, 마일스톤 계획은 별도 문서가 아니라 charter의 섹션이다. Escalator는 결정론적: hard gate(결제·인증/개인정보·데이터 삭제·마이그레이션·공개 API·비가역 변경) 하나라도 걸리면 최소 Tier 1 + risk/rollback 섹션 강제, "뭘 만들지 모름"이면 별도 Discovery 문서 유형이 아니라 **첫 마일스톤을 spike로** 지정.
- **deterministic vs LLM 경계, 그리고 validation의 정체.** 결정론: gate 트리거 키워드 목록, tier→템플릿 매핑, 파일 위치 규칙. LLM: tier 판정, 내용 작성, 섹션 취사. 그리고 분류의 validation은 rubric이나 validator 스크립트가 아니라 **사용자의 1클릭 확인**이다 — 1인 환경에서는 판정자가 항상 그 자리에 있고, 이것이 어떤 자동 검증보다 싸고 정확하다. Planning Package Manifest는 삭제하라: 유일한 소비자가 같은 워크플로우의 다음 단계인 중간 YAML 아티팩트는 순수한 직렬화 의례다. 분류 결과는 문서 머리 frontmatter 5줄(status, tier, parent, created, gates)로 족하고, manifest의 유일한 좋은 아이디어인 "검증 전 하위 PRD 미작성"은 charter의 bullet 목록("추후 brief")으로 표현된다.
- **저장·SSOT: 살릴 것만 살려라.** `current/`(살아있는 사실) vs `work/`(동결되는 변경 기록) 분리는 이 파일에서 가장 가치 있는 아이디어다 — 채택. `decisions/`는 폴더 2개가 아니라 **append-only `decisions.md` 파일 하나**로 시작. 삭제할 것: `catalog.yaml`(파일과 반드시 드리프트하는 레지스트리 — grep/Glob이 이미 쿼리 엔진이고, 드리프트한 카탈로그는 LLM이 거짓을 진실로 읽게 만들어 없느니만 못하다), 7종 ID 네임스페이스(FEAT/INIT/GOAL/INSIGHT/SPEC/REL/PRODUCT — git 저장소에서 파일 경로가 이미 안정 ID이며 상대 링크로 충분), doc_status·work_status 이중 상태머신(합쳐서 draft/active/done/dropped 4개 — "released이지만 measured 아님"은 상태가 아니라 닫을 때 문서에 쓰는 "결과" 섹션이다), `evidence/`·`releases/`·빈 스캐폴드 폴더(첫 실사용 시점에 추가). 참고로 repo를 확인했는데 현재 그린필드(discussion 문서 + README뿐)이므로 작은 설계를 택하는 비용이 정확히 0이다.
- **구현 가능성·이식성은 내 안이 명백히 우위다.** GPT 안(`routing-rules/ schemas/ templates/ overlays/ lifecycle-rules/ validators/`)은 슬래시 커맨드 6개+와 validator 런타임 규모다. 내 안은 **런타임 코드 없이 SKILL.md(라우팅 규칙 + gate 목록 1페이지) + 템플릿 3개**가 전부라서, 같은 마크다운 파일이 Claude Code 스킬로도, Codex의 프롬프트/AGENTS.md로도 그대로 재사용된다 — "여러 프로젝트에 걸쳐 재사용"이라는 요구는 하네스가 순수 instructions+templates일 때 가장 잘 충족된다. 토큰 절약도 구조로 해결된다: Tier 0은 문서 0개, 분류 산출은 ≤10줄, plan 시 읽는 컨텍스트는 부모 charter + `current/` 요약으로 상한을 둔다.

### Risks & blind spots

- **내 렌즈의 한계:** 사용자가 조만간 실제로 결제·법무가 걸린 대형 initiative를 돌린다면 Tier 2가 얇게 느껴질 수 있다. 다만 비대칭이 핵심이다 — 필요할 때 섹션·폴더를 **추가**하는 비용은 몇 분이지만, 안 쓰는 85개 개념 체계를 **축소**하는 비용은 마이그레이션이다. 확장은 싸고 축소는 비싸다.
- **GPT 안(및 정교화를 선호하는 다른 렌즈)이 놓치는 것: LLM 운영 관료제의 silent rot.** work_status 8단계(idea→…→measured→closed)를 갱신할 사람이 없다. 엔터프라이즈에선 상태 부패를 사람이 눈치채지만, 1인+LLM 체계에선 아무도 감사하지 않고, 미래 세션의 LLM이 부패한 메타데이터를 사실로 읽는다. 구조가 작을수록 부패할 표면도 작고, git+grep은 레지스트리가 아니라 내용에서 진실을 복원한다.
- **질문 프레이밍 자체의 맹점:** "분류 기준을 얼마나 정교하게 만들까"가 아니라 **"오분류의 비용이 얼마인가"**가 진짜 설계 변수다. 1인 환경에서 오분류 비용은 거의 0이다(승인자 없음, 즉시 tier 승급 가능). 오분류가 싸면 분류기는 단순해야 한다 — 정교한 분류기는 오분류가 비싼 조직에서만 이자를 낸다.
- 문서 체계의 주 소비자가 사람이 아니라 **미래의 LLM 세션**이라는 점도 간과되기 쉽다: 사람용 탐색성(깊은 폴더 택소노미, 진입점 파일 5개)보다 짧음·grep 가능성·단일 파일 응집이 우선이다.

### Confidence

`high` — repo가 그린필드라 마이그레이션 비용이 0이고, "1인 개발"이라는 명시 조건이 GPT 설계의 전제(다팀 조율·승인 체계)를 직접 무효화하며, 확장이 축소보다 싸다는 비대칭은 이 케이스에서 반박하기 어렵다.

## Round 2: 상호 비판 (rebuttals)

*각 멤버는 다른 두 멤버의 Round 1 전문과 Codex 제안 요지를 받아 반박·수용·고수를 작성했다.*

## 🗳️ Scalability Architect — Rebuttal

### Strengths in others

- **Maintainability — 골든 픽스처 10건.** 이번 라운드 전체에서 스케일 관점 최고의 아이디어다. 오분류가 발생할 때마다 픽스처가 늘어난다는 것은 **분류 품질이 사용량과 함께 단조 증가**한다는 뜻이고, 이것이 LLM 분류기가 스케일에서 살아남는 유일한 구조다. 부수 효과가 더 크다: 모델 교체(Claude→Codex→차기 모델)는 1인 하네스의 가장 확실한 "스케일 이벤트"인데, 픽스처는 그 마이그레이션의 회귀 스위트가 된다. 벤더 중립 markdown 규칙 + 얇은 어댑터 구조도 같은 이유로 옳다.
- **Maintainability — "기계적 소비자 없는 메타데이터 금지."** 이것은 유지보수 규칙으로 포장된 토큰 예산 규칙이다. GPT 원안의 `informed_by`, `last_reviewed`, `related_specs`는 소비자가 없으면 매 Read마다 컨텍스트 토큰을 태우는 죽은 하중이다. "커맨드 4개가 유일한 상태 변경 경로"도 단일 라이터 직렬화로서 정확하다. "Change 한 건 5분 초과 시 우회 시작"은 사실상 **최빈 경로의 p99 레이턴시 SLO**이며, 내 Round 1의 "진짜 스케일 축은 사람 손"을 나보다 날카롭게 정식화했다.
- **Simplicity — "확장은 싸고 축소는 비싸다."** 불확실한 부하 앞에서 업그레이드 경로만 보존한 최소 프로비저닝, 정통 용량 계획 원리다. "문서 주 소비자는 미래 LLM 세션이므로 짧음·grep 가능성·단일 파일 응집"도 스케일 통찰이다 — 희소 자원은 컨텍스트 윈도우이고, 단일 파일 응집은 조회 팬아웃(Read N회 → 1회)을 최소화한다. T0에 문서 0개를 배정한 것도 옳다: 최고 빈도 경로가 최저 오버헤드를 가져야 한다.
- **Codex — 수치 상한과 재사용 선행.** `max_tokens_total 5000, max_depth 3, max_overlays 4` 같은 고정 수치는 세 로컬 멤버 중 누구도 안 낸 **기계 검증 가능한 예산**이다. "패키지 결정 전 재사용 검색 선행"은 write 전 dedup, 즉 캐시 정책으로서 정확하고 내가 놓친 것이다. confidence 낮으면 인간 승인 강제도 옳은 백프레셔다.

### Weaknesses & rebuttals

**Simplicity의 "manifest·catalog·ID 전부 삭제, grep이면 충분, validation은 1클릭" — 어디까지 맞고 어디서 틀리는가.**

1. **Manifest 삭제 — 소비자 분석이 틀렸다.** "유일한 소비자가 다음 단계"라는 전제가 오류다. 소비자는 최소 셋 더 있다. (a) **재개(resume) 경로**: 1인 환경에서 가장 자주 죽는 컴포넌트는 디스크가 아니라 세션이다(컴팩션, 크래시, 노트북 덮기). 체크포인트 없는 분류는 재개 시 가장 비싼 토큰을 두 번 내고, 더 나쁘게는 **두 번째에 다른 답이 나온다** — "LLM이 가장 못하는 게 세션 간 일관된 분류"라는 Simplicity 본인의 명제가 자기 제안을 벤다. (b) Maintainability의 골든 픽스처는 직렬화된 분류 출력이 있어야 assert할 수 있다. manifest를 지우면 픽스처 회귀 테스트의 비교 대상이 사라진다. (c) T0로 분류했던 게 T2로 판명났을 때의 블랙박스(비행기록). 단, 형식 비판은 수용한다 — 아래 Concessions 참조.
2. **Catalog 삭제 — grep의 CPU가 아니라 토큰이 문제다.** grep은 수천 파일에서도 공짜다. 그건 나도 안다(Round 1: "1인 규모에서 문서 개수는 병목 아님"). 비용은 **결과를 컨텍스트로 소비하는 쪽**에 있다. "active인데 parent 없는 feature는?", "이 brief를 supersede한 건 뭐지?", "X와 관련해 이미 뭐가 있지?" — 이건 문자열 매칭이 아니라 조인·발견 쿼리라, 인덱스가 없으면 LLM이 파일 N개를 읽어 머릿속에서 조인한다. 인덱스면 Read 1회다. 그리고 grep의 최악 실패는 **조용한 miss**다: 파일이 이동한 뒤 옛 경로 문자열을 grep하면 LLM은 "못 찾은 걸 모른 채" 진행한다. Simplicity의 드리프트 비판은 **수기 관리 카탈로그**에만 유효하다 — 나도 그건 반대했다. 훅에서 재빌드되는 파생 인덱스는 **구조적으로 드리프트가 불가능**하다. "관리하거나-없애거나"는 거짓 이분법이고, materialized view라는 세 번째 선택지를 그는 논박하지 않고 건너뛰었다.
3. **ID 삭제 — 자기 설계와 모순된다.** Simplicity는 current/work 분리와 /plan-close(닫을 때 "결과" 섹션)를 **살렸다**. 즉 그의 설계에서도 파일은 이동한다(work→archive, 승격). 경로가 ID인 시스템에서 이동은 모든 인바운드 상대 링크를 깨고, 그걸 고치려면 링크 인덱스(=지운 catalog)와 재작성 스크립트(=지운 validator)가 필요하다. 삭제한 두 부품이 삭제한 세 번째 부품의 전제였던 셈이다. 게다가 이 사용자 환경엔 지금 codex·claude 워크트리 2개를 병렬로 띄우는 `race` 스킬이 실재한다 — 두 워크트리가 같은 경로를 다르게 만들면 경로-ID는 머지에서 충돌하지만, `feat-20260812-email-auth`형 ID는 생성 시점에 충돌이 구조적으로 불가능하다. GPT 원안의 FEAT-014 순차 ID가 틀렸다는 데는 동의하나, 답은 "ID 폐지"가 아니라 "충돌 불가능한 ID"다.
4. **1클릭 validation — 가용성과 용량을 혼동했다.** "판정자가 항상 그 자리에 있다"는 맞다. 그러나 그 판정자의 주의력이 **시스템 전체에서 가장 희소한 자원**이다. 깨진 링크·누락 섹션·예산 초과·고아 문서 같은 기계적 속성을 눈으로 검사시키는 것은, Simplicity 자신이 두려워하는 "5분 넘으면 우회"를 유발하는 바로 그 toil이다. 인간의 1클릭은 기계가 못 하는 단 하나 — "이 분류·계획이 말이 되는가" — 에 예약하고, 나머지는 토큰 0원·클릭 0회·O(n) 스크립트가 매번 돌면 된다. 100줄 파이썬 훅은 CI 관료제가 아니다.
5. **"런타임 코드 0, SKILL.md가 전부" — 개념 수를 세고 상주 토큰을 안 셌다.** SKILL.md의 25개 개념은 **매 세션 컨텍스트에 상주하며 과금되고**, 프롬프트 강제는 컨텍스트 압박이 심해지는 긴 세션 후반 — 규율이 가장 필요한 순간 — 에 확률적으로 무너진다. 스크립트의 복잡도는 컨텍스트 밖에 살고 한계 토큰 비용이 0이다. 로직을 프롬프트에서 스크립트로 옮기는 것이 이 시스템에서 가장 레버리지 큰 오프로딩인데, Simplicity의 설계는 정확히 그 반대로 **컨텍스트에 상주해야 하는 것을 극대화**한다.
6. **"오분류 비용 ≈ 0" — 비대칭을 뭉갰다.** 과소분류가 싼 것은 승급 경로가 쌀 때뿐인데, 승급을 싸게 만드는 부품(체크포인트)을 그가 지웠다. 과대분류는 토큰 낭비에 더해 **미래 세션이 읽을 코퍼스를 오염**시킨다("오도하는 문서는 무문서보다 나쁨" — 그가 동의한 Maintainability의 명제). 비용은 0이 아니라 비대칭이다.

**Codex의 "Graph Store / 큐 워커 / 샤딩" — 어디까지 맞고 어디서 틀리는가.**

1. **성장 축을 잘못 짚었다.** 1인 개발자의 100x는 요청 처리량이 아니다 — 쓰기 수요는 하루 한 자릿수에 상한이 인간의 직렬 주의력이고, **병목이 운영자 자신이면 샤딩할 파티션이 존재하지 않는다.** 실제로 100x가 되는 것은 누적 코퍼스(archive), 링크 밀도, 세션 수, 그리고 컨텍스트 윈도우 압박이다. 그 성장 축의 해법은 hot/cold 티어링·파생 인덱스·토큰 예산이지 큐 스루풋이 아니다. Codex는 처리량 문제를 풀었는데, 출제된 것은 보존·조회 문제다.
2. **Postgres/Neo4j + Git mirror는 고전적 dual-write다.** 디렉토리 하나에 다 들어가는 마크다운 수백 장을 위해 진실 소스 2개와 상시 동기화 데몬, 그리고 백업·마이그레이션·업타임이라는 운영 표면을 산다. Git이 이미 그 데이터베이스다: 내용 주소화 저장, 원격 복제, 트랜잭션(커밋), 타임트래블, 쿼리 엔진(grep+인덱스). 기획 시스템에 DB 프로세스라는 **하드 가용성 의존성**을 추가하는 것은 음(-)의 스케일링이다.
3. **큐·idempotency key·2단계 커밋 — 본능은 옳고 기계가 과대하다.** 중간에 죽은 /plan-docs가 파일 3개 중 2개만 쓴 상태의 재실행 안전성은 실제 문제다. 그러나 해법은 결정적 경로 + 파일 존재 검사(멱등성 공짜) + 충돌 불가능 ID이고, 최악의 경우에도 advisory flock 하나다. 마크다운 파일에 2PC는 분산 시스템 코스프레다.
4. **Ops Adapter(이슈트래커·분석 webhook/CI 동기화)** — 동기화 표면 하나하나가 상시 정합성 부채이고, 이 순간부터 기획 하네스에 업타임 요구사항이 생긴다. 1인 시스템이 가장 피해야 할 것이 "돌봐야 하는 인프라"다.
5. 공정하게: 훗날 다중 프로젝트 연합이 필요해져도 답은 각 repo의 catalog를 읽는 **읽기 전용 집계 스크립트**까지다. 여전히 DB는 아니다. Codex 안에서 가져갈 것은 인프라가 아니라 수치 상한과 재사용-선행 정책이다.

**Maintainability — 동의가 많지만 두 곳은 반대한다.**

1. **"저장 구조 v1은 current/·work/·decisions/ 3개, 나머지는 첫 필요 시 추가" — 릴리프 밸브에는 틀린 휴리스틱.** 기능은 필요 시 추가가 맞지만, archive/는 **부하 방출 밸브**다. 그 필요는 이벤트로 오지 않고 누적 압력으로 오며, work/에 200개가 쌓인 뒤의 이동 도입은 마이그레이션이 된다(그가 가장 싫어할 종류의). 빈 archive/ 디렉토리 + /plan-close의 승격 규칙 한 줄은 지금 공짜다. 공짜일 때 밸브를 달아라.
2. **"오버레이는 한 파일 안의 섹션" — 기본값으론 옳지만 분리 임계가 없다.** 조회 응집(Read 1회)으로는 병합이 이긴다. 그러나 migration 오버레이의 롤백 런북처럼 **실행 단계에서 반복 조회되는 뜨거운 섹션**이 PRD 한가운데 박히면, 구현 세션마다 PRD 전체 토큰을 다시 낸다. hot/cold 티어링은 유닛 사이만이 아니라 유닛 안에도 적용된다 — "N회 이상 단독 조회되거나 X줄 초과 시 분리"라는 임계 규칙이 필요하다.
3. 사소하지만: 픽스처는 분류기를 오프라인에서 검증할 뿐, 파이프라인 실행 자체의 비용 상한이 없다. Codex의 수치 예산을 그의 validator에 배선해야 완결된다.

### Concessions

1. **T0 무문서화 (← Simplicity).** 내 Round 1의 T0(Brief 1장)는 오타 수정급 작업엔 한 단계 무거웠다. 수정한다: T0 = 파일 0개, 대화 내 계획, 기록은 git 커밋. 단, 조건부다 — 결정론적 escalator와 일급 /plan-reclassify(내 Round 1이 지적한 최흔 실패 모드)가 전제다. 승급이 예외가 아니라 정상 경로가 되도록 설계한다.
2. **Manifest의 형식 (← Simplicity).** 별도 YAML 파일은 철회한다. T1+에서 문서를 **frontmatter만 먼저 쓰고 멈추는 방식**(승인 후 본문 채움)으로 바꾸면 체크포인트 의미론은 보존되고 파일 수는 늘지 않는다. Simplicity의 "직렬화 의례" 비판은 내 요구사항이 아니라 내 포맷을 바꿨다.
3. **골든 픽스처 채택 (← Maintainability).** 내 validator의 범위를 구조 린트 단층에서 **구조 린트 + 분류 회귀** 2층으로 수정한다. schema_version의 프로젝트별 pin도 내 additive-only 규칙을 날카롭게 만들었으므로 채택.
4. **재사용 검색 선행 + 수치 예산의 기계 검증 (← Codex).** /plan의 생성 전 단계에 "기존 문서 검색→수정/supersede/신규 판정"을 넣고, 내 "tier별 길이 예산"을 Codex식 고정 수치로 못박아 린트에 배선한다. 인프라는 기각하되 상수는 채택.
5. **스케일 축의 재정식화 (← Maintainability).** "이탈이 최대 리스크"는 내 "사람 손이 스케일 축"의 상위 명제다: 우회는 운영자 측의 load shedding이며, 수요 자체가 증발한다. T0 5분 SLO를 모든 예산의 구속 조건으로 삼는다.

### Defenses

1. **단계 경계의 디스크 체크포인트는 고수한다.** 이 시스템에서 신뢰할 수 없는 컴포넌트는 저장소가 아니라 세션이다. crash-only 설계의 답은 늘 같다: 비싼 계산(분류) 결과를 경계마다 디스크에 남겨라. 형식은 양보했고(frontmatter-first) 요구사항은 양보하지 않는다.
2. **파생 catalog는 고수한다.** 훅 재빌드 materialized view는 상시 토큰 0, 재빌드 O(n), 구조상 드리프트 불가이며, 링크 validator가 어차피 만들어야 하는 링크 그래프의 공짜 부산물이다. 그리고 내 Round 1의 "문서 개수는 병목 아님"과 모순이 아니다: **개수는 병목이 아니고, 컨텍스트에 들어가는 토큰이 병목**이다. catalog는 grep이 느려서가 아니라 파일 N개 대신 인덱스 1개를 읽게 하는 토큰 방패로서 존재한다.
3. **타입-날짜-슬러그 ID는 고수한다.** 이동(승격·아카이브)이 설계에 내장된 이상, 그리고 병렬 워크트리가 이 환경의 현재형 사실인 이상, 경로-ID는 조용히 깨진다. Maintainability도 독립적으로 같은 결론("링크는 경로가 아닌 ID로")에 도달했다 — 이 논점에서 Simplicity는 혼자이고, 그의 반례는 그 자신이 살려둔 기능과 모순된다.
4. **스크립트 검증은 강하게 고수한다.** 인간은 유닛당 한 번 정책을 승인하고, 기계는 영원히 0토큰으로 역학을 검사한다. 역할을 바꾸면 시스템은 운영자 피로 속도로 스케일한다.
5. **DB·큐·샤딩 불가는 강하게 고수한다.** git이 저장소이고, 단일 인간 라이터는 샤딩 불가능한 병목이며, 연합이 필요해지는 날의 해법도 catalog 위의 읽기 전용 집계 스크립트까지다.

### Revised position

토론 후 내 최종 입장: 섀시는 Maintainability의 "얇은 결정론적 척추"(3계층 유닛, 라우팅 테이블, 커맨드 4개가 유일한 변이 경로, 골든 픽스처, schema pin)를 그대로 쓰되, 그 위에 스케일이 실제로 요구하는 세 부품 — (1) 세션 사망을 전제한 단계 경계 디스크 체크포인트(별도 manifest 파일이 아니라 frontmatter-first 생성으로 구현), (2) 훅이 재빌드하는 파생 catalog(토큰 방패이자 링크 validator의 부산물), (3) 이동과 병렬 워크트리에 견디는 타입-날짜-슬러그 ID — 를 양보 없이 얹는다. Simplicity에게서는 T0 무문서 고속 경로와 frontmatter 5줄의 검약, 그리고 "미래 LLM 세션이 주 소비자"라는 소비자 정의를 가져오고, Codex에게서는 인프라를 전부 기각하는 대신 고정 수치 예산과 생성 전 재사용 검색을 가져온다. 이 시스템의 100x는 요청 처리량이 아니라 누적 코퍼스와 세션 수이며, 구속 조건은 호출당 컨텍스트 토큰과 운영자 주의력(T0 5분 SLO) 둘뿐이다 — 따라서 모든 메커니즘은 "상시 토큰 0(스크립트·훅·파생 인덱스), 경계마다 디스크 체크포인트, 이동·병렬에 안전한 ID"라는 세 시험을 통과해야 하고, 그 시험을 통과하지 못하는 것(그래프 DB, 큐, 샤딩, 눈으로 하는 린트, 프롬프트 상주 강제 규칙)은 부하가 실물로 도착하기 전까지 만들지 않는다.

## 🗳️ Maintainability Advocate — Rebuttal

### Strengths in others

**Scalability Architect.** (1) `feat-20260812-email-auth` 식 타입-날짜-슬러그 ID는 유지보수 관점에서도 정답이다. 순차 ID(FEAT-014)는 "다음 번호" 라는 중앙 상태를 요구하고, 중앙 상태는 곧 관리해야 할 메커니즘이다. 조정이 전혀 필요 없는 ID 체계는 유지보수 대상이 하나 줄어드는 것이고, 날짜가 박힌 이름은 그 자체로 자기문서화다. (2) `/plan-reclassify` 부재가 최흔 실패 모드라는 지적은 뼈아프게 옳다. 재분류 경로 없는 분류 체계는 스키마 마이그레이션 없는 스키마다 — 첫 오분류 순간부터 분류 전체가 거짓말이 되기 시작한다. 내 Round 1의 4개 커맨드에는 이게 없었다. (3) catalog을 수기 편집 금지 파생 인덱스로 본 것, validator를 토큰 0원 스크립트로 둔 것은 내 입장과 수렴한다.

**Simplicity Champion.** (1) "주 소비자는 미래 LLM 세션, 짧음·grep 가능성 우선"은 이 토론 전체에서 가장 날카로운 유지보수 통찰이다. 문서의 독자가 세션마다 리셋되는 LLM이라면 장문 문서는 컨텍스트 윈도우 안에서 썩는다. (2) "확장은 싸고 축소는 비쌈"은 내 "기계적 소비자 없는 필드 금지" 원칙을 프로세스 전체로 일반화한 것이고, 방향이 옳다. (3) "해당 없으면 삭제" 선택 섹션 방식은 내 "오버레이=한 파일 안의 병합 섹션"과 사실상 같은 결론이다. (4) 드리프트하는 카탈로그는 해악이라는 지적 — 현실과 어긋날 수 있는 모든 산출물은 유지보수 부채라는 원칙의 정직한 적용이다.

**Codex.** (1) 수치 제한(max_depth 3, max_overlays 4, max_tokens_total 5000)은 스크립트로 강제 가능한 종류의 규칙이라 값지다 — 정책으로서 옳다. (2) "재사용 검색 선행"은 내 Round 1이 과소평가한 지점이다. 중복 문서는 문서 부패의 1순위 경로인데, 내 /plan에는 "기존 유닛 먼저 검색" 단계가 없었다. (3) LLM 산출물을 스키마 검증 후 반영한다는 원칙 자체는 내 척추와 동일하다.

### Weaknesses & rebuttals

**Simplicity Champion — "validation은 사용자 1클릭": 6개월 뒤 유지 불가능하다.** 이 주장은 판단(judgment)과 검증(verification)을 뭉갠다. 인간은 "이 계획이 타당한가"는 판정할 수 있지만, "모든 링크가 살아있는가, frontmatter가 파싱되는가, 예산을 넘겼는가"를 클릭 한 번으로 검증하지 않는다 — 어떤 클릭도 인바운드 링크 전체를 보지 않기 때문이다. 6개월 뒤 문서 80개 시점에 파일 하나를 rename하면 인바운드 링크 6개가 죽는데, 1클릭은 이걸 구조적으로 못 잡는다. 그리고 인간의 클릭은 습관화된다: 1클릭은 3주 안에 0확인 도장이 된다. 스크립트의 존재 이유는 습관화되지 않는다는 것이다. 결정적으로 이 주장은 그 자신의 공리와 모순된다. "운영자는 세션마다 리셋되는 LLM, 세션 간 일관된 상태 갱신이 LLM 최약점"이라고 해놓고, 상태 무결성을 인간의 주의력과 LLM의 자율 규율에 맡긴다. 세션 리셋에서 살아남는 유일한 기억은 repo이고, repo를 완전한 기억력으로 읽는 유일한 리뷰어는 스크립트다. 그는 결정론의 최강 논거를 제시하고 결론에서 그것을 버렸다. 덧붙이면, 그의 "grep이 쿼리 엔진" 주장도 몰래 내 validator에 의존한다 — grep 가능성은 공짜가 아니라 일관된 키·슬러그 명명 규율의 산물이고, 그 규율을 강제하는 것이 바로 스크립트다. 카탈로그를 지울 자격은 validator가 있을 때만 생긴다.

**Simplicity Champion — "상태 4개(draft/active/done/dropped)면 충분": superseded가 빠지면 그의 다른 원칙이 죽는다.** done과 superseded는 미래 세션이 반드시 구별해야 하는 차이다. done 문서는 "출시됐고 여전히 사실일 수 있는" 기록이고, superseded 문서는 "지금은 틀렸으며 대체물이 어디인지 가리켜야 하는" 기록이다. superseded를 지우면 6개월 뒤 어떤 세션이 grep으로 옛 가격 정책 문서(done)를 찾아 현재 사실로 소비한다 — "오도하는 문서는 무문서보다 나쁘다"는, 그 자신도 동의한 원칙이 정확히 이 지점에서 무너진다. superseded는 `superseded_by` 포인터라는 기계적 소비자를 가진 유일한 종결 상태다. 상태 하나에 소비자 하나 — 내 razor로도 이건 남는다.

**Simplicity Champion — "ID 네임스페이스 삭제, 파일 경로가 ID": 자기 설계와 충돌한다.** 그는 current/work 분리를 살리자고 했다. 그 분리는 파일 이동(work→동결→archive, 승격)을 전제한다. 경로가 ID면 모든 이동이 모든 인바운드 링크를 깨뜨린다. 선택지는 셋뿐이다: (a) 파일을 안 옮긴다 — 그가 살린 생명주기가 죽는다. (b) 이동 때마다 링크를 전부 재작성한다 — 그가 지운 도구가 부활한다. (c) 링크가 썩게 둔다. 경로-ID와 파일 생명주기는 양립 불가능하고, 그는 둘 다 골랐다. 해법은 이미 이 테이블 위에 있다: Scalability의 날짜-슬러그를 파일명으로 쓰고 링크는 슬러그로 걸면, 레지스트리도 카탈로그도 카운터도 없이 이동 불변 ID가 생긴다. 파일명이 ID, 디렉터리가 생명주기다.

**Simplicity Champion — "오분류 비용 ≈ 0": gate 미스에는 성립하지 않는다.** 분류가 hard gate 평가를 건너뛰게 만들면(결제·개인정보·마이그레이션) 비용은 0이 아니라 gate가 존재하는 이유 그 자체다. 그는 gate를 살렸지만, 질문 2개짜리 분류기가 gate를 확인했다는 기록을 아무 데도 남기지 않으면, 6개월 뒤 gate 미스를 디버깅할 방법이 없다 — 무엇을 확인했는지 기록이 없는 시스템은 실패를 재현할 수 없다. 또 T0의 "대화 내 5줄 계획"은 유일하게 소실이 보장된 저장 매체에 계획을 두는 것이다(세션 리셋은 그의 공리다). 원본 대화 파일에서 GPT의 다이어그램 7개가 빈 코드펜스로 유실된 것이 정확히 이 실패의 실물 표본이다. 5줄은 커밋 메시지 본문이나 append-only decisions 로그(그가 살린 그것)로 흘려보내면 파일 0개 유지라는 그의 목표를 깨지 않고 흔적이 남는다.

**Codex — PGO는 1인이 유지보수할 수 없고, 유지보수할 이유도 없다.** 컴포넌트 7개는 계약·버전·실패 모드를 가진 표면 7개다. 질문은 "만들 수 있는가"가 아니다(LLM은 뭐든 만든다). "6개월 뒤 OS 업데이트로 Neo4j가 깨졌을 때 제품 개발을 멈추고 그걸 고칠 사람이 누구인가"다. Postgres/Neo4j/큐 워커는 제품 가치 0인 운영 부채이고, git+파일은 이미 수천 명이 운영해주는 인프라다. Graph Store는 git의 일을 복제한다: 관계=frontmatter 링크, 쿼리=grep, 이력=git log. "Git mirror"라는 말 자체가 자백이다 — mirror는 sync를, sync는 drift를, drift는 감시가 필요한 reconciliation 작업을 낳는다. 1인 시스템은 정확히 이렇게 죽는다. 그리고 "markdown 파일을 위한 2단계 커밋"은 그 자체로 귀류법이다. 10x/100x 대비 큐·샤딩도 마찬가지다: 1인 개발자의 요청률 상한은 한 인간의 타이핑 속도다. 100x 요청은 구조적으로 도래하지 않고, 도래하는 것은 100x 문서인데 그건 큐 문제가 아니라 grep·lint 문제다. 발생 불가능한 부하를 위한 코드는 음(-)의 유지보수 가치다 — 존재하는 한 살려둬야 하므로. Ops Adapter는 두 번째 백엔드가 실존하지 않는 한 speculative generality다(내 Claude/Codex 어댑터는 두 백엔드가 오늘 실존하므로 다르다 — 추상화는 두 번째 구체가 도착했을 때 정당화된다). "confidence 낮으면 인간 승인"도 조직 모델의 오적용이다: 1인 하네스에서 인간 승인은 무조건적이다. confidence가 gate해야 할 것은 인간이 보느냐가 아니라 하네스가 무엇을 제안하느냐다(낮으면 spike/discovery 제안). Codex 안의 올바른 부분은 전부 정책 테이블이고 틀린 부분은 전부 런타임이다 — 숫자는 내 validator 설정으로 컴파일해서 가져가고, 기계는 통째로 버려야 한다.

**Scalability Architect — 메커니즘 증식과 잘못된 최적화 축.** (1) open-loops 리포트·hot/cold tiering·lint 예산은 각각 새 메커니즘이다. 1인 환경에서 읽히지 않는 리포트는 그 자신이 드리프트 생성기다(그가 받아들인 카탈로그 논리 그대로). open-loops는 별도 산출물이 아니라 기존 validator의 플래그(`--all`에서 종결 상태 없는 work/ 항목 나열)로 접어야 한다. 메커니즘은 접지 말고 늘리지 말라. (2) progressive disclosure 토큰 스테이징(2K rubric → 단계별 템플릿 로드)은 싼 축(토큰)을 최적화하려고 비싼 축(하네스 자체의 인간 이해 가능성)에 구조 비용을 지불한다. 파일 수·로드 순서 규칙이 늘어나는 5파일 파이프라인보다, 소유자가 2분에 다시 읽는 1페이지 SKILL.md가 낫다. 그 스스로 "진짜 스케일 축은 호출당 토큰과 사람 손"이라 해놓고 설계의 상당 부분이 토큰 축을 최적화한다 — 토큰 단가는 떨어지고 인간 주의력은 떨어지지 않으므로, 유지보수는 이 둘을 엄격히 서열화한다: 사람 손 >> 토큰. 스테이징은 자연스러운 파일 배치(스킬+템플릿 디렉터리)에서 공짜로 떨어질 때만 취하라. (3) "Manifest는 쿼리 플랜" 은유는 우아하지만 끝까지 밀면 그의 산출물을 배신한다: 실제 DB에서 쿼리 플랜은 실행 후 폐기되는 일시물이다. 은유에 충실하려면 manifest는 실행 후 독립 파일로 존속하면 안 되고 — 이는 아래 내 양보(frontmatter로의 붕괴)를 오히려 지지한다. 체크포인트 파일도 close 시 동결·삭제 규칙이 없으면 work/가 쓰레기의 콜드 스토리지가 된다. (4) additive-only + schema_version 지지는 옳지만 함정을 안 짚었다: 필드가 영원히 죽지 않으면 2년 뒤 frontmatter는 고고학 발굴지가 된다. additive-only에는 스키마 파일 내 deprecation 표기("field X는 vN부터 무시")가 짝으로 붙어야 한다.

### Concessions

내 Round 1 입장을 실제로 수정한 것들이다. 관통하는 줄기는 내 자신의 razor("기계적 소비자 없는 산출물 금지")를 내 설계에 되먹인 것이다.

1. **ID 체계 (← Scalability):** 순차 ID와 일체의 ID 레지스트리를 버리고 타입-날짜-슬러그 파일명을 ID로 채택한다. Simplicity의 "경로가 ID"도 절반 흡수된다: 파일명 부분이 ID, 디렉터리 부분이 생명주기.
2. **재분류 (← Scalability):** /plan-reclassify를 추가한다(기존 유닛 대상 /plan 재실행으로 접는 형태). 이것 없는 내 4-커맨드 설계는 불완전했다.
3. **Manifest의 형태 (← Simplicity):** 독립 YAML 산출물로서의 Manifest를 철회한다. 소비자가 다음 단계뿐인 중간 직렬화라는 비판이 옳다. 분류 기록(tier, gate 체크 결과, 질문별 1줄 근거)은 해당 유닛 파일의 frontmatter ~5줄로 붕괴한다. 기록의 존재는 사수하되(Defenses 참조) 그릇을 양보한다.
4. **5축 → 2질문 + gate (← Simplicity):** 1인 환경에서 Coordination은 상수이고 Scope/Impact는 "blast radius"로 접힌다는 붕괴를 수용한다. Uncertainty만 독립 질문으로 남긴다 — discovery/spike 모드로 라우팅하는 유일한 축이라 기계적 귀결이 있기 때문이다.
5. **카탈로그 (← Simplicity):** "파생 인덱스로 유지"에서 "v1에는 없음, grep으로 충분"으로 후퇴한다. 단, 삭제가 아니라 연기다 — 스크립트 소비자가 실제로 등장하는 시점(예: 문서 100개 초과 또는 크로스 프로젝트 쿼리 필요)을 트리거 조건으로 명문화한다.
6. **T0 무파일 (← Simplicity):** Change 최하위 계층은 기획 파일 0개를 수용한다. 단 5줄 흔적은 대화가 아니라 커밋 메시지 본문 또는 decisions 로그 한 줄로 남긴다는 조건부다.
7. **재사용 검색 선행 (← Codex):** /plan 1단계에 "기존 유닛 grep 검색" 을 명시한다. 내 Round 1의 누락이었다.

### Defenses

1. **스크립트 검증은 사수한다 (vs Simplicity).** 단, 분업을 명확히 해서: 구조(스키마·링크·예산·gate 기록 존재)는 스크립트, 실질(이 계획이 맞는가)은 인간 1클릭. 근거는 위 반박 그대로 — repo가 유일한 세션 간 기억이고, 그것을 완전한 기억력으로 읽는 리뷰어는 스크립트뿐이며, 인간 클릭은 습관화된다. 비용 반론도 선제한다: 이 validator는 YAML·링크·글자수 검사 ~100줄이고, 벤더 중립이라 Claude/Codex 교체에서도 살아남는다. "런타임 코드 없음"이 지키려는 가치(이식성)를 스크립트가 더 잘 지킨다.
2. **superseded 상태는 사수한다 (vs Simplicity).** 4개+1: draft/active/done/dropped에 superseded(`superseded_by` 필수)를 더한다. 기계적 소비자를 가진 유일한 추가 상태이며, 없으면 미래 세션이 폐기된 사실을 현재 사실로 소비한다.
3. **골든 픽스처 10건은 사수한다 (vs Simplicity의 "런타임 없음" 함의).** 픽스처가 테스트하는 것은 코드가 아니라 rubric 프롬프트다: 고정 요청문 10건에 /plan을 돌려 tier+gate 결과를 기대값과 diff한다. 재분류에서 얻은 교훈을 rubric에 반영할 때(반드시 하게 된다) 픽스처만이 조용한 회귀를 막는다. 회귀 테스트 불가능한 프로세스는 비가시적으로 열화한다 — 이것이 하네스 자신의 유지보수성이다. 비용은 명령 한 번이다.
4. **분류 기록의 존재는 사수한다 (vs Simplicity의 Manifest 전면 삭제).** 그릇은 frontmatter로 양보했지만, 기록 자체는 블랙박스 비행기록계다. gate 미스를 디버깅하고 픽스처를 증식시키는 입력이 이것이다. "오분류 비용 ≈ 0"은 gate에 대해 거짓이다.
5. **schema_version은 사수한다.** Simplicity의 razor로 공격받을 필드지만, 소비자가 실존한다: validator와 미래의 마이그레이션 스크립트. 그리고 유일하게 사후 소급이 불가능한 필드다 — 버전 없는 파일이 몇 버전인지는 나중에 알아낼 방법이 없다. 한 줄로 진화 경로 전체를 산다. additive-only + deprecation 표기와 짝으로.
6. **파일+git이 곧 Graph Store다 (vs Codex).** 솔로 하네스의 어느 성숙 단계에서도 Postgres/Neo4j/큐/2PC를 거부한다. 솔로의 성숙은 인프라 증설이 아니라 픽스처 증가와 rubric 개선이다. 내 얇은 2-어댑터(Claude/Codex)는 두 구체 백엔드가 오늘 실존하므로 Codex의 Ops Adapter와 범주가 다르다.

### Revised position

토론 후 내 최종 입장은 "얇은 결정론적 척추"를 더 얇게 깎되 척추의 뼈는 하나도 빼지 않는 것이다: 계층은 T0(파일 0, 흔적은 커밋 메시지·decisions 로그)/T1(1페이지 1파일, 해당 없으면 삭제하는 섹션형 오버레이)/T2(charter+자식 brief)로 하고, 분류는 질문 2개(blast radius, 무엇을 만들지 아는가)+명시적 hard gate 체크리스트로 붕괴시키되 그 답과 gate 결과를 유닛 파일 frontmatter ~5줄에 기록한다(독립 Manifest 폐기, 기록은 존속); ID는 타입-날짜-슬러그 파일명이고 링크는 슬러그로 걸어 레지스트리·카탈로그 없이 이동 불변성을 얻으며(카탈로그는 v1 부재, 트리거 조건부 연기), 상태는 draft/active/done/dropped+superseded(`superseded_by` 포인터가 유일한 추가 상태의 존재 이유)로 하고, 검증은 구조=스크립트(~100줄: 스키마·링크·예산·gate 기록·open-loop 플래그)/실질=인간 1클릭으로 분업하며, /plan에는 재사용 검색 선행과 /plan-reclassify를 추가하고, 골든 픽스처 10건이 rubric 편집마다 하네스 자신을 회귀 테스트하며, schema_version+additive-only+deprecation 표기로 진화 경로를 열어두고, Codex의 수치 제한은 validator 설정으로 흡수하되 PGO 런타임 전체(Graph Store·큐·2PC·Ops Adapter)는 어느 단계에서도 거부한다 — 판정 기준은 끝까지 하나다: 이 하네스의 모든 메커니즘은 소유자가 한 자리에서 다시 설명할 수 있고, 명령 한 번으로 테스트되고, 고고학 없이 삭제 가능해야 하며, 그 기준을 통과하지 못하는 것은 기능이 아니라 부채다.

## 🗳️ Simplicity Champion — Rebuttal

### Strengths in others

- **Scalability의 "LLM은 제안, 결정론은 강제" 원칙**: 이것은 사실 단순성 원칙이다. 세션마다 리셋되는 LLM의 일관성을 신뢰할 필요가 없는 구조 — 내가 Round 1에서 GPT 원안을 공격한 핵심 근거를 그가 설계 원칙으로 더 깔끔하게 정식화했다. 또 "1인 규모에서 문서 개수는 병목이 아니다, 그래프 DB 만들지 마라"는 자기 절제는 이 council에서 가장 정직한 문장 중 하나다.
- **Scalability의 병렬 워크트리 지적**: 이 사용자는 실제로 /race로 codex·claude를 동일 프롬프트, 워크트리 2개에서 돌린다. 순차 ID(FEAT-014)의 전역 카운터가 경쟁 상태라는 지적은 관념이 아니라 이 사용자의 실사용 시나리오다.
- **Maintainability의 "기계적 소비자 없는 메타데이터 필드 금지"**: council 전체에서 가장 좋은 한 줄 설계 법칙. 내 "manifest는 직렬화 의례" 주장을 나보다 잘 일반화했다. 그리고 "Change 한 건이 5분 넘으면 우회가 시작된다"는 이탈 프레임은 단순성을 수사학이 아니라 지연 예산으로 계량화했다 — 이 5분을 하네스의 수용 기준으로 훔쳐가겠다. 오버레이를 파일이 아니라 한 파일 안의 섹션으로 본 것도 내 결론과 독립적으로 수렴했다: 수렴이 아니라 검증이다.
- **Codex의 Round 2 자기 수정 방향**: Project 제거, max_depth 3·max_overlays 4 같은 고정 수치 제한, 패키지 결정 전 재사용 검색(생성 전 Grep 한 번이면 되는 싼 규칙). 수치 캡은 한 줄이고 메커니즘은 시스템이다 — 캡 쪽으로 기운 것 자체가 옳은 본능이다. "무증거 생성 금지"도 규칙으로서는 옳다.

### Weaknesses & rebuttals

**Scalability에게.**

1. **/plan-index 파생 인덱스는 상환할 쿼리가 없다.** Materialized view는 비싼 조회를 다수의 읽기로 상환할 때 정당화된다. 문서 100개 미만에서 그 "비싼 조회"는 Grep+Glob 수십 ms이고, 결과의 소비자는 어차피 행동하려면 파일 본문을 읽어야 하는 LLM이다. 인덱스가 아끼는 것은 0에 수렴하고, 새로 사는 것은 재빌드 스크립트 1개, 재빌드를 잊지 않게 할 훅 1개, 그리고 "재생성 전의 낡은 인덱스를 LLM이 진실로 읽는" 실패 모드다. "결정론적으로 재빌드된다"는 보장은 재빌드가 실제로 실행됐을 때만 성립하고, 그걸 보장하는 훅이 또 하나의 가동부다. 본인 입으로 "문서 개수는 병목 아님"이라 했다 — 그 순간 인덱스의 존재 이유가 본인 논증 안에서 소멸한다. 트리거를 명명하고 기다려라: "Grep이 체감상 느려진 날" 추가하면 된다.
2. **훅 기반 validator 파이프라인은 공짜가 아니다.** "토큰 0원"이지만 (a) 훅은 도구별 설정이다 — Claude settings.json의 훅은 Codex로 이식되지 않는다. 본인이 세운 벤더 중립성 목표가 본인 메커니즘에서 먼저 깨진다. (b) 편집마다 발화하면 90% 케이스인 T0에 지연세를 물린다 — Maintainability의 5분 예산이 validator 소음으로 소진된다. (c) 1인 환경에서 오탐하는 validator의 최종 상태는 "사용자가 꺼버림"이다. 정직한 버전은 파이프라인이 아니라 /plan-close가 실행하는 스크립트 1개다. 검증 빈도는 편집 빈도가 아니라 의사결정 빈도에 맞춰야 한다.
3. **단계 경계 디스크 체크포인트(manifest → docs → validation report → plan)는 워크플로우 엔진 사고의 이식이다.** 보호 대상인 "비싼 실행"이 markdown 1~2개 생성이다. T1 brief 재생성 비용은 몇 센트, 체크포인트·재개 기계의 스펙 비용은 그 재실행 전액을 영원히 상회한다. 살아남는 체크포인트는 "파일 쓰기 전 승인 정지" 하나뿐이고, 그것은 대화 내 확인이지 영속 YAML이 아니다. Progressive disclosure 논점 자체는 옳지만 디스크 산출물 없이 성립한다: SKILL.md가 rubric을 싣고, 선택된 템플릿 파일 하나만 읽으면 된다 — 그것은 파이프라인이 아니라 파일 구성이다. 특히 "validation report" 파일은 내가 Round 1에서 죽인 "소비자 1명짜리 중간 YAML"을 다른 단계에서 개명 부활시킨 것이다.

**Maintainability에게.**

1. **4개 커맨드는 본인의 5분 예산과 충돌한다.** 커맨드는 인간의 의사결정 지점마다 하나여야 하는데, 여기 결정은 둘뿐이다: "무엇을 얼마나 기획할까"(분류+확인+생성)와 "닫아도 되나"(검증+동결+승격). /plan을 돌린 뒤 /plan-docs를 안 돌리는 시나리오가 존재하는가? 승인은 /plan 안에서 이미 끝났다 — /plan-docs는 결정이 아니라 이어지는 턴이다. /plan-validate는 /plan-close가 어차피 실행할 스크립트의 단독 메뉴 항목, 즉 사용 사례 없는 메뉴다. 또 "커맨드가 유일한 상태 변경 경로"는 텍스트 파일 세계에서 강제 불가능하다. 사용자는 반드시 파일을 직접 고친다. 설계는 그것을 전제로 생존해야 한다 — 상태가 frontmatter 한 줄이면 생존하고, 커맨드 경유를 전제한 이중 부기면 깨진다.
2. **골든 픽스처 10건은 오분류 비용 ≈ 0인 분류기를 위한 테스트 인프라다.** 픽스처가 사는 것: 러너, 출력 비교기, 템플릿이 진화할 때마다의 유지보수, 실행마다 LLM 호출 10번. 잡는 것: 3-way 선택 + 자기교정 escalator가 이미 싸게 흡수하는 오류. 같은 증거를 더 싸게 쓰는 방법이 있다: 분류가 틀릴 때마다 그 요청문을 SKILL.md rubric에 예시로 붙인다("예: X → T1, 근거 …"). 프롬프트 속 예시는 분류기를 직접 개선하고, 테스트 하네스 속 픽스처는 개선 없이 검사만 한다. 진단은 받고 장치는 기각한다 — 덤으로, rubric에 쌓인 예시는 훗날 정말 러너가 필요해지는 날 그대로 픽스처 데이터가 된다. 문은 열어두되 지금 짓지 마라.
3. **routing.md 분리는 드리프트 제조기다.** 행 3개짜리 라우팅 테이블은 테이블이 아니라 산문이다. SKILL.md의 tier 설명이 곧 라우팅이다. 파일을 나누는 순간 "rubric은 A라는데 테이블은 B"라는, LLM이 가장 못 견디는 종류의 모순을 하네스가 스스로 공급하게 된다. 게이트 8개 × 강제 오버레이 매핑까지 넣어도 SKILL.md 10줄이다.
4. **"ID 링크만이 이동에서 생존한다"는 과장이다.** 이 설계에서 이동은 정확히 한 번, close 시점에, 스크립트에 의해 일어난다. 같은 스크립트가 링크를 재작성하거나 구 경로에 1줄 tombstone을 남기면 끝 — 5줄이다. 그것을 아끼려고 모든 링크에 영원히 ID 간접층을 물리는 것은 나쁜 거래이고, 결정적으로 ID는 resolver를 요구한다. 그 resolver의 이름이 무엇인가? catalog다. 본인이 파생 인덱스로 강등시킨 그 catalog를, ID 링크가 하드 의존성으로 재승격시킨다. 경로 링크의 resolver는 파일시스템이다.

**Codex에게.**

1. **PGO 7컴포넌트는 셸 스크립트의 마이크로서비스 다이어그램이다.** 1인 환경에서의 실체: Request Intake = 사용자가 타이핑, Rule Engine = SKILL.md rubric 20줄, Manifest Composer = 같은 LLM 턴, Execution Planner = 문서의 plan 섹션, Graph Store = 파일시스템, Policy Validator = 스크립트 1개, Ops Adapter = git commit. 프로세스가 아닌 컴포넌트는 문단일 뿐인데, 컴포넌트라고 명명하는 순간 언젠가 프로세스가 되리라는 가정이 밀수되고, 그래서 Postgres/Neo4j·큐 워커·idempotency key·2단계 커밋이 따라 들어온다. 정당화 규모를 명시한다. 큐 워커: 기획 요청이 무인 상태에서 처리 속도보다 빨리 도착할 때 — 외부 요청자(팀, 접수 폼, 자율적으로 기획을 발의하는 에이전트 플릿)가 생겼을 때다. 기준은 문서 수가 아니라 동시 요청자 수 > 1이다. Graph Store: 링크의 이행적 추적·영향 분석을 프로그램이 상시 질의하고 frontmatter Grep이 측정 가능하게 실패할 때 — 현실적으로 문서 수천 개 + 저장소 횡단이다. 둘 다 1인의 지평선에 없고, 둘 다 같은 파일 포맷 뒤에 나중에 끼울 수 있다 — 나중에 끼울 수 있다는 사실 자체가 지금 짓지 말라는 논증이다. 본인의 Round 2 수정(max_depth 3, 필수 필드 최소화)이 내 논점을 증명한다: 깊이 3에 필드 7개짜리 그래프의 이름은 frontmatter다.
2. **D0~D3 + max_tokens_by_stage는 4번째 분류 차원이다.** tier가 이미 깊이를 결정한다. 별도 깊이 축은 우리 모두가 방금 붕괴시킨 조합 폭발 rubric의 재도입이다. 장황함은 config가 아니라 템플릿의 한 줄("이 문서는 1페이지를 넘지 않는다")로 잡는다.
3. **유사 요청 캐시·렌더 캐시**: 주 몇 회 실행되는 생성 단계에 캐시 무효화라는 유명한 난제를 사서 센트를 아낀다. **2단계 커밋**: git의 working tree가 초안이고 commit이 확정이다 — git이 이미 2단계 커밋이다. **idempotency key**: 파일명이 idempotency key다.
4. **"confidence 낮으면 인간 승인 강제"**: 조건부 게이트는 confidence 추정이라는 새 문제를 산다. 더 단순한 불변식이 이를 포섭한다: 항상 승인받는다. 1인 환경에서 승인 클릭은 1초, 조건 분기는 스펙이다.

### Concessions

1. **병렬 워크트리 ID 충돌 (Scalability) — 수정한다.** 내 Round 1의 "파일 경로가 안정 ID"는 명명 규칙을 특정하지 않았고 병렬 케이스를 아예 고려하지 않았다. 전역 카운터가 경쟁 상태라는 진단을 수용하고, 폴더명을 `type-YYYYMMDD-slug`(예: feat-20260812-email-auth)로 명시한다 — 그의 슬러그 ID를 경로 안으로 흡수한 것이고 비용은 규약 한 줄이다. 단, 하나는 짚어둔다: 동일 프롬프트 레이스는 동일 슬러그를 낳아 머지 충돌을 내는데, 그것은 버그가 아니라 기능이다. 같은 요청의 기획서 2벌은 반드시 조정돼야 하고 경로 충돌이 그것을 표면화한다. 순차 ID였다면 FEAT-014와 FEAT-015로 조용히 갈라졌을 것이다.
2. **재분류 경로 (Scalability) — 전면 수용.** 내 escalator는 대화 중 상향만 다뤘고 "이틀 지나 보니 이 T1은 T2였다"에 답이 없었다. 수정: 기존 폴더 위에서 /plan 재실행 = 재분류. 있는 것을 읽고 델타를 제안한다(brief → charter 승격, decisions 보존). 새 커맨드 0개, SKILL.md 한 문장. 하향은 안 쓴 섹션의 삭제이므로 별도 지원이 필요 없다 — 지원할 방향은 상향뿐이라는 비대칭도 명시한다.
3. **schema_version (Maintainability) — 절반 수용.** pin-and-migrate 기계는 v1에 과잉이지만, 필드 자체는 그의 법칙("기계적 소비자 없는 필드 금지")의 유일하게 원칙 있는 예외다: 소비자가 미래의 v2이고, 사후 복원이 불가능하다(어느 템플릿 버전이 그 문서를 썼는지는 나중에 알아낼 방법이 없다). frontmatter에 `harness: v1` 한 줄을 추가한다 — 내 5줄이 6줄이 된다.
4. **세션 간 분류 재현성 (Maintainability) — 진단 수용, 장치 기각.** 나는 오분류 비용 ≈ 0만 말했는데 그가 가리킨 것은 다른 비용이다: 같은 요청이 세션마다 다르게 분류되는 비일관성 자체가 신뢰와 문서 코퍼스의 일관성을 침식한다. escalator는 틀림을 고치지만 흔들림은 못 고친다. 수용 형태는 rubric 예시 축적(in-prompt few-shot) — 그의 픽스처 데이터를 그의 러너 없이 쓰는 것이다.
5. **create_after_validation의 죽은 약속 (Scalability) — 수용.** manifest를 죽였으니 유예된 문서가 어디 사는지 답해야 했다: T2는 charter의 마일스톤 체크리스트, T1은 brief의 "나중에" 줄. /plan-close 스크립트가 미체크 박스를 grep한다 — 그의 open-loops 리포트를 close 스크립트의 grep 한 줄로 이행한다.

### Defenses

1. **Manifest 파일은 여전히 없다.** Scalability의 "쿼리 플랜" 방어는 계획과 실행 사이에 수 자릿수 비용 격차가 있을 때 성립하는데, 여기서 실행은 markdown 1~2개 생성이다. Maintainability의 "감사 가능성" 방어는 수용하되 위치를 옮긴다: 분류 결과와 축별 1줄 근거는 생성된 문서의 frontmatter/헤더에 산다(tier, gates, why). 감사 가능성은 보존되고 산출물 수는 늘지 않는다. 승인 클릭 10초 뒤에도 살아 있는 manifest는 영수증이고, 영수증은 문서 옆이 아니라 문서 안에 붙인다. 파일 쓰기 전에 분류를 사용자에게 보여 1클릭 확인받는 절차는 유지한다 — 대화 텍스트로, YAML 파일로가 아니라.
2. **검증 = 의사결정 지점의 인간 확인 + close 시점 스크립트 1개.** Scalability의 구조적 불신("LLM이 게이트를 조용히 건너뜀")에 대한 답: 게이트 8문항의 yes/no 출력은 사용자가 반드시 보는 유일한 장소인 승인 메시지에 인쇄된다 — 조용한 생략이 구조적으로 시끄러워진다. 산문 문서에 대한 스키마 검증 스크립트는 검사 가능한 것(frontmatter 키)만 검사하고 실질(롤백 계획이 진짜인가)을 놓친다. 실질의 판정자는 인간뿐이고 1인 환경에서 그는 항상 그 자리에 있다. 기계 검증은 /plan-close의 스크립트 1개(링크 해석, 미체크 박스, 상태 설정)로 족하다.
3. **커맨드 2개, tier 3개를 고수한다.** 인간의 결정이 두 개뿐이기 때문이다. 문서 생성과 검증은 결정이 아니라 결정 내부의 단계다.
4. **파생 인덱스 없음, ID resolver 없음, 링크는 상대 경로.** 이동 문제는 close 스크립트의 링크 재작성/tombstone으로 지불한다(위 양보의 대가이며, 이것이 ID 체계 전체보다 싸다).
5. **개념 예산과 이식성.** 양보로 추가된 것은 명명 규약 1줄, harness 버전 1줄, 재분류 1문장, open-loop grep 1줄 — ≈ 25가 ≈ 28이 됐고 여전히 시스템이 아니라 줄들이다. "확장은 싸고 축소는 비싸다"와 정합적이다. 벤더 이식성 논거도 유지한다: SKILL.md+템플릿+스크립트는 Codex AGENTS.md로 복사 이식되지만, 훅 파이프라인·큐·그래프 스토어는 이식되지 않는다.

### Revised position

최종안: 커맨드 2개(/plan = 분류 → 게이트 8문항 출력 → 1클릭 확인 → 문서 생성, 기존 폴더 위 재실행은 재분류; /plan-close = 스크립트 1개로 링크 검사·미체크 박스 grep·승격·동결), tier 3개, SKILL.md 1페이지(rubric + 게이트 + 오분류 때마다 축적하는 few-shot 예시), 템플릿 3개(빈 섹션은 삭제), 폴더명 `type-YYYYMMDD-slug`, frontmatter 6줄(status/tier/parent/created/gates/harness), append-only decisions, current/work 분리 — 런타임 코드는 close 스크립트 하나뿐이다. Scalability에게서 슬러그 명명·재분류 경로·open-loop 검사를, Maintainability에게서 harness 버전 줄·재현성 진단(장치가 아닌 예시 축적으로 이행)·5분 예산을, Codex에게서는 수치 캡의 본능만 템플릿 가드레일로 가져왔다. 인덱스·훅 파이프라인·4커맨드·픽스처 러너·PGO·큐·그래프 스토어는 각각 명명된 관측 가능한 트리거("Grep이 느려질 때", "동시 요청자 > 1", "문서 수천 + 저장소 횡단")가 울릴 때까지 짓지 않으며, 그 트리거 중 어느 것도 n=1에서 관측되지 않는다. 이 하네스의 수용 기준은 Maintainability의 예산을 그대로 채택한다: Change 한 건이 분류→확인→문서화까지 5분 안에 끝나지 않으면, 그 실패의 원인은 기능 부족이 아니라 과잉이다.

## Synthesis (v1 — codex gpt-5.3 실행 기준; 이후 gpt-5.6-sol 재실행을 반영한 최종 synthesis는 `03-codex-gpt5.6-debate-and-final-synthesis.md` 참조)

*(하이브리드 카운슬: Codex cross-vendor debate + 로컬 Claude 카운슬 3역할 × 2라운드. 로컬 3인은 모두 같은 모델(Claude)이므로 로컬 멤버 간 합의는 독립 검증이 아니라 공유 프라이어의 반복일 수 있다. 반면 Codex(gpt-5.3-codex-spark)와 로컬 멤버가 서로 못 본 채 수렴한 지점은 진짜 cross-vendor 신호다.)*

### Consensus (합의점 — cross-vendor 수렴 포함)

1. **GPT 원안의 뼈대는 옳고 규모는 틀렸다.** "요청 크기가 아니라 의사결정의 종류·불확실성·위험에 비례한 문서 묶음" 방향, hard gate, current/work(현재 사실 vs 동결되는 변경 기록) 분리, 합산 점수 금지는 4자 전원 채택. 그러나 7개 객체 유형 × 5축 × 10 오버레이 × 이중 상태머신(≈80개 개념)은 1인+LLM 운영에서 유지 불가 — 전원 축소.
2. **Planning unit은 3-tier**: T0 Change / T1 Feature / T2 Initiative. Experiment·Strategy·GTM·Platform은 독립 유형이 아니라 라벨·선택 섹션·current/ 상시 문서. Codex도 Round 2에서 Project를 의사결정 단위에서 스스로 제외.
3. **Rule-First + LLM Compose**: LLM은 제안(분류 제안, gate 탐지, 문서 내용), 결정론적 규칙은 강제(gate→필수 섹션 매핑, tier→템플릿 매핑, 상태 전이, 길이 예산).
4. **인프라 없음**: Graph Store(Postgres/Neo4j)·큐 워커·샤딩·2단계 커밋·Ops Adapter는 로컬 3인 만장일치로 기각 — 1인의 요청률 상한은 인간의 직렬 주의력이라 샤딩할 파티션이 없고, git+파일이 이미 그 데이터베이스다. Codex에게서 살아남은 것은 수치 상한(max_depth 3, max_overlays 4, 길이 캡)과 "생성 전 재사용 검색"뿐.
5. **순차 ID(FEAT-014) 금지**: 이 사용자의 실환경(race/Orca 병렬 워크트리)에서 전역 카운터는 경쟁 상태. `type-YYYYMMDD-slug` 명명으로 충돌을 구조적으로 차단.
6. **frontmatter 최소주의**: "기계적 소비자 없는 메타데이터 필드 금지" — GPT 원안의 13필드는 부패 예정. ~6줄(status/tier/parent/created/gates/harness_version)로.
7. **벤더 중립 코어**: 하네스 = markdown 규칙(SKILL.md) + 템플릿 + 스크립트. Claude Code/Codex엔 얇은 어댑터만.
8. **수용 기준 = 이탈 방지**: Change 한 건이 5분 넘으면 우회 시작 → 하네스 사망. 최빈 경로(T0)는 문서 0개.

### Divergence — 해결된 이견 (토론에서 입장이 실제로 이동)

1. **독립 Manifest 파일 → 폐기, 기록은 존속**: Scalability가 형식을 양보(frontmatter-first 체크포인트), Maintainability가 그릇을 양보. 최종: 분류 결과(tier·gate yes/no·축별 1줄 근거)는 생성된 문서의 frontmatter에 살고, 승인은 파일 쓰기 전 대화 내 1클릭.
2. **5축 평가 → 2질문 + gate**: Coordination은 1인 환경에서 상수, Scope·Impact는 "blast radius"로 수렴, Risk는 gate가 결정론 처리, Uncertainty만 독립 축(spike/discovery 라우팅 트리거).
3. **T0 무문서화**: Scalability가 Brief 1장에서 파일 0개로 양보 — 단 흔적은 대화가 아니라 커밋 메시지/decisions 한 줄(세션은 유일하게 소실이 보장된 저장 매체).
4. **상태 머신**: 이중 상태(5+8) 기각 → draft/active/done/dropped + **superseded**(superseded_by 포인터 필수 — "기계적 소비자를 가진 유일한 추가 상태").
5. **재분류 경로**: 전원 수용 — 별도 커맨드가 아니라 기존 유닛 위 /plan 재실행 = 재분류(델타 제안, decisions 보존).
6. **저장 구조 v1**: current/ + work/ + decisions.md(append-only) 3개로 시작, evidence/·releases/는 첫 필요 시.

### Divergence — 남은 이견 (구현 중 결정 필요)

1. **파생 catalog 인덱스**: Scalability "조인·발견 쿼리의 토큰 방패, 훅 재빌드면 드리프트 불가" vs Simplicity "문서 100개 미만에선 상환할 쿼리가 없고 재빌드 훅이 또 하나의 가동부". 수렴된 처리: v1엔 없음, 트리거 명문화(grep 체감 저하 / 문서 ~100+ / 크로스 프로젝트 질의).
2. **검증의 형태와 시점**: 스크립트 존재 자체와 "의사결정 시점 실행"은 합의. 훅 파이프라인·독립 /plan-validate는 미합의(2:1 기각 우세).
3. **골든 픽스처 러너 vs rubric few-shot**: 오분류 데이터 축적은 합의. 러너를 지금 짓느냐(Maintainability)/트리거 전까지 rubric 예시로만 쓰느냐(Simplicity)는 미합의.
4. **커맨드 개수**: 4개 vs 2개. Simplicity 논거(커맨드 = 인간 의사결정 지점, 결정은 2개뿐)가 토론 후 우세.
5. **링크 표기**: slug-ID 링크(이동 불변, 2표) vs 상대 경로 + close 스크립트 재작성/tombstone(1표). 폴더명 slug는 합의라 실질 차이는 작음.

### 가장 강한 비판 (토론 하이라이트)

- Maintainability→Simplicity: "'세션마다 리셋되는 LLM'을 공리로 세워놓고 상태 무결성을 인간 주의력과 LLM 자율 규율에 맡겼다 — 결정론의 최강 논거를 제시하고 결론에서 버렸다. 인간 1클릭은 3주 안에 0확인 도장이 된다."
- Scalability→Simplicity: "삭제한 두 부품(catalog·validator)이 삭제한 세 번째 부품(경로-ID)의 전제였다. 가장 자주 죽는 컴포넌트는 디스크가 아니라 세션이다."
- Simplicity→Codex: "PGO 7컴포넌트는 셸 스크립트의 마이크로서비스 다이어그램. 'Git mirror'라는 말 자체가 자백이다. 깊이 3에 필드 7개짜리 그래프의 이름은 frontmatter다."
- Scalability→Codex: "병목이 운영자 자신이면 샤딩할 파티션이 존재하지 않는다. 처리량 문제를 풀었는데, 출제된 것은 보존·조회 문제다."
- Simplicity→Scalability: "'validation report' 파일은 네가 죽인 '소비자 1명짜리 중간 YAML'의 개명 부활이다. 훅은 도구별 설정이라 네가 세운 벤더 중립성 목표를 네 메커니즘이 먼저 깬다."

### Recommendation (권장 아키텍처 — 하나)

**"얇은 결정론적 척추(Thin Deterministic Spine)" 하네스** — 토론 후 3인의 수정 입장이 수렴했고 Codex의 유효 성분을 흡수한 안:

- **유닛/티어**: T0 Change(파일 0, 흔적은 커밋 메시지·decisions 한 줄) / T1 Feature(1파일: 문제·결과·범위·AC·열린 질문·실행계획 + "해당 없으면 삭제" 선택 섹션 — hypothesis·migration·measurement·gtm) / T2 Initiative(charter + 자식 brief들, 마일스톤은 charter 섹션). 기술 스펙은 사용자의 기존 고정 워크플로우로 출구 연결.
- **분류(LLM 제안 + 인간 확정)**: 2질문(blast radius / 무엇을 만들지 아는가) + hard gate 체크리스트(결제·개인정보/보안·법무·데이터 삭제·마이그레이션·외부 API·비가역 변경). gate yes/no를 승인 메시지에 인쇄 → 사용자 1클릭 → 확정. gate 1개 이상이면 최소 T1 + risk/rollback 섹션 강제. uncertainty 높으면 별도 Discovery 유형이 아니라 첫 마일스톤 = spike. 오분류 발생 시마다 SKILL.md rubric에 few-shot 예시 축적.
- **기록**: 독립 manifest 없음. frontmatter 6줄(status/tier/parent/created/gates/harness_version), 상태 5개(draft/active/done/dropped/superseded+superseded_by). 분류 근거 축별 1줄을 문서 머리에.
- **저장/ID**: 폴더명 `type-YYYYMMDD-slug`. current/(살아있는 사실) + work/(종료 후 동결) + decisions.md(append-only). 승격은 close 체크리스트("다른 작업이 다시 참조할 공통 사실만 승격" — GPT 원안 유지).
- **커맨드 2개(+재분류는 재실행)**: `/plan` = 재사용 검색(grep) → 분류 → gate 인쇄 → 1클릭 → 생성; 기존 유닛 위 재실행 = 재분류. `/plan-close` = 구조 검증 스크립트(frontmatter 스키마·링크 해석·미체크 박스·open-loop·길이 예산) → 동결 → 승격 → 상태 확정. 검증은 의사결정 시점에만(훅 아님).
- **배포**: 벤더 중립 코어(SKILL.md 1페이지 + 템플릿 3 + close 스크립트 ~100줄) + Claude/Codex 얇은 어댑터. 프로젝트별 override 파일 1개, 템플릿 포크 금지.
- **명명된 트리거 전까지 짓지 않는 것**: 파생 catalog(grep 체감 저하/문서 100+), 픽스처 러너(축적된 rubric 예시가 그날의 데이터), 훅 파이프라인, 그래프 DB·큐·샤딩(동시 요청자>1, 수천 문서+저장소 횡단).

### 구현 우선순위

1. **SKILL.md v1** — tier 3 정의, 2질문 rubric, gate 8 체크리스트, 상태·frontmatter·명명 규약, few-shot 자리. (하네스의 80%)
2. **템플릿 3개** — T0 규약, T1 brief(선택 섹션 포함), T2 charter. 길이 캡 명기.
3. **/plan 커맨드** — 재사용 검색→분류→gate 인쇄→1클릭→생성, 재실행=재분류.
4. **/plan-close + 검증 스크립트** — 링크·미체크박스·스키마·예산, 동결·승격 체크리스트.
5. **운영 루프** — 오분류→rubric 예시 추가; decisions.md 축적; 트리거 감시.
6. **(조건부) 다중 프로젝트 확장** — harness_version pin, override 파일, 필요 시 catalog 도입.

### 전원이 같은 이유로 틀릴 수 있는 지점

- 4자 모두 "가볍게"로 수렴 — 축소 편향이 공유 프라이어일 수 있다. 결제·법무가 걸린 대형 Initiative를 실제로 곧 돌리면 T2가 얇게 느껴질 수 있다(그 경우 "확장은 싸다"는 비대칭에 기대라).
- 검토 대상 원문 자체가 불완전했다: 붙여넣기 과정에서 코드펜스 7곳(다이어그램 등)이 유실된 상태로 검토됐다.
- 전원이 "미래 LLM 세션이 주 소비자"를 전제 — 사람 협업자가 생기는 순간 무문서 T0·대화 내 승인 같은 절약은 재검토 대상이다.
