# 페이로드 1건 손 부착 — 하네스를 자기 저장소 밖에서 처음 돌린다

> 깊이 **Deep** · 단위 T2 · 모드 delivery · 의도 write · 영역 tooling, docs · 게이트 없음
> 승인 창구는 Tech Spec 의 확인란 하나다(D-60). 이 문서는 승인 대상이 아니다 —
> 다만 「마일스톤 계획」이 비어 있으면 차단 `milestone-plan` 이 승인과 종료를 막는다.

## 왜 이 이니셔티브인가

Romeo 하네스를 실제 제품 저장소 1건에 손으로 부착하고 그 저장소의 작업 1건을 관통시켜 M5 attach 의 요구사항을 실측으로 얻는다

- **지금 없는 것:** 하네스는 자기 저장소 밖에서 한 번도 돈 적이 없다. 작업 단위 24건의 `facets` 가 전부 `tooling`·`docs` 이고, 부착 상태 파일 `.harness/romeo.project.yaml` 은 `self: true` 인 최소판이며 파일 자신이 「대상 식별자·경로를 적지 않는다」고 적는다. 부착이 실제로 무엇을 놓는 일인지가 문서에도 코드에도 없다.
- **생기면 무엇이 달라지나:** 부착이 「무엇을 어디에 놓고 무엇으로 확인하는가」로 정의되고, 그 정의가 실제 제품 저장소에서 한 번 실행돼 종료 코드로 확인된다. 그러면 M5 의 `attach` 명령은 상상한 절차가 아니라 **손으로 밟아 본 절차**를 자동화한다. 동시에 하네스가 처음으로 자기가 아닌 것을 판정한다.
- **성공을 무엇으로 아는가:** 네 가지를 전부 명령의 종료 코드·파일 존재로 판정한다(K-51) — ① 대상 저장소에서 `romeo doctor --strict --scope repository` 가 exit 0 · ② 대상 저장소에 `docs/work/<id>/` 가 서고 `status: done` 으로 닫힌다 · ③ 그 단위의 `facets` 에 `tooling`·`docs` 가 아닌 값이 하나 이상 있다 · ④ 부착 절차가 낸 구멍이 M5 요구사항 목록으로 적힌다. **④의 개수가 0 이어도 결과다** — 구멍이 없다는 관측이지 실패가 아니다.

## 범위·비범위

- **이 이니셔티브가 하는 것:** 실제 제품 저장소 **1건**(`My-Automated-Worker/instagram-dm-sender`)에 하네스를 손으로 부착하고, 그 저장소의 실제 작업 1건을 `/plan` → 승인 → 구현 → close 로 관통시키고, 그 과정이 드러낸 것을 기록한다.
- **하지 않는 것:** 부착을 **자동화하지 않는다** — 손으로 밟는 것이 이 이니셔티브의 방법이다. 두 번째 저장소에 붙이지 않는다. 대상 저장소의 BMad 를 제거하거나 Romeo 에 종속시키지 않는다. 부착 과정에서 발견한 하네스 결함을 그 김에 고치지 않는다(§12) — `docs/planning/open-questions.md` 에 열어 둔다.
- **다른 이니셔티브에 넘기는 것:** `attach`·`update --dry-run`·롤백 명령은 M5 다 — 이 이니셔티브는 그 명령이 만족해야 할 요구사항을 만들 뿐 명령을 만들지 않는다. 문서 재사용·승격·지표는 M4 다. BMad 를 제거할지 종속시킬지의 판단은 이 관통이 낸 실측을 근거로 **별도 단위**에서 한다.

## 마일스톤 계획

T2 는 한 번에 끝나지 않는다. **마일스톤마다 무엇이 서면 다음으로 넘어가는지**를 여기 적는다 —
이 절이 비어 있으면 차단 `milestone-plan` 이 승인을 거부한다. 각 마일스톤은 그 자체로 되돌릴 수 있어야 한다.

| # | 마일스톤 | 끝났다고 말할 조건 | 다음으로 넘어가는 관문 | 되돌리기 |
| --- | --- | --- | --- | --- |
| M1 | 부착 — 대상 저장소에 무엇을 놓아야 하네스가 도는지 실측하고 실제로 놓는다 | 대상 저장소에서 `romeo doctor --strict --scope repository` 가 exit 0 이고, 그때 놓인 파일 목록이 `scenarios/10-attach-payload.md` 런북과 일치한다 | 부착 없이는 나머지 셋이 시작되지 않는다. 관문은 doctor exit 0 하나다 (이 폴더의 `spec.md`) | 대상 저장소에서 부착 파일 삭제 + `CLAUDE.md` 의 managed block 제거 — 그 저장소의 git 이 원본을 보존한다. Romeo 쪽은 런북 파일 revert |
| M2 | 라우터가 남의 저장소에서 돈다 — 그 저장소의 실제 요청 1건을 `/plan` 으로 분류해 승인까지 | 대상 저장소에 `docs/work/<id>/` 가 서고 `status: active`(승인됨)가 되며, 그 단위의 `facets` 에 `tooling`·`docs` 아닌 값이 하나 이상 있다 | M1 의 부착이 라우터를 그 저장소에서 실행 가능하게 만든다. 여기서 **BMad 공존이 처음 관측된다** — 같은 `CLAUDE.md` 안의 두 라우팅 규칙이 서로를 지우는지 | 대상 저장소의 `docs/work/<id>/` 삭제 |
| M3 | 관통을 끝낸다 — 구현·검토·close | 그 단위가 `status: done` 으로 닫히고 `required_checks` 가 전부 통과한다. 하네스가 처음으로 `tooling`·`docs` 아닌 영역의 작업을 판정한다 | M2 가 승인까지 갔어야 구현이 시작된다(D-27). 관통시킬 실제 작업이 그 시점에 없으면 여기서 멈추고 그것을 정직하게 적는다 | 대상 저장소에서 그 작업의 구현 커밋 `git revert` + 작업 단위 폴더 삭제 |
| M4 | 구멍을 M5 요구사항으로 정리한다 | M1~M3 이 남긴 관측이 `docs/planning/open-questions.md` 의 Q 항목과 M5 요구사항 목록으로 적히고, 각 항목이 어느 마일스톤의 어느 실측에서 나왔는지 가리킨다 | M1~M3 이 실제로 겪은 것만 적는다 — 겪지 않은 것을 상상해 적지 않는다(K-51) | 문서 revert |

- **첫 마일스톤을 먼저 하는 이유:** 나머지 셋이 전부 부착을 전제한다. 그리고 부착은 이 이니셔티브에서 **유일하게 답이 미정인 조각**이다 — `romeo compile` 의 `--root` 가 읽는 곳과 쓰는 곳을 둘 다 정하므로(`romeo/compile.py:386`·`410`) 대상 저장소에 `core/`·`adapters/`·`.harness/bindings.yaml` 이 있어야 도는데, 그것을 복사할지 참조할지가 정해진 적이 없다. M2~M4 는 그 답이 나온 뒤에야 형태가 정해진다.
- **중간에 멈춰도 되는 지점:** 네 마일스톤 사이 전부. M1 만 해도 「부착이 무엇인가」의 답과 런북이 남고, M2 까지면 BMad 공존 관측이 남는다. 다만 **M3 없이는 「하네스가 하네스만 시험한다」가 해소되지 않는다** — 그것이 이 이니셔티브를 연 이유이므로, M1·M2 에서 멈추면 그 사실을 결과에 적는다.

## 제약·전제

- **바꿀 수 없는 것(기술·조직·일정):** 표준 라이브러리 + PyYAML 만 쓴다. 코어에 도구명·모델명을 넣지 않는다(C-C6). 승인 창구는 Tech Spec 의 확인란 하나다(D-60). **대상 저장소 쓰기는 이 저장소의 작업 공간 밖이다** — `implementer` 의 쓰기 범위는 `workspace` 이고 K-66 은 저장소 밖 반영을 승인 대상으로 둔다. 그래서 대상 저장소 작업은 **그 저장소를 작업 공간으로 삼는 별도 실행**에서 한다(사용자 확정 2026-09-04). 이 규칙을 이번에 고치지 않는다.
- **지금 참으로 가정하는 것:** 대상 저장소 변경은 `git revert`·파일 삭제로 되돌아간다(215 커밋·dirty 0·운영 상태를 건드리지 않음) · BMad 지침과 Romeo managed block 이 같은 `CLAUDE.md` 안에서 서로를 지우지 않는다(G-M3 §6.1 5단계 결론 「공존한다」 — 실제 저장소에서는 미관측) · 대상 저장소에 M3 시점에 관통시킬 실제 작업이 있다.
- **그 가정이 틀리면 무엇이 무너지나:** 공존 가정이 틀리면 M2 에서 `CLAUDE.md` 충돌이 드러난다 — 이니셔티브가 무너지는 것이 아니라 **주입 위치를 다시 정하는 일**이 M1 으로 되돌아온다. 실제 작업이 없으면 M3 를 열지 못하고 M1·M2 에서 멈춘다. 되돌리기 가정이 틀리는 경우는 대상 저장소가 dirty 하거나 부착이 추적되지 않는 파일을 덮는 경우뿐이라, M1 은 **부착 전 `git status` 가 clean 인 것을 먼저 확인**한다.

## 위험·중단 조건

- **가장 큰 위험:** 부착이 대상 저장소의 평소 작업을 망가뜨리는 것. 그 저장소의 `CLAUDE.md` 106줄은 대부분 `bmad-*` 스킬 라우팅 표이고, 거기에 Romeo 의 라우팅 규칙이 더해지면 **두 개의 「무엇을 언제 쓰는가」가 한 파일에 공존한다.** managed block 은 마커 밖을 보존하므로 파일이 깨지지는 않지만, 사람도 에이전트도 어느 쪽을 따를지 모르는 상태는 파일이 깨진 것보다 나쁠 수 있다.
- **중단 조건(무엇을 보면 멈추는가):** ① 같은 마일스톤에서 관통이 **연속 2회 실패**하면 3회차 전에 멈춘다(§10) · ② 부착이 대상 저장소의 기존 작업을 **한 번이라도 막으면** 즉시 되돌리고 주입 방식을 재검토한다 · ③ 부착에 `core/` 전체 복사가 유일한 방법으로 확인되면 그것을 **결정으로 적고 M5 요구사항에 넘긴다** — 이 이니셔티브에서 `compile` 을 고치지 않는다(§12).
- **되돌리기:** 대상 저장소는 부착 파일 삭제 + `CLAUDE.md` managed block 제거로 돌아간다 — 그 저장소의 git 이 원본을 보존하고, 부착 전 `git status` clean 을 확인하므로 무엇이 부착분인지 `git status` 만으로 갈린다. Romeo-Harness 쪽은 `git revert <구현 커밋>`. 이 이니셔티브는 운영 상태·외부 상태·비용을 건드리지 않는다.
