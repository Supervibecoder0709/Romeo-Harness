### AC-1

- 반례: 매니페스트를 읽지 못한 오류를 일반적인 ‘스킬 형식 오류’로 표시하고 종료 코드 1을 내는 구현. AC는 충족하지만, 기대 결과의 ‘부착 매니페스트가 없다’는 진단은 잘못된 원인으로 대체된다.
- 검토 시점: 누락 상태와 명령 결과는 확인 가능하다. 다만 종료 코드만으로는 의도한 부착 검사 때문에 실패했는지 알 수 없다.
- 표현: ‘부착 매니페스트’의 파일 경로가 없다. 매니페스트 없는 루트 전체에 대한 전칭으로 읽는다면 여집합화는 가능하지만, 무엇의 부재를 기준으로 삼는지 먼저 특정되어야 한다.

### AC-2

- 반례: 하네스 자체의 소스와 개발 설정까지 정상 판정의 필수 조건으로 삼는 구현. 자기 저장소는 통과하지만, 시나리오 10대로 부착한 외부 저장소는 개발 설정이 없다는 이유로 실패한다.
- 검토 시점: 자기 저장소의 통과는 확인 가능하다. 그 결과로 외부 저장소의 정상 부착까지 확인할 수는 없다.
- 표현: 명시적 전칭이나 두 경우의 혼합은 없다. 다만 검사 대상이 자기 저장소 한 곳에 한정되어, 기대 결과에 있는 외부 부착 성공 사례가 빠져 있다.

### AC-3

- 반례: 현재 매니페스트의 필수 경로 목록을 검사 코드에 그대로 복사한 구현. 현재 목록의 항목을 하나씩 지우면 모두 해당 경로와 실패가 나오지만, 매니페스트를 바꿔도 검사 내용은 바뀌지 않는다. 선언을 **읽어** 판정한다는 의도를 충족하지 않는다.
- 검토 시점: 누락 상태에서의 동작은 확인 가능하다. 다만 최종 실패 기록만으로는 삭제 전 정상 부착 상태였는지, 다른 결함 때문에 실패했는지 구별되지 않는다.
- 표현: ‘어느 하나’가 선택한 한 항목인지, 모든 요구 항목을 각각 뜻하는지 모호하다. 전칭 의도라면 여집합화할 수 있다. 또한 ‘위 명령’은 `--root`가 있는 AC-1과 없는 AC-2 중 무엇인지 불분명하다.

### AC-4

- 반례: `compile`이 `outputs`에 하네스가 생성한 파일과 대상 저장소의 기존 스킬 8개를 함께 기록한다. 검사는 목록 안의 문제만 세므로 AC를 충족하지만, 기존 스킬 문제가 계속 부착 실패로 처리된다.
- 검토 시점: 검사 범위와 종료 코드의 관계는 확인 가능하다. 다만 이미 다른 이유로 실패하는 루트에서는 외부 스킬 문제를 추가해도 종료 코드가 같으므로, 그 기록만으로 외부 문제를 제외했다고 확인할 수 없다.
- 표현: ‘밖’은 이미 여집합을 가리키지만 ‘몇 건이든’은 전칭이다. 기준인 `outputs`가 실제 생성 범위와 일치한다는 조건이 없고, ‘경로 아래’가 파일 자체와 하위 디렉터리를 어떻게 포함하는지도 불분명하다.

### AC-5

- 반례: 변경된 템플릿 대신 이전 리비전의 산출물 캐시를 재사용하면서, `harness_revision`만 현재 HEAD로 기록하는 구현. 값 비교는 맞지만 실제 부착 내용과 리비전 표기가 어긋난다.
- 검토 시점: 실행 당시 HEAD와 생성 파일을 연결한 기록이 있으면 확인 가능하다. 검토 시점의 HEAD만 비교하면, 실행 이후 커밋이 추가된 경우 당시의 일치를 확인할 수 없다.
- 표현: 대상 파일에 기록하라는 요구가 위험 설명의 **‘대상 저장소에 아무것도 쓰지 않는다’**와 충돌한다. `compile`의 기록이 그 선언에서 제외되는지 이 절에는 없다.

### AC-6

- 반례: 빈 값과 존재하지 않는 커밋은 거부하지만, 실제 산출물과 관계없는 과거 커밋을 기록하면 통과시키는 구현. AC는 충족해도 리비전 표기의 진실성은 확인하지 못한다.
- 검토 시점: 두 입력 경우의 실패는 확인 가능하다. 다만 커밋 존재 여부는 어느 하네스 저장소를 조회하는지 고정되어야 같은 결과를 확인할 수 있다.
- 표현: ‘비어 있음’과 ‘존재하지 않는 커밋’이라는 두 경우가 한 문장에 섞여 있다. ‘비어 있음’에 키 자체의 누락도 포함되는지 불분명하다. 커밋 부재는 여집합 표현이지만, 기준 저장소의 범위가 명시되지 않았다.

## 요약

- **AC-1:** 종료 코드만 요구해 잘못된 실패 진단도 허용한다.
- **AC-2:** 자기 저장소 통과만으로 외부 부착 성공을 대신한다.
- **AC-3:** 매니페스트를 읽지 않는 구현도 충족하며, 대상 항목과 명령이 모호하다.
- **AC-4:** `outputs`에 기존 스킬이 섞여도 의도한 제외 범위를 보장하지 못한다.
- **AC-5:** 실제 산출물과 리비전의 연결이 없고, 대상 쓰기에 관한 설명이 충돌한다.
- **AC-6:** 커밋의 존재만 확인해 실제 부착 내용과 무관한 리비전도 허용한다.


## 반영

반박은 판정이 아니라 입력이다. 6건 전부 문장을 고쳤고, AC 는 6개에서 8개가 됐다.

- **AC-1** — 종료 코드만으로는 매니페스트 때문에 실패했는지 알 수 없다는 지적을 받아 **finding id
  `ATTACH_MANIFEST_MISSING` 을 출력이 담을 것**을 더했다. 매니페스트의 경로도 `core/policy/attach.yaml` 로 특정했다.
- **AC-2** — 자기 저장소 통과가 외부 부착 성공을 대신한다는 지적을 받아 **임시 부착 사본에서의 통과**를
  같은 AC 에 더했다. 두 루트가 각각 통과해야 한다.
- **AC-3** — 요구 목록을 코드에 복사한 구현도 충족한다는 지적이 이 단위의 의도를 정확히 겨눴다
  (같은 결함 모양이 Q-102 에서도 났다). 지운 경로 **문자열을 출력이 담을 것**으로 좁히고,
  **AC-4 를 새로 만들어** 「매니페스트에 새 경로를 더하면 실패한다」를 판별로 세웠다 — 복사한 구현은 여기서 실패한다.
  「위 명령」이 어느 것인지 모호하다는 지적은 수용 기준 머리에 **판정 명령**을 한 번 정의해 해소했다.
- **AC-5**(구 AC-4) — 「몇 건이든」 전칭을 지우고, **밖에서 더하면 0 유지 · 안에서 깨뜨리면 0 아님** 두 방향을
  한 AC 에 명시했다. 이미 다른 이유로 실패하는 루트에서는 구별되지 않는다는 지적을 그 두 방향이 막는다.
- **AC-6**(구 AC-5) — 검토 시점의 HEAD 와 비교하면 실행 이후 커밋이 추가된 경우 확인할 수 없다는 지적을 받아,
  **한 번의 검사 실행이 두 값을 함께 읽어 비교**하는 것으로 바꿨다. 그리고 「대상 저장소에 아무것도 쓰지 않는다」와의
  **실제 모순**을 지적받아 위험·영향 범위 절을 고쳤다 — 이 단위가 쓰는 것은 **임시 부착 사본**뿐이고
  실제 프로젝트 저장소는 Charter M4 에서만 쓴다.
- **AC-7·AC-8**(구 AC-6) — 「비어 있음」과 「실재하지 않는 커밋」 두 경우가 한 문장에 섞여 있다는 지적을 받아
  **둘로 나눴다**. 「비어 있음」에 키 자체의 누락이 포함되는지 불분명하다는 지적은 AC-7 에 **키 부재와 빈 문자열**을
  둘 다 적어 해소했다. 기준 저장소의 범위는 AC-8 에 「판정 명령을 실행한 하네스 저장소」로 명시했다.

**반영하지 않은 것** — 없다. AC-3·AC-6 의 「실제 산출물과 리비전 표기의 진실성」(캐시를 재사용하면서 리비전만
현재 HEAD 로 적는 구현)은 지적이 옳지만, 그것을 판별하려면 산출물 해시와 리비전을 묶어야 하고 그것은
**Charter M3 의 `update --dry-run`(드리프트)** 이 소유한다. 여기서 고치지 않고 넘긴다(§12) — M1 은
리비전이 **있고 실재하는가**까지를, M3 이 그것이 **산출물과 맞는가**를 본다.
