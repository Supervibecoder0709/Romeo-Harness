### AC-1

- **반례:** 유효한 `level`·`source`를 갖추고, `cue`는 “요청 문장이 길다”, `why`는 “긴 요청에는 미정 사항이 많다”로 채운 예시. 네 필드의 형식은 충족하지만, 이번 문제인 **판단·조사 요구를 놓친 오분류**를 설명하지 않는다.
- **검토 시점:** 항목 수·필드·값의 형식은 확인 가능하다. 다만 이 조건만으로 예시 내용이 교정하려는 오분류와 관련 있는지는 확인되지 않는다.
- **표현:** “각 항목”의 집합은 해당 `examples` 목록으로 식별 가능하다. 여집합 관점에서는 필수 필드나 허용값 조건을 어긴 항목이 대상이다. 형식의 충족과 내용의 타당성이 구분되지 않은 점이 문제다.

### AC-2

- **반례:** fixture와 교정값은 모두 일치하지만, 검사가 `source` 목록을 문자열로 잘못 취급하여 정상 정책표에서도 실패한다. 잘못된 `level`로 바꿔도 실패하므로 요구된 실패 결과는 얻지만, **정상과 오류를 구별하는 검사**는 아니다.
- **검토 시점:** 파일 존재와 교정값 일치는 확인 가능하고, 값 변경에 따른 실패도 검토 시점에 재현 가능한 성질이다. 그러나 “사람이 실제로 고쳐”라는 수정 주체·이력은 `human_correction`이라는 필드명과 현재 값만으로 입증되지 않는다.
- **표현:** 정상 기록과의 일치, 잘못된 값에 대한 실패라는 두 경우가 섞여 있으며, 정상 상태에서 검사가 통과한다는 조건은 없다. 전칭 범위는 예시·참조 ID·허용 레벨로 한정할 수 있고, 여집합에서는 기록 불일치나 잘못된 값인데도 통과한 경우를 찾을 수 있다.

### AC-3

- **반례:** 카드는 정책표를 읽고 변경된 `cue`도 출력하지만, 검사에 쓰는 실제 문구는 보조 데이터 파일에 복제한다. “최종 검사 파일”에는 해당 문자열이 없어도, 정책 문구를 고칠 때 보조 파일까지 고쳐야 하는 구조가 남는다.
- **검토 시점:** 정책표를 읽는 경로, 문구 변경에 따른 출력, 참고 예시라는 접두의 의미는 모두 검토 시점에 확인 가능하다. 사후에 확인할 수 없는 작업 순서를 요구하지는 않는다.
- **표현:** **“최종 검사 파일”의 범위가 불명확하다.** 보조 파일·저장된 예상 출력·가져온 상수까지 포함하는지 알 수 없어, 문자열 부재 조건을 어디까지 확인해야 하는지 정해지지 않는다.

### AC-4

- **반례:** 없음. 유효한 제안과 정책표 예시 목록을 고정하면, 레벨이 다른 예시는 포함하고 같은 예시는 제외한다는 선택 조건은 분명하다. 예시 내용 자체가 틀린 문제는 AC-1·2의 빈틈이다.
- **검토 시점:** 제안의 값과 실제 출력 항목을 비교하면 확인 가능하다.
- **표현:** “전부”의 대상은 정책표의 예시 목록으로 식별 가능하다. 포함·제외 두 경우가 함께 있지만 서로 여집합이다. 여집합으로 점검할 대상도 **누락된 불일치 예시**와 **잘못 출력된 일치 예시**로 구분 가능하다.

### AC-5

- **반례:** 기존 줄을 보존하면서 모든 참고 예시를 개행 없는 긴 한 줄에 붙인다. 개행 기준으로는 예산 안에 들어가지만, 화면에서는 여러 줄로 자동 줄바꿈되어 확정 카드가 매우 길어진다.
- **검토 시점:** 개행 기준 줄 수는 확인 가능하다. 다만 그 결과가 사람이 실제 화면에서 보는 카드 길이까지 보장하지는 않는다.
- **표현:** “개행 기준” 자체는 명확하지만, 한 줄의 길이나 예시를 합쳐 인쇄하는 방식은 제한하지 않는다. AC-4의 전부 출력·AC-6의 기존 줄 보존과 함께 적용할 때, 예시 수와 문구 길이가 커지는 경우를 어디까지 대상으로 삼는지도 불명확하다.

### AC-6

- **반례:** 구현 과정에서 기존 안내 한 줄을 공통 카드 생성 부분에서 제거한다. 이후 예시 없는 카드와 예시 있는 카드를 비교하면 전자의 줄은 모두 후자에 남지만, **변경 전에 사람이 보던 안내는 양쪽에서 사라져 있다.**
- **검토 시점:** 같은 제안으로 만든 두 출력의 비교는 가능하다. 그러나 변경 후의 두 출력만 비교해서는 변경 전 정보의 보존을 확인할 수 없다.
- **표현:** “기존 줄”이 변경 전 카드인지, 변경 후 구현에서 예시만 끈 카드인지 모호하다. “전부”의 여집합인 누락된 줄을 찾을 수는 있지만, 비교 기준부터 확정되어야 한다. 줄의 순서와 중복 횟수까지 보존하는지도 명시되지 않았다.

### AC-7

- **반례:** 본문에 항목을 정책표 순서대로 나열한 뒤 “뒤에 있는 항목이 앞의 항목보다 우선한다”고 설명한다. 목록 비교와 삭제·교환 검사는 요구대로 동작하고 검토자도 본문을 읽지만, 안내하는 우선순위의 의미는 반대다.
- **검토 시점:** 목록 순서와 본문 의미는 모두 검토 시점에 확인 가능하다. 다만 **“검토자가 읽는다”는 절차**일 뿐, 읽은 결과 본문이 어떤 의미상 조건을 충족해야 하는지는 명시하지 않는다. 기계 검사에서 의미 판단을 제외한 것 자체가 문제는 아니다.
- **표현:** 항목 삭제와 순서 교환이라는 두 변형이 한 문장에 들어 있다. 전칭 대상은 현재 목록의 각 항목과 서로 다른 항목 쌍으로 식별할 수 있고, 여집합은 변형했는데도 검사가 통과하는 경우다. AC-2처럼 정상 상태에서의 검사 통과는 명시되지 않았다.

## 요약

- **AC-1:** 필드 형식만 충족하고도 오분류 원인과 무관한 예시를 넣을 수 있다.
- **AC-2:** 정상 상태도 실패하는 검사를 배제하지 못하며, 기록 일치와 실제 사람의 교정 이력을 혼동한다.
- **AC-3:** “최종 검사 파일”의 범위가 불명확하여 보조 파일에 문구 복제가 남을 수 있다.
- **AC-5:** 개행 수만 제한하므로 실제 화면 길이와 가독성을 보장하지 못한다.
- **AC-6:** 변경 후 출력끼리의 비교만으로 변경 전 안내의 보존을 보장하지 못한다.
- **AC-7:** 검토자가 읽는다는 절차와 본문 의미가 올바르다는 결과 조건이 구분되지 않는다.
## 반영 (2차)

지적 6건 중 5건을 반영하고 1건(AC-4)은 반례 「없음」이라 그대로 두었다.

- **AC-1(형식만 충족하고 오분류 원인과 무관한 예시)** → 한계를 AC-1 안에 적었다. `cue` 문구가 `source` fixture 의
  교정 사유를 옳게 요약하는지는 검사가 판정하지 않고 **검토자가 둘을 나란히 읽는다**. 낱말 일치로 재는 쪽은
  고르지 않았다 — 짧은 낱말 대조는 통과만 보이는 빈 검사에 가깝다.
- **AC-2·AC-7(정상 상태에서 통과한다는 조건이 없다)** → 두 AC 에 「지금 정책표(와 본문)에서 이 검사는 통과한다」를
  명시했다. 지적대로 그 조건이 없으면 **정상 상태에서도 실패하는 검사**가 요구를 충족해 버린다.
- **AC-2(「사람이 실제로 고쳐」는 필드명으로 입증되지 않는다)** → 수정 주체를 주장하지 않는 문장으로 바꿨다:
  「그 fixture 가 기록한 교정 결과값과 같다」.
- **AC-3(「최종 검사 파일」의 범위)** → 범위를 적었다: 검사 파일 자체와 **그 파일이 가져오는 어떤 상수·데이터
  파일**에도 실제 `cue` 문자열이 없다. 보조 파일로 옮기는 우회를 막는다.
- **AC-5(개행 없는 긴 한 줄)** → 두 제약을 더했다: 한 예시당 한 줄, 그리고 각 줄의 길이가 카드가 다른 줄에 이미
  쓰는 접기 폭을 넘지 않는다.
- **AC-6(변경 후 두 출력 비교로는 변경 전 보존을 확인할 수 없다)** → **기준을 변경 전 실제 출력으로 옮겼다.**
  승인 전에 `inputs/card-baseline.proposal.yaml` 과 그것으로 만든 `inputs/card-before-20260910.txt`(HEAD `488e787`)를
  등록했고, 검사는 그 파일의 줄이 구현 후 카드에 전부 남는지 본다. 기준선 제안의 `uncertainty` 를 `low` 로 둔 것은
  의도다 — 예시의 `level` 과 달라야 예시 줄이 실제로 인쇄되고, 그때 비로소 밀어냄을 볼 수 있다. 환경 의존 줄의
  제외 규칙도 AC 에 적었다.
- **AC-4** → 반례 「없음」. 고치지 않았다.
