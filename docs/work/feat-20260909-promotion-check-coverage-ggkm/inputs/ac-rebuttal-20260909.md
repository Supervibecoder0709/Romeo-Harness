### AC-1
- 반례: 두 모듈은 `READ_ROOTS`를 선언하고 모듈 내부 함수도 이를 사용하지만, 실제 문서 읽기는 `docs/current`를 하드코딩한 외부 helper에 위임한다. 두 모듈에는 `/ "docs"`가 없으므로 판별 규칙을 통과하지만 실제 읽기 루트는 등록부에 잡히지 않는다.
- 검토 시점: `/ "docs"` 0건은 검토 시점에 확인 가능하다. 그러나 “자기가 읽는 모든 루트”에는 간접 호출·외부 helper가 포함되는지 정의가 없어 완전성을 확인할 수단이 불명확하다.
- 표현: “자기가 읽는 저장소 하위 루트”와 “파일을 찾는 함수”는 열거되지 않은 전칭 집합이다. 여집합은 “실제 읽기 경로 중 `READ_ROOTS`에서 유도되지 않은 경로가 하나라도 있음”으로 쓸 수 있지만, 실제 읽기와 유도의 범위가 먼저 정의돼야 한다.

### AC-2
- 반례: 두 이벤트의 `paths`에 `docs/**`가 있지만 그 뒤에 `!docs/current/**`가 있다. 정의된 문자열 판별은 `docs/**`를 덮는 패턴으로 찾지만, 실제 워크플로에서는 뒤의 제외 패턴 때문에 `docs/current` 변경이 트리거되지 않는다.
- 검토 시점: 현재 `READ_ROOTS`, 워크플로, 검사 코드를 대상으로 확인할 수 있는 명제다. 과거 순서는 필요하지 않는다.
- 표현: “합집합의 각 루트 × 양쪽 이벤트”라는 전칭은 명확하고, 여집합도 “루트·이벤트 조합 중 덮는 패턴이 없는 것이 하나라도 있음”으로 쓸 수 있다. 다만 판별 규칙이 부정 패턴, 패턴 순서, 경로 정규화를 다루지 않는다.

### AC-3
- 반례: 판정 코드가 `push.paths`만 검사하고 `pull_request.paths`는 무시해도, 두 이벤트에서 문서 패턴을 한꺼번에 제거한 사본은 `push` 때문에 미덮임 1건 이상을 내고 현재 사본은 0건을 낼 수 있다.
- 검토 시점: 두 입력을 독립된 현재 상태의 사본으로 만들면 검토 시점에 확인 가능하다. git 이력이나 실제 수정 순서를 관측할 필요는 없다.
- 표현: 한 문장에 양성 사본과 음성 사본이 섞여 있다. 음성 결과를 “1건 이상”으로만 정해 어느 루트·이벤트가 미덮임이어야 하는지 잃는다. 그래서 AC-2의 두 이벤트 축을 판별했다는 근거가 되지 않는다.

### AC-4
- 반례: 두 배열에 요구된 네 문자열을 모두 넣은 뒤 `!docs/current/**`와 `!docs/work/**`를 뒤에 추가한다. 문자열 포함 조건은 충족하지만 해당 문서 변경은 실제 트리거에서 제외될 수 있다.
- 검토 시점: 워크플로의 현재 YAML 구조와 순서를 읽어 확인할 수 있다.
- 표현: 네 개의 명시적 포함 조건이라 여집합은 “네 항목 중 하나 이상이 없음”으로 쓸 수 있다. 다만 “담는다”는 유효한 최종 매칭이 아니라 단순 포함으로도 충족되어, 부정 패턴과 순서 효과를 배제하지 못한다.

### AC-5
- 반례: 시작할 때 `docs/current/`의 모든 `.md`를 스캔해 각각을 자동으로 매핑의 키로 넣고, 문서 자체에서 기대값을 만드는 일반 함수를 연결한다. 모든 파일이 자동 등록되므로 “키가 아닌 파일”은 절대 생기지 않고, 자기 자신과의 대조도 항상 통과한다.
- 검토 시점: 매핑 생성 방식과 CLI 동작은 검토 시점에 확인 가능하다. 다만 “그 문서와 대조할 파생 함수”가 실제로 호출되는지, 무엇을 정본으로 파생해야 하는지는 이 AC만으로 확인 기준이 없다.
- 표현: 모든 `.md`에 대한 전칭이며 여집합은 이미 “매핑 키가 아닌 파일”로 표현돼 있다. 그러나 매핑이 디렉터리 스캔과 독립된 폐쇄형 등록부인지 규정하지 않아 조건이 공허하게 참이 될 수 있다. 등록부 구조와 미등록 동작도 한 문장에 섞여 있다.

### AC-6
- 반례: 검사 코드가 fixture에서 선택한 `unregistered.md`라는 이름만 특별 처리한다. 그 파일을 추가·삭제한 짝은 요구된 종료 코드와 출력을 내지만, 실제 예정 문서인 `decisions.md` 같은 다른 이름은 잡지 못한다.
- 검토 시점: 두 독립된 임시 루트 상태로 만들면 검토 시점에 확인할 수 있다. “두었다가 지운다”를 실제 과거 순서로만 해석하면 최종 상태만으로는 확인할 수 없으므로, 기록된 실행 증거가 필요하다.
- 표현: “매핑에 없는 `.md` 하나”는 단일 예시만 요구하는 존재 표현이다. 파일명·중첩 위치가 달라지는 전체 여집합을 대표하지 않아 구현의 예시 특수화를 막지 못한다.

### AC-7
- 반례: 새 `UNCHECKED_PROMOTION` 검사의 호출을 빠뜨리거나 항상 거짓인 조건 뒤에 둔다. 기존 검사만 통과해 명령은 종료 코드 0을 내지만, 새 검사의 거짓 양성이 없다는 의도는 확인되지 않는다.
- 검토 시점: 종료 코드 0은 현재 체크아웃에서 확인 가능한 명제다. 새 검사가 실제 실행됐는지는 종료 코드만으로 확인할 수 없다.
- 표현: 관측 가능한 “종료 코드 0”과 인과 해석인 “새 검사가 거짓 양성으로 잡지 않는다”가 섞여 있다. 후자는 호출 여부나 해당 검사 결과가 별도로 드러나지 않으면 전자로부터 도출되지 않는다.

### AC-8
- 반례: 목록에 `UNCHECKED_PROMOTION`을 두 번 넣거나 항목만 추가하고 목록에 적힌 총 개수는 이전 값으로 남긴다. “목록에 있다”는 충족하지만 이름을 세는 문서의 수치는 틀린다.
- 검토 시점: 문서의 현재 목록·중복·표시된 총수를 정적으로 확인할 수 있다.
- 표현: 정확한 토큰의 존재만 요구하며, “세는 목록”의 구조·유일성·총수와의 일치는 정하지 않는다. 여집합을 단순히 “토큰이 없음”으로 쓰면 목록의 정확성까지는 포착하지 못한다.

### AC-9
- 반례: 「누가 이 문서를 보는가」 절에 검증기가 보지 않는다는 내용과 이유만 쓰고, 실제로 누가 보는지는 한 명도 적지 않는다. 요구된 부정 설명과 검사 대상 0건은 충족하지만 절 제목이 약속한 독자·소비자는 설명되지 않는다.
- 검토 시점: 현재 문서의 frontmatter, 라우팅 분류, 검사 대상 목록은 검토 시점에 확인 가능하다. 그러나 검사 대상 0건은 “분류가 없어서 제외된다”는 원인까지 증명하지 않는다. 별도의 하드코딩 제외가 원인이어도 0건은 같다.
- 표현: “승격 문서”가 현재 등록된 문서만 뜻하는지 미래 문서까지 포함하는지 경계가 없는 전칭이다. 현재 집합으로 한정하면 여집합은 “frontmatter가 있거나 검사 대상에 포함된 승격 문서가 하나라도 있음”으로 쓸 수 있다. 독자, frontmatter, 검증 대상, 배제 이유, 대상 수까지 여러 명제가 한 AC에 섞여 있다.

## 요약

- AC-1 — 간접 읽기와 외부 helper를 포함한 실제 읽기 루트의 범위가 정의되지 않았다.
- AC-2 — 부정 패턴과 선언 순서를 무시해 실제 CI 트리거와 다른 결론을 낼 수 있다.
- AC-3 — 양쪽 패턴을 동시에 제거해 한 이벤트만 검사하는 결함을 드러내지 못한다.
- AC-4 — 문자열 존재만 요구해 뒤따르는 제외 패턴을 막지 못한다.
- AC-5 — 파일 스캔 기반 자동 등록과 자기 대조로 미등록 조건을 공허하게 만들 수 있다.
- AC-6 — 한 파일 예시에 특수화된 구현도 짝 검사를 통과할 수 있다.
- AC-7 — 종료 코드 0만으로 새 검사의 실행 여부와 거짓 양성 부재를 구분하지 못한다.
- AC-8 — 항목 존재만으로 중복이나 총개수 불일치를 막지 못한다.
- AC-9 — 실제 독자를 요구하지 않으며, 대상 0건이 배제 이유의 진실성을 증명하지 않는다.
## 반영 (2026-09-09 · 1차)

아홉 지적을 전부 읽고 AC 를 다시 썼다. 반영한 것과 반영하지 않은 것을 나눈다.

**반영 — 통과 가능한 구멍이었다.**

- AC-1: 「외부 helper 에 위임하면 `/ "docs"` 0건이면서 실제 읽기 루트는 등록부 밖」 → 판별 규칙을 둘로 늘렸다.
  ① 리터럴·경로 조립·경로 결정 위임 호출이 0건. ② **루트 상수를 바꿔치면 두 함수가 새 루트를 본다** —
  선언과 사용이 이어져 있다는 것을 정적 검사가 아니라 동작으로 보인다.
- AC-2·AC-4: 「`docs/**` 뒤에 `!docs/current/**` 를 붙이면 문자열 조건은 충족하고 실제 트리거는 막힌다」 →
  이 워크플로의 두 목록에 `!` 로 시작하는 항목을 쓰지 않기로 정하고, 그것 자체를 검사 실패 조건으로 넣었다.
  순서·정규화까지 다루는 일반 매처를 만드는 대신 **부정 패턴을 쓰지 않는다는 규약**으로 닫는다.
- AC-3: 「양쪽에서 한꺼번에 빼면 `push` 만 검사하는 구현도 통과한다」 → 짝을 이벤트마다 따로 만들었다.
  `push` 에서만 뺀 사본은 `push` 쌍만, `pull_request` 에서만 뺀 사본은 `pull_request` 쌍만 내야 한다.
  보고 단위도 루트 목록이 아니라 `(루트, 이벤트)` 쌍으로 바꿨다.
- AC-5: 「디렉터리를 훑어 자동 등록하면 미등록이 영영 생기지 않아 조건이 공허하게 참이 된다」 →
  매핑은 소스에 리터럴로 적힌 키만 갖는다고 규정하고, 파일을 더하거나 지워도 키 집합이 그대로인 것을 판별 규칙에 넣었다.
- AC-6: 「fixture 이름 하나만 특별 처리해도 짝을 통과한다」 → 서로 다른 두 이름으로 짝을 만든다.
  그중 하나는 실제로 예정된 `decisions.md` 다.
- AC-7: 「새 검사 호출을 빠뜨려도 종료 코드는 0 이다」 → 0 의 의미를 AC-6 에 묶었다.
  같은 진입점(`bin/romeo integrity`)이 미등록 문서가 있는 루트에서 1 을 내므로, 이 저장소의 0 은 건너뛴 0 이 아니다.
- AC-8: 「두 번 넣어도 있다는 조건은 충족한다」 → 「정확히 한 번」과 목록이 세는 이름의 개수를 넣었다.
- AC-9: 「절 제목이 약속한 독자를 적지 않아도 충족된다」 · 「검사 대상 0건이 배제 **이유**를 증명하지 않는다」 →
  절 제목을 「이 문서를 검사하는 것과 하지 않는 것」 으로 바꿔 독자 약속을 없애고, 대신 무엇이 이 문서를 보는지를 적을 것을 요구에 넣었다.
  인과 주장(0건의 원인이 분류 부재라는 것)은 AC 에서 빼고 문서 본문의 설명으로만 둔다 —
  검토 시점에 참·거짓을 가릴 수 없는 명제를 AC 에 두지 않는다.
- AC-9 의 「여러 명제가 섞여 있다」 → AC-9(문서에 적힌다)와 AC-10(그 문장이 참이다)으로 쪼갰다.

**반영하지 않은 것.**

- AC-8 의 「목록의 이름 집합이 코드가 실제 인쇄하는 이름과 같은지」 — 옳은 지적이지만 이 단위의 범위 밖이다(§12).
  그것을 하려면 integrity 자신이 인쇄하는 이름을 코드에서 뽑는 파생기가 필요하고, 그것은 지금 있는 `derive()` 만한 크기다.
  `docs/planning/open-questions.md` 에 연다.
- `romeo validate` 의 `AC_UNIVERSAL` 이 AC-2 의 「하나라도」를 전칭으로 경고한다. 고치지 않는다 —
  그 낱말은 전칭이 아니라 **여집합 표현**이고, AGENTS.core §11 이 AC 를 닫는 방법으로 권하는 형태다.
  경고 패턴이 두 쓰임을 구분하지 못하는 것이며 종료 코드를 바꾸지 않는다(K-31).
