### AC-1

- 반례: `find_docs`와 `broken_links`만 `READ_ROOTS`를 사용하고, 다른 실행 경로는 `"do" + "cs"`처럼 문자열을 조립해 별도 경로를 읽는 구현이다. 제시된 리터럴·`/ "docs"` 검사와 두 함수의 바꿔치기 실험은 만족하지만, 읽는 경로의 단일 출처라는 의도는 깨진다.
- 검토 시점: 동적 바꿔치기 결과는 검토 시점에 확인 가능하다. 다만 “실제 출처”가 모든 파일 접근을 뜻하는지, 두 명명 함수만 뜻하는지 확인 수단이 정의되지 않았다.
- 표현: “자기가 읽는 저장소 하위 루트”, “실제 출처”, “다른 모듈에 경로 결정을 넘기는 호출”은 범위가 열려 있다. 전칭의 여집합을 “`READ_ROOTS`에서 유래하지 않은 저장소 경로 접근”으로 쓸 수 있지만, 어떤 호출을 경로 접근으로 셀지 정해야 한다.

### AC-2

- 반례: 두 이벤트의 `paths`가 모든 `READ_ROOTS`를 덮지만, 해당 워크플로의 검사 job에 `if: false`가 있거나 `integrity`·`validate` 단계가 빠진 산출물이다. 경로 대조기는 요구대로 동작해도 문서 변경 시 의도한 검사는 실행되지 않는다.
- 검토 시점: 루트와 패턴의 관계, 누락 쌍 출력은 검토 시점에 확인 가능하다. 그러나 “CI가 읽는 파일을 덮는다”는 상위 의도까지 보려면 해당 이벤트에서 실제 검사 job이 실행되는지도 별도로 확인해야 한다.
- 표현: “합집합의 각 루트 × 양쪽 이벤트”는 여집합을 누락된 `(루트, 이벤트)` 쌍으로 명확히 바꿀 수 있다. 반면 “그 쌍의 형태”는 문자열, 튜플, 한 줄 출력 중 무엇인지 불명확하다.

### AC-3

- 반례: 세 사본의 내용과 예상 결과를 하드코딩한 전용 함수가 `push`, `pull_request`, 0쌍을 반환하고, AC-2의 실제 대조 로직은 호출하지 않는 테스트다. 요구된 세 관측은 나오지만 회귀 방지 대상은 검증하지 않는다.
- 검토 시점: 세 입력이 현재 파일에서 파생됐는지와 git 이력을 참조하지 않는지는 검토 시점에 확인 가능하다. 과거의 작업 순서를 요구하지 않는 점은 문제가 없다.
- 표현: “AC-2의 판정”이 동일한 검사 함수 호출을 뜻하는지 단순히 같은 결과 형식을 뜻하는지 열려 있다. 세 경우가 한 AC에 섞여 있지만 서로 짝을 이루는 판별 사례라 분리 자체가 필수인 것은 아니다.

### AC-4

- 반례: 두 `paths` 목록에 요구 패턴이 정확히 들어 있지만 `branches`가 실제로 사용하지 않는 브랜치만 허용하는 워크플로다. 문서 변경은 여전히 실제 CI를 시작하지 못한다.
- 검토 시점: 목록 내용과 제외 패턴 부재는 정적인 현재 상태로 확인 가능하다. 다만 실제 대상 브랜치와 이벤트 활성 여부는 이 AC의 확인 범위에 없다.
- 표현: “두 목록 어느 쪽에도”라는 전칭은 “`!`로 시작하는 항목이 하나라도 존재한다”라는 여집합으로 명확히 바꿀 수 있다. 두 이벤트와 포함·제외 조건이 한 문장에 묶였지만 집합은 유한하고 식별 가능하다.

### AC-5

- 반례: 리터럴 키와 파생 함수가 든 매핑을 만들고 미등록 `.md`도 정확히 지목하지만, 실제 `integrity` 실행에서는 매핑의 파생 함수를 전혀 호출하지 않는 구현이다. 등록 누락은 막아도 등록된 문서의 내용 대조는 사라진다.
- 검토 시점: 키의 작성 방식, 파일 변화에 대한 키 집합의 불변성, 미등록 파일 출력은 검토 시점에 확인 가능하다. 각 매핑 값이 실제 대조 경로에서 호출되고 결과가 비교되는지는 별도 관측이 필요하다.
- 표현: “그 문서와 대조할 파생 함수”는 함수의 존재만 뜻하는지 실제 호출·비교까지 뜻하는지 불명확하다. “모든 `.md` 중 매핑 키가 아닌 파일”의 여집합은 등록된 키 집합과 정확히 일치하는 `.md` 집합으로 쓸 수 있다.

### AC-6

- 반례: 검사 코드가 `decisions.md`와 테스트에서 선택한 다른 이름 하나만 특별 처리하는 구현이다. 두 이름의 추가·삭제 실험은 모두 맞지만, 세 번째 이름의 미등록 문서는 통과할 수 있다.
- 검토 시점: 두 이름에 대한 짝 실험은 검토 시점에 확인 가능하다. 그러나 유한한 두 사례만으로 “파일 이름에 기대지 않는다”라는 일반 명제를 확인할 수는 없다.
- 표현: 전칭인 “파일 이름에 기대지 않는다”의 여집합은 “이름에 따라 결과가 달라지는 미등록 `.md`가 하나라도 있다”이다. 현재 두 이름만 열거되어 있어 그 여집합 전체를 배제하지 못한다.

### AC-7

- 반례: 임시 루트가 주어질 때만 새 등록 검사를 실행하고, 기본 저장소 루트에서는 건너뛰는 진입점이다. AC-6은 같은 `bin/romeo integrity`로 1을 내고 저장소에서는 0을 내지만, 저장소의 0은 여전히 새 검사를 건너뛴 결과다.
- 검토 시점: 현재 저장소의 종료 코드 0은 신선한 실행 증거가 있으면 확인 가능하다. “건너뛰지 않았다”는 것은 다른 루트의 실패만으로는 확인되지 않으며, 현재 저장소 실행에서 검사 호출이 관측되어야 하는 인과 명제다.
- 표현: “같은 진입점”은 같은 옵션·루트·환경·분기까지 뜻하지 않는다. 0과 1이라는 두 경우와 비건너뜀 결론이 한 문장에 묶여 있고, 앞의 두 값만으로 뒤 결론이 따라오지 않는다.

### AC-8

- 반례: 범위 절의 목록에 `UNCHECKED_PROMOTION`을 한 번 포함해 이름 네 개를 세지만, 실제 구현은 목록에 없는 다섯 번째 이름도 인쇄하는 산출물이다. 문서의 명시된 횟수와 개수는 맞아도 전체 진단 목록이라는 의도는 배신한다.
- 검토 시점: 문서 안의 출현 횟수와 목록 항목 수는 검토 시점에 확인 가능하다. 구현이 실제로 인쇄할 수 있는 이름의 전체 집합과 목록이 같은지는 별도 대조가 필요하다.
- 표현: “integrity 자신이 인쇄하는 이름을 세는 목록”이 완전한 목록인지 일부 목록인지 불명확하다. 완전성을 원한다면 여집합은 “구현에는 있지만 목록에 없거나, 목록에는 있지만 구현이 인쇄하지 않는 이름”이다.

### AC-9

- 반례: 요구된 네 내용을 모두 적었지만, 실제로는 `bin/romeo integrity`가 등록 검사만 수행하고 대조·링크 검사는 호출하지 않는 문서다. 문장 존재 요건은 충족하지만 설명은 사실이 아니다.
- 검토 시점: 절과 문장의 존재는 확인 가능하다. frontmatter 부재, validate 비대상, 이유, integrity의 실제 검사 범위가 사실인지도 현재 코드에서 확인할 수 있지만, AC는 이를 사실 대조로 요구하지 않고 “적는다”로만 표현한다.
- 표현: “승격 문서”와 “이 문서”가 섞여 있어 모든 승격 문서에 관한 설명인지 `enforcement.md` 하나에 관한 설명인지 모호하다. 네 가지 서로 다른 사실 주장도 한 AC에 묶여 있다.

### AC-10

- 반례: 검사 대상 목록이 절대경로 `/repo/docs/current/enforcement.md`를 포함한다. 문자열이 `docs/current/`로 시작하는 항목은 0건이므로 글자 그대로는 충족하지만, 승격 문서는 실제 검사 대상이다.
- 검토 시점: 특정 계산 함수, 실행 인자, 경로 정규화 방법이 정해지면 검토 시점에 확인 가능하다. 현재는 “검사 대상 목록을 계산”하는 진입점과 경로 표현이 지정되지 않아 검토자가 같은 결과를 재현한다는 보장이 없다.
- 표현: “`docs/current/`로 시작”은 저장소 상대경로라는 전제가 빠진 표현이다. 여집합은 “정규화한 저장소 상대경로가 `docs/current/` 아래인 대상이 하나라도 존재한다”로 볼 수 있으나, 현재 문장에는 정규화 기준이 없다.

## 요약

- AC-1 — `READ_ROOTS` 단일 출처의 적용 범위와 경로 접근의 여집합이 정의되지 않았다.
- AC-2 — 경로 필터 대조만으로 실제 검사 job의 실행까지 보장하지 않는다.
- AC-3 — 세 사례가 AC-2의 동일한 검사 로직을 거친다는 연결이 없다.
- AC-4 — 요구 패턴이 있어도 브랜치 등 다른 조건으로 워크플로가 실행되지 않을 수 있다.
- AC-5 — 등록된 파생 함수가 실제 대조에 호출된다는 요구가 없다.
- AC-6 — 두 파일명만으로 이름 비의존이라는 전칭을 증명하지 못한다.
- AC-7 — 다른 루트의 실패로 현재 저장소 실행의 비건너뜀을 증명할 수 없다.
- AC-8 — 문서 목록과 실제 출력 이름 전체 집합의 완전 일치를 요구하지 않는다.
- AC-9 — 요구 문장의 존재만 확인하고 설명의 사실성은 요구하지 않는다.
- AC-10 — 계산 진입점과 저장소 상대경로 정규화가 정해지지 않았다.
## 반영 (2026-09-09 · 2차)

열 지적을 전부 읽었다. 1차 때 놓쳤던 것은 **AC 를 글자대로 충족하면서 실행 경로를 비우는** 위조였다.

**반영 — 통과 가능한 위조였다.**

- AC-2·AC-4: 「경로 필터는 넓혔는데 job 에 `if: false` 가 있거나 검사 스텝이 빠졌다」 ·
  「`branches` 가 실제로 쓰지 않는 브랜치만 허용한다」 → AC-4 를 네 조건으로 늘렸다.
  경로 두 항목 · 제외 패턴 부재 · `branches`/`branches-ignore` 부재 · 두 검사 스텝 실재와 `if:` 부재.
  경로만 넓히고 실행 경로가 막혀 있으면 이 단위는 아무것도 바꾸지 않은 것이다.
  ③④ 는 지금도 참임을 승인 전에 실측했다(회귀 조건) — ①② 만 판별 조건이다.
- AC-3: 「세 사본의 기대값을 하드코딩한 전용 함수는 AC-2 로직을 부르지 않고도 요구된 세 관측을 낸다」 →
  세 입력이 **같은 판정 함수 하나**를 거치고 차이는 인자뿐이라는 것을 AC 에 넣었다.
- AC-2 의 「그 쌍의 형태가 불명확」 → 보고 형태를 `(루트, 이벤트)` 튜플의 목록으로 못박았다.
- AC-5: 「매핑은 만들었지만 파생 함수를 실제 대조에서 부르지 않는 구현」 → **가장 실질적인 지적이다.**
  등록부로 바꾸면서 대조 자체가 조용히 사라질 수 있다. 판별 규칙을 하나 더했다 —
  매핑의 값을 반드시 어긋나게 하는 함수로 바꿔치면 `PROMOTION_DRIFT` 와 종료 코드 1 이 나온다.
- AC-6: 「두 이름만 특별 처리한 구현도 통과한다」 → 두 이름 중 하나를 **실행할 때마다 달라지는 이름**으로 바꿨다.
  AC 문장도 전칭(「이름에 기대지 않는다」)에서 판별 규칙(「매핑 키에 드는가로만 갈린다」)으로 옮겼다.
- AC-7: 「임시 루트일 때만 새 검사를 도는 진입점이면 저장소의 0 은 여전히 건너뛴 0 이다」 →
  다른 루트의 실패를 근거로 삼는 것을 그만두고, **같은 실행 자신의 출력**으로 옮겼다.
  `bin/romeo integrity` 가 「등록 N건 · 미등록 M건」 을 인쇄하고, 이 저장소에서 그 줄이 1건·0건을 말한다.
- AC-9: 「요구 문장의 존재만 확인하고 설명의 사실성은 요구하지 않는다」 → 기계로 볼 수 있는 절반을 넣었다 —
  그 절이 말하는 frontmatter 부재가 참일 것(첫 줄이 `---` 가 아니다).
- AC-10: 「계산 진입점과 정규화가 정해지지 않았다」 → `romeo.validate.find_docs('.')` 를 진입점으로 못박고,
  결과를 저장소 루트 기준 상대경로 문자열로 만든 뒤 판정한다고 적었다.

**반영하지 않은 것.**

- AC-6 의 「유한한 두 사례로 전칭을 증명할 수 없다」 — 원리적으로 옳고 닫을 수 없다.
  무작위 이름으로 이름 특수화를 막는 데까지가 이 단위가 할 수 있는 것이다.
- AC-8 의 「문서 목록과 실제 출력 이름 전체 집합의 완전 일치」 — 1차와 같은 이유로 범위 밖이다(§12).
  `docs/planning/open-questions.md` 에 연다.
- AC-9 의 「설명 전체의 사실성」 — 「분류가 없어서 제외된다」는 인과 주장은 검토 시점에 참·거짓을 가릴 수 없다.
  AC 에서 빼고 문서 본문의 설명으로만 둔다.

## 승인 전 프로브 (2026-09-09)

검증 계획 9개 명령을 **구현 전 상태**에서 전부 실행했다. 분류대로 갈렸다 —
판별 `check-1`·`check-4`·`check-5`·`check-9` 는 exit 1, 회귀 `check-3`·`check-6`·`check-7`·`check-8` 은 exit 0.

**한 건이 빈 검사였다.** `check-2` 를 `python3 -m unittest tests.test_integrity -v` 로 두었더니 exit 0 —
그 모듈이 이미 있고 통과하므로 이 단위가 없어도 통과한다. 새 케이스를 기존 모듈에 더하는 계획이 원인이었다.
`tests/test_promotion_registry.py` 라는 **새 모듈**로 옮기고 다시 재니 exit 1 이다.
AC-4 의 ③④(`branches` 부재 · `if:` 부재 · 두 스텝 실재)도 함께 실측해 회귀 조건임을 확인했다.
