### AC-1

- **반례:** 함수 진입 때 봉인 여부를 한 번 확인한 뒤 명령을 실행하는 구현. 실행 중 다른 호출이 검토 봉투를 기록해 봉인해도, 먼저 시작한 호출은 마지막에 증거를 저장한다. 봉인된 상태에서 시작하는 세 검사는 모두 충족하면서도, 살아남은 워커가 봉인 뒤 증거를 바꿀 수 있다.
- **검토 시점:** 판정 호출이 앞에 놓였는지는 최종 코드에서 확인 가능하다. 다만 전후 바이트가 같다는 사실은 중간에 쓰고 복구하지 않았음을 증명하지 않는다. 표식 파일이 없다는 사실도 명령 호출 자체가 없었다는 것과는 다르다.
- **표현:** “어떤 쓰기·실행보다 먼저”는 최초 확인 이후까지 보호하는지 불명확하다. 봉인/미봉인을 여집합으로 나눌 수 있지만, **어느 시점의 상태인지** 없으면 실행 도중 봉인되는 경우가 빠진다.

### AC-2

- **반례:** 재작업용 run과 검토 관련 기록이 있는 run에는 이어쓰기를 허용하지만, 일반 명령 기록만 있는 기존 run에는 이어쓰기를 거부하는 구현. 제시된 세 장면은 충족하면서도, 같은 단위에 아직 봉인된 run이 없는 정상 작업의 증거 기록을 막을 수 있다.
- **검토 시점:** “봉인된 뒤에 호출”, “상수를 바꿔친 채 호출”은 검사 코드의 순서와 실행 결과가 남으면 검토 가능하다. 최종 run 파일만으로는 그 순서와 조건을 확인할 수 없다.
- **표현:** “여집합 셋”은 전체 여집합을 빠짐없이 나눈 분류가 아니다. 일반 명령만 있는 기존 미봉인 run 등이 명시되지 않았다. 허용 사례, 상수 교체에 따른 허용·거부, 검사 작성 규칙도 함께 묶여 있다. “정상 기록”의 관측 기준과 “검사 소스”의 파일 범위도 불명확하다.

### AC-3

- **반례:** 두 evidence 명령은 모든 조건을 충족하지만, `review record` 명령줄 처리는 입력 JSON을 대상 봉투 경로에 먼저 복사한 뒤 `record_review_envelope`을 호출하는 구현. 핵심 함수가 봉인을 감지해 거부해도, 호출 전에 바뀐 봉투는 남는다. 이 세 번째 명령줄 경로는 AC-3에 없다.
- **검토 시점:** 종료 코드·stderr·전후 파일 비교는 검토 가능하다. 그러나 `true`는 실행되어도 표식이 남지 않으므로, 이 검사로는 명령의 비실행을 구별할 수 없다.
- **표현:** “명령줄에서도 같다”가 AC-1 전체를 뜻하는지, 명시한 (a)(b)만 뜻하는지 모호하다. 기대 결과의 명령 세 종류 중 두 종류만 열거했고, 봉투 보존인 (c)와 비실행인 (d)는 빠져 있다.

### AC-4

- **반례:** 첫 단계에서 두 상태 필드를 확인하고, 미settle이면 `worker-stop`을 호출하며, 거부되면 §7로 보내는 문서. 다만 **중지 요청이 수락되면 종료 상태를 다시 확인하지 않고** 바로 `task-update`로 진행하도록 한다. 요구한 문구와 줄 순서는 모두 갖추지만, 중지 수락이 종료 완료를 보장하지 않는 경우 앞 워커가 남는다.
- **검토 시점:** 문서의 첫 단계와 분기는 최종 문서에서 확인 가능하다. 여기의 “첫 단계”는 과거 실행 순서에 대한 주장이 아니다. 다만 제시된 줄 순서 검사는 중지 수락 뒤의 진행 조건까지 확인하지 못한다.
- **표현:** 이미 settle인 경우, 중지 수락, 중지 거부가 묶여 있으며 **수락 후 분기**가 비어 있다. “어떤 명령도”는 전칭인데 대상 명령 집합이 명확하지 않다. 여집합으로 따지려면 AC-1·2와 같은 기록 경로 및 상태 범위를 가리키는지부터 정해져야 한다.

### AC-5

- **반례:** 요구된 행·세 단계·미관측 표시·§11.2 항목을 모두 갖추되, 첫 `worker-show` 결과를 근거로 나중에 같은 터미널을 닫는 절차. 조회와 닫기 사이에 사람이 터미널을 넘겨받을 수 있다면, 확인 당시에는 미인수였고 절차도 모두 지켰지만 사람의 터미널을 닫게 된다.
- **검토 시점:** 표의 행 수와 문구는 검토 가능하다. 그러나 사람의 인수 여부를 **어느 출력 필드와 값으로 확인하는지**는 제시되지 않았다. “2026-09-10에 사람이 UI에서 닫았다”는 과거 사실도 원 관측 자료가 필요하며, `operator_close` 값만으로 날짜·조작자·UI 경로까지 확정되지는 않는다. CLI 경로를 미관측으로 표시하는 것 자체는 실제 복구 성공을 요구하지 않는다.
- **표현:** “정확히 하나”는 대상 표가 정해져 있어 범위가 명확하다. 반면 §11.2의 “같은 항목”은 동일성을 판단할 기준이 없고, `terminal close`라는 문자열의 존재만으로 그 복구 경로를 가리킨다고 볼 수 없다.

### AC-6

- **반례:** **없음.** 요구한 의미의 문장이 실제로 존재하고, 그 문장 안에 올바른 봉인 라벨이 있으며, import 규칙까지 충족한다면 이 AC의 문서 변경 의도는 충족된다. 라벨만 엉뚱한 곳에 있는 문서는 검사에 통과할 수 있어도 AC 자체를 글자 그대로 충족한 반례는 아니다.
- **검토 시점:** 문장·라벨·import 방식은 최종 파일에서 확인 가능하다. 다만 “확인했으므로”는 과거 확인 행위를 근거로 컴파일을 제외한다. 검토 대상 버전에서도 원본을 가리키는 상태가 유지되는지와 과거 조사 사실이 섞여 있다.
- **표현:** 요구는 **그 문장 안의 라벨**인데 판별 규칙은 **문서 어디에든 있는 라벨**을 찾는다. 문장의 의미도 문자열 검색으로는 확인되지 않는다. 핵심 문제는 전칭보다 요구와 판별 범위의 불일치다.

## 요약

- **AC-1:** 최초 봉인 확인 이후, 실행 도중 봉인되는 경우의 보호가 빠져 있다.
- **AC-2:** 세 사례가 미봉인 run의 전체 여집합을 덮지 않고, “정상 기록”도 불명확하다.
- **AC-3:** `review record` 명령줄 경로와 봉투 보존·명령 비실행 확인이 빠져 있다.
- **AC-4:** `worker-stop` 수락 뒤 종료 확인과 다음 단계 진행 조건이 없다.
- **AC-5:** 사람의 터미널 인수 여부를 판단할 근거와 그 판단이 유효한 시점이 불명확하다.
- **AC-6:** 문장에 대한 요구를 문서 전체의 라벨 검색으로 판별하며, 컴파일 제외 근거는 과거형이다.
## 반영 (2026-09-10 · 1차)

여섯 지적을 전부 읽었다. 통과 가능한 구멍은 **확인 시점이 하나뿐인 것**(실행 도중 봉인)과 **여집합이 열거되지 않은 것**이었다. AC 를 6개에서 7개로 다시 잘랐다(정본 규칙을 AC-3 으로 분리).

**반영.**

- AC-1: 「함수 진입 때 한 번 확인한 뒤 실행하는 구현은 실행 도중 봉인돼도 마지막에 저장한다」 → **두 번 확인**으로 바꿨다 — 실행 전과, 실행이 끝나고 쓰기 직전에 **디스크에서 다시 읽어**. 판별 상태 ④(넘긴 명령 자체가 그 run 을 봉인하는 경우)를 더해 그 구현이 실패하게 했다. 「전후 바이트가 같다는 것이 중간 쓰기 없음을 증명하지 않는다」는 관측 한계로 인정한다 — 대조 가능한 것은 최종 상태뿐이고, 검사가 보는 것도 그것이다.
- AC-2: 「일반 명령만 있는 미봉인 run 을 거부하는 구현이 세 장면을 통과한다」 → 여집합을 **넷으로 열거**했다(빈 run · 일반 명령만 · 방어 검사만 · 봉인 뒤의 새 run). 「정상 기록」의 관측 기준(길이 +1 · 마지막 id · 최상위 head · 로그 파일 · 봉투 내용)을 적었다. 상수 바꿔치기와 검사 작성 규칙은 AC-3 으로 분리하고 「검사 소스」를 `tests/test_sealed_run_refusal.py` 한 파일로 못박았다.
- AC-3(옛 AC-3 → 새 AC-4): 「`review record` 명령줄 경로가 빠졌다」·「`true` 는 비실행을 구별하지 못한다」 → 명령줄 세 경로(`evidence run`·`evidence checks`·`review record`)를 전부 열거하고, 넘기는 명령을 **파일 하나를 만드는 명령**으로 바꿨으며, (a)(b)(c) 와 파일 부재까지 요구했다. CLI 의 `review record` 는 입력 JSON 을 복사하지 않고 `record_review_envelope` 에 경로를 그대로 넘기는 것(`romeo/cli.py:312`)을 확인했다 — 반례의 구현은 지금 코드가 아니지만 AC 가 그것도 막는다.
- AC-4(→ 새 AC-5): 「`worker-stop` 수락 뒤 종료 확인 없이 진행하는 문서」 → 세 갈래 (가)(나)(다) 를 열거하고 (나) 에 「**수락됐어도** 같은 `worker-show` 를 다시 돌려 (가) 가 성립할 때만」 을 넣었다. 판별 규칙에 `worker-show` 2회 이상을 더했다. 「어떤 명령도」는 세 명령(`evidence run`·`evidence checks`·`review record`)으로 유한하게 바꿨다.
- AC-5(→ 새 AC-6): 「사람의 인수 여부를 어느 필드로 보는지 없다」·「조회와 닫기 사이의 틈」 → 확인 필드를 둘로 못박았다(`.result.terminalResource.ownerDispatchId` == 그 dispatch id · `.result.observation.exactWorker` == true — 이 dispatch 가 아직 그 터미널의 소유자이고 신원이 이 워커로 증명된 상태). ①② 사이에 다른 단계를 두지 않는다는 요구를 행에 넣었다 — 틈을 없애지는 못하고 좁힌다. 「2026-09-10 사람이 UI 에서 닫았다」는 날짜·경로 주장을 빼고, 관측된 종료가 `exitCause.kind operator_close` 하나뿐이라는 것만 남겼다. §11.2 의 「같은 항목」은 `orca terminal close --terminal` 문자열을 담은 항목으로 판별 기준을 정했다.
- AC-6(→ 새 AC-7): 「문장 요구를 문서 전체 검색으로 판별한다」·「컴파일 제외 근거가 과거형」 → 판별 범위를 **7번 항목 안의 한 문장**으로 좁혔다 — 백틱 라벨·「거부」·「새 run」 셋을 한 문장에 담아야 한다. 컴파일 문장은 AC 에서 빼고 「바꾸지 않는 것」으로 옮겼다.

**반영하지 않은 것.**

- AC-1 「표식 파일이 없다는 것이 명령 호출 자체가 없었다는 것과 다르다」 — 부수 효과 없는 실행과 비실행은 관측으로 구별되지 않는다. 검사가 보는 것은 부수 효과이고, 그것이 없으면 그 명령이 산출물에 아무 일도 하지 않은 것이므로 이 단위의 목적(오염 방지)에는 충분하다.
- AC-5 「과거 사실은 원 관측 자료가 필요하다」 — `docs/work/feat-20260909-metrics-four-counters-dyz2/review-spoiled/README.md` 와 `worker-show --dispatch ctx_396c4aad204d` 가 원 자료다. AC 는 그 사실을 요구에서 뺐으므로 판정에 닿지 않는다.
