### AC-1

- 반례: 두 번 모두 디스크에서 **미봉인 상태**를 확인하지만, 두 번째 확인과 실제 쓰기 사이에 다른 호출이 검토 봉투를 기록하는 구현. 요구한 확인 위치와 네 판별 사례를 만족하면서도, 뒤늦은 바깥 쓰기가 봉인 기록을 덮어쓰거나 증거를 추가할 수 있다.
- 검토 시점: 확인 위치와 각 사례의 결과는 검토 가능하다. 다만 파일의 전후 바이트 일치만으로는 **중간 쓰기가 없었다는 사실**까지 확인할 수 없고, 네 사례에는 두 번째 확인 이후의 동시 실행이 없다.
- 표현: **“아무것도 쓰지 않는다”의 대상 집합이 불명확하다.** ④에서는 명령 실행과 안쪽 호출의 쓰기를 허용한다. 바깥 기록 함수의 쓰기와 넘긴 명령의 부작용을 구분하지 않아, 허용되는 쓰기를 제외한 여집합도 확정하기 어렵다.

### AC-2

- 반례: 새 명령의 실패 출력 대신 이전 검사의 성공 로그를 새 로그 파일에 저장하는 구현. 열거한 정상 기록 조건인 항목 수·라벨·`head_sha` 대응·파일 존재는 모두 맞지만, 증거 내용은 실제 결과와 다르다.
- 검토 시점: 열거한 후조건은 검토 가능하다. 그러나 **“지금처럼”은 변경 전 어느 상태의 어떤 동작을 보존한다는 것인지** 기준이 없다.
- 표현: 봉인 라벨이 없는 run이라는 여집합 표현은 명확하다. 다만 “정상 기록”이 열거한 후조건만 뜻하는지, 실제 결과와 로그의 일치 및 기존 기록 보존까지 포함하는지 불명확하다.

### AC-3

- 반례: 기록 라벨이 `REVIEW_RECORD_LABEL`의 **부분 문자열인지**로 봉인을 판정하고, 패치 값으로 원래 값과 겹치지 않는 문자열을 사용하는 구현. 원래 라벨은 허용하고 교체 라벨은 거부하며 상수도 사용하지만, 평상시에는 `review` 같은 별도 라벨까지 봉인으로 오인한다. AC-1·2의 의미에는 어긋나지만 AC-3의 두 판별 결과는 만족한다.
- 검토 시점: 상수 사용과 패치 결과는 검토 가능하다. 다만 **“바꿔친 채 부르면”의 호출 대상**이 봉인 판정 함수인지, 실제 기록 함수들인지 명시되지 않았다.
- 표현: 교체 값과 원래 값의 관계가 정해지지 않아, 값 선택에 따라 같은 부분 문자열 비교 오류가 드러나거나 숨는다. 리터럴 0건이라는 표기 제약과 올바른 봉인 판정은 별개의 요구다.

### AC-4

- 반례: 공통 CLI 처리부가 run 경로를 잘못 계산해 세 명령 모두 `run <id>를 찾을 수 없음`이라는 오류로 exit 1을 반환하는 구현. stderr에 run id가 있고 기존 파일과 표지 파일도 그대로지만, **봉인 방어에 도달하지 않았으며 정상 run도 사용할 수 없다.**
- 검토 시점: 종료 코드·stderr·파일 상태는 검토 가능하다. 그러나 제시된 관측값만으로는 **봉인 때문에 거부했는지** 구별할 수 없다.
- 표현: “세 경로도 같다”에 비해 실제 요구는 봉인된 입력의 실패 결과만 다룬다. 그 여집합인 미봉인 입력의 CLI 동작은 이 AC에 없고, AC-2의 관측 대상은 내부 함수다.

### AC-5

- 반례: 없음. 문서의 실제 첫 단계와 세 분기의 행동·진행 조건까지 요구하므로, 예제나 주석에 키워드만 넣은 잘못된 절차는 **AC 전체**를 충족하지 않는다.
- 검토 시점: 문서에 적힌 순서와 분기는 검토 가능하다. 다만 제시된 문자열 순서·등장 횟수 검사는 두 번째 `worker-show`가 수락 뒤 재관측에 해당하는지, 세 분기의 진행 조건이 맞는지까지 확인하지 않는다.
- 표현: “아니면”은 (가)의 여집합으로 읽을 수 있다. 다만 §7의 마지막 확인을 **(가)의 두 조건 모두**와 같다고 요구하는 반면, AC-6③은 `observation.status == exited`만 명시한다. 같은 복구 완료 조건을 서로 다른 강도로 적었다.

### AC-6

- 반례: 필수 문구와 세 단계가 모두 있지만, 마지막에 `exited`만 확인하면 복구 완료로 취급하는 행. dispatch 상태가 아직 `failed`·`completed` 중 하나가 아니어도 AC-6 자체는 만족한다. **AC-5의 settle 조건에는 미달하는 안내**다.
- 검토 시점: 행 개수와 문서상 단계 순서는 확인 가능하다. 반면 “미관측”과 “관측된 종료는 하나뿐”은 **어느 관측 기록을 어느 시점까지 조사한 주장인지** 없어 사실 여부를 확인할 범위가 정해지지 않았다. “그 직후”도 문서상 인접 순서인지 실제 실행 간격인지 구분이 필요하다.
- 표현: “정확히 하나”는 지정된 표로 범위가 정해져 있다. 그러나 관측 결과의 “하나뿐”은 대상 집합이 열거되지 않아, 다른 관측이 없다는 여집합을 확인할 수 없다. 절차 지시와 과거 관측 사실도 한 AC에 섞여 있다.

### AC-7

- 반례: 7번에 요구한 뜻과 세 낱말을 갖춘 문장을 넣고, 같은 항목의 복구 안내에는 **봉인 라벨을 지운 뒤 같은 run에 재시도하도록** 적은 스킬. 요구된 문장은 존재하고 검사도 만족하지만, 함께 실린 지시가 그 원칙을 무너뜨린다.
- 검토 시점: 문장 존재와 검사 소스는 검토 가능하다. 다만 낱말 세 개의 동시 출현은 그 문장의 의미나 주변 지시와의 일관성을 확인하지 않는다.
- 표현: **“문장 1개 이상”은 존재 조건**이어서, 같은 항목에 반대 지시나 예외가 함께 있는 경우를 제한하지 않는다. 문장 하나의 뜻과 항목 전체가 지시하는 행동의 범위가 다르다.

## 요약

- **AC-1:** 두 번째 확인 이후의 쓰기 경쟁이 남고, “아무것도 쓰지 않는다”의 범위가 불명확하다.
- **AC-2:** 정상 기록의 관측 조건이 실제 결과와 다른 로그도 허용하며, “지금처럼”의 기준이 없다.
- **AC-3:** 패치 판별이 부분 문자열 오인을 놓칠 수 있고, 호출 대상이 명시되지 않았다.
- **AC-4:** 봉인과 무관한 공통 오류도 모든 관측 조건을 만족할 수 있다.
- **AC-5:** 문자열 판별이 분기의 의미를 확인하지 못하며, 복구 완료 조건이 AC-6보다 강하다.
- **AC-6:** 종료 관측만으로 settle을 대신할 수 있고, 과거 관측 주장의 자료·시점 범위가 없다.
- **AC-7:** 필요한 문장 하나가 있어도 같은 항목의 모순된 복구 안내를 배제하지 못한다.
## 반영 (2026-09-10 · 2차)

일곱 지적을 전부 읽었다. 남은 구멍은 **비교 방식이 정해지지 않은 것**(부분 문자열)과 **거부 사유를 구별할 관측이 없는 것**(CLI)이었다.

**반영.**

- AC-1: 「아무것도 쓰지 않는다의 대상 집합」 → 그 호출이 만드는 쓰기 셋(evidence yaml · 로그 파일 · 봉투 파일)으로 못박고, 넘긴 명령의 부수 효과와 안쪽 호출의 쓰기는 집합 밖임을 적었다(④ 가 그 경우다).
- AC-2: 「이전 검사의 성공 로그를 새 로그에 저장하는 구현」·「지금처럼의 기준이 없다」 → 「지금처럼」을 뺐다. 마지막 항목의 `exit_code` 가 실제 종료 코드(0 과 1 을 각각 넘겨 본다)이고 `command_log_state` 가 `True` 인 것(로그가 있고 `log_sha256`·봉인 줄과 맞는다)을 기준에 더했다 — 로그 내용이 실제 결과와 다른 구현은 여기서 실패한다.
- AC-3: 「부분 문자열 판정이 두 판별을 통과한다」·「호출 대상 불명」 → 판정을 **동일성**으로 못박고, 바꿔치는 값을 「원래 값과 서로 부분 문자열이 아닌 값」으로, 호출 대상을 `run_command` 으로 정했다. 진부분 문자열 라벨과 포함하는 더 긴 라벨의 run 이 거부되지 않는 상태 ② 를 더했다 — 부분 문자열 비교는 ② 에서 실패한다.
- AC-4: 「공통 오류도 모든 관측 조건을 만족한다」 → stderr 에 「새 run」 낱말(AC-1 의 거부 메시지)을 요구하고, 여집합(봉인되지 않은 run 에 같은 세 명령이 exit 0 · 파일 생성 · 기록 증가)을 더했다. 공통 오류 구현은 여집합에서 실패한다.
- AC-5: 「복구 완료 조건이 AC-6 보다 강하다」 → AC-6 ③ 을 (가) 의 두 조건으로 올려 같게 했다. 「문자열 판별이 분기의 의미를 확인하지 못한다」는 아래 「반영하지 않은 것」.
- AC-6: 「종료 관측만으로 settle 을 대신한다」 → ③ 을 (가) 와 같게 했다. 「미관측의 자료·시점 범위」 → 근거를 저장소 안의 두 자리(`.harness/observations.yaml` · §11.1)에 `terminal close` 관측 기록이 없다는 것으로 정하고, 검사가 그 부재를 같이 보게 했다. 「하나뿐」을 「거부된 워커의 종료로 관측된 것 1건(`ctx_396c4aad204d`)」으로 유한하게 바꿨다. 「그 직후」는 문서상 인접(같은 행에서 ①② 사이에 다른 단계 없음)으로 정했다.
- AC-7: 「필요한 문장이 있어도 같은 항목의 모순된 안내를 배제하지 못한다」 → 여집합 규칙을 더했다 — 7번 항목 안에서 봉인 라벨을 담은 문장 중 「거부」도 「새 run」도 담지 않는 문장이 0개.

**반영하지 않은 것.**

- AC-1 「두 번째 확인과 쓰기 사이의 경쟁」 — 파일 잠금 없이는 없앨 수 없는 창이고, 이 단위가 막으려는 것은 분 단위로 벌어진 사건(봉인 뒤에 시작한 명령)이다. 밀리초 창은 한계로 적고 검사하지 않는다. 잠금은 별도 단위다.
- AC-5 「문자열 판별이 분기의 의미를 확인하지 못한다」 — 절차 문서의 의미를 기계가 판정할 수단이 없다. 판별 규칙은 요구가 그 자리에 있는지를 보고, 의미는 검토자가 읽는다(§11 「아무도 읽지 않아도 되는 것은 읽지 않는다고 적는다」 — 여기서는 검토자가 읽는다고 적는다).
