아래 반례는 확인란 문구를 근거로 구성한 **가상 산출물**입니다.

### AC-1

- **반례:** 실제 판정 id를 빠짐없이 한 행씩 담았지만, 차단 판정의 설명을 “경고만 출력한다”라고 적은 표. id와 행 수는 맞아도 사용자는 동작을 잘못 이해한다.
- **검토 시점:** 확인 가능하다. 다만 “지금 내는 판정”의 기준이 실제 실행 동작인지, 코드에 선언된 이름인지 정해져 있지 않다.
- **표현:** “이 저장소가 지금 내는 판정”은 범위가 확정되지 않은 집합이다. 원천 집합이 정해져야 ‘문서에서 빠진 id·문서에만 있는 id’로 누락과 과잉을 확인할 수 있다. 판정의 설명·차단과 경고 구분의 정확성은 요구하지 않는다.

### AC-2

- **반례:** 두 id 집합은 정확히 비교하지만, 같은 id를 유지하면서 차단 조건을 바꾼 코드는 그대로 통과시키는 검사. 문서의 “무엇을 막는지”가 낡아도 집합은 일치한다.
- **검토 시점:** 비교 입력과 실행 결과로 확인 가능하다. 다만 추출 결과가 실제 집행되는 판정을 나타내는지는 집합 비교만으로 확인되지 않는다.
- **표현:** “뽑은 판정 id”의 인정 형식과 제외 범위가 없다. 주석·실행되지 않는 코드·변수로 구성한 id의 취급이 불명확하다. 양쪽 차집합이라는 표현은 명확하지만, 기대 결과의 `exit 1`과 여기의 “0이 아님”은 서로 다르다.

### AC-3

- **반례:** ①은 추가한 줄의 구문 오류 때문에 종료하고, ②·③은 id 불일치 때문에 종료한 실측 기록. 세 종료 코드는 모두 비정상이지만, 정상적인 판정 추가를 탐지했다는 증거는 아니다.
- **검토 시점:** 위조한 파일 상태와 실행 기록이 남으면 사후 확인 가능하다. 종료 코드만으로는 실패 원인이 AC-2의 집합 비교였는지 구별할 수 없다.
- **표현:** 세 경우는 열거되어 있다. 그러나 ①의 “실재하지 않는 `check("<새 id>"` 한 줄”이 **새 id를 사용하는 유효한 호출**인지, 구문도 미완성인 줄인지 모호하다.

### AC-4

- **반례:** `[글](경로)` 형태만 검사하여 해당 검사용 파일 묶음(fixture)은 실패시키지만, 경로를 별도 줄에 정의하는 참조형 링크는 건너뛰는 구현. 검사하지 않은 링크는 계속 깨져 있다.
- **검토 시점:** 문서·대상 경로·실행 결과로 확인 가능하다. 특정 fixture의 실패만으로 다른 링크 표기까지 탐지한다고 확인할 수는 없다.
- **표현:** “찾으면”은 발견한 뒤의 동작만 규정하여 탐색 누락을 남긴다. 링크 표기 범위와 상대경로의 기준 위치가 불명확하다. 범위가 정해져야 ‘검사에서 빠진 상대 링크’라는 여집합을 확인할 수 있다.

### AC-5

- **반례:** id 중복을 탐지하면서, 제목이 같은 경우도 “중복 id”로 처리하는 구현. 지정한 fixture는 실패하지만, id가 서로 다른 정상 작업도 제목이 같으면 잘못 차단한다.
- **검토 시점:** 실제 id 중복과 종료 결과는 확인 가능하다. 마지막의 “폴더명만 보는 구현”은 다른 구현에 관한 부수 주장으로, 현재 구현의 결과만으로 검증되지 않는다.
- **표현:** “중복이면 실패”만 있어 중복이 아닌 경우의 잘못된 차단을 배제하지 않는다. 또한 “fixture를 통과한다”가 **명령의 성공 종료**인지, **예상한 비정상 종료를 확인한 검증의 성공**인지 모호하다. 두 의미는 여기서 반대다.

### AC-6

- **반례:** 인자 없이 실행하면 기본 경로가 다른 정상 저장소 사본을 가리키는 구현. 이 작업 트리에서 명령을 실행하여 0을 얻지만, 실제 검사 대상은 다른 파일들이다.
- **검토 시점:** 확인 가능하다. 다만 실행 위치·실제 검사 대상·검사 당시 파일 상태가 연결되어야 그 0이 무엇을 확인한 결과인지 알 수 있다.
- **표현:** “이 저장소의 작업 트리에서 실행”은 실행 위치를 나타내지만 검사 대상을 확정하지 않는다. 전칭 표현의 문제는 없다.

### AC-7

- **반례:** id 집합은 유지하고 승격 후보도 한 줄로 인쇄하지만, 기존 판정 조건을 바꾸어 종전 정상 입력을 실패시키는 구현. 명시된 집합 비교는 같아도 기존 종료 동작은 달라진다.
- **검토 시점:** 승인 기준 커밋이 기록되어 있다면 사후 비교 가능하다. 시간 순서 자체가 확인 불가능한 요구는 아니다. 다만 id 비교는 동작 보존이나 후보 출력의 성격까지 증명하지 않는다.
- **표현:** “추가 없음”은 현재에만 있는 id라는 차집합으로 확인할 수 있지만, “집합이 같다”는 삭제도 금지하므로 범위가 다르다. `check("`라는 특정 표기만으로 전체 종료 판정 목록을 대표할 수 있는지도 불명확하다. id 보존과 후보 출력이라는 별개 요구도 섞여 있다.

### AC-8

- **반례:** `bin/romeo integrity`를 실행하되, 실패를 무시하도록 설정한 단계. 명령은 실행되지만 무결성 오류가 CI, 즉 저장소 자동 검사의 실패로 이어지지 않는다.
- **검토 시점:** 단계의 존재는 파일로 확인 가능하다. 실제 실행 조건과 실패 처리 방식까지 보아야 자동 검사에서의 효과를 확인할 수 있다.
- **표현:** “단계를 담는다”는 존재만 요구한다. 어떤 상황에서 실행되는지와 실패를 무시해도 되는지가 정해져 있지 않다.

## 요약

- **AC-1:** id가 맞아도 판정 설명과 차단·경고 구분이 거짓일 수 있다.
- **AC-2:** id 일치로 동작의 일치까지 확인할 수 없으며 추출 규칙도 불명확하다.
- **AC-3:** 비정상 종료가 집합 불일치 탐지 때문인지 구별하지 못한다.
- **AC-4:** 발견한 링크만 처리하는 구현이 탐색 누락을 남길 수 있다.
- **AC-5:** 정상 작업의 잘못된 차단을 배제하지 않으며, 다른 구현에 관한 “통과” 표현도 모호하다.
- **AC-6:** 종료 코드 0이 해당 작업 트리를 실제 검사한 결과인지 연결되지 않는다.
- **AC-7:** 추가 금지와 집합 보존의 범위가 다르고, 동작 보존·후보 출력이 별도로 남는다.
- **AC-8:** 실행 단계가 있어도 검사 실패를 무시하는 설정을 허용한다.
## 반영

반박은 판정이 아니라 입력이다. 아래는 이 반박을 읽고 확인란을 고친 것과, 고치지 않고 남긴 것이다.

| AC | 지적 | 반영 |
| --- | --- | --- |
| AC-1 | 원천 집합이 확정되지 않았고, 차단·경고 구분의 정확성을 요구하지 않는다 | **수용.** 표의 각 행이 담을 것을 `(id, 수준, 출처 파일)` 로 못 박고, 수준(`error`/`warning`)을 대조 대상에 넣었다 — 차단을 경고라고 적으면 AC-2 가 잡는다 |
| AC-2 | 추출 규칙과 제외 범위가 없다. 주석·죽은 코드·변수로 만든 id 의 취급이 불명확하다. `exit 1` 과 「0 이 아님」이 다르다 | **수용.** 네 원천을 파일·표기까지 열거하고, 주석 줄과 문자열 리터럴이 아닌 표현을 제외로 명시했다. 종료 코드는 「1」로 통일했다 |
| AC-3 | 종료 코드만으로는 실패 원인이 집합 불일치인지 구별되지 않는다. ①의 위조 줄이 유효한 호출인지 모호하다 | **수용.** 「위조한 id 가 출력에 인쇄된다」를 더했고, ①을 기존 호출과 같은 형태의 유효한 `check("<id>", True)` 한 줄로 명시했다 |
| AC-4 | 「찾으면」이 탐색 누락을 남긴다. 링크 표기 범위와 상대경로 기준이 없다 | **수용.** 대상 표기를 인라인 링크로 한정하고 제외할 접두 넷을 열거했으며, 기준 위치를 「그 문서의 위치」로 못 박았다. 참조형 링크는 대상 밖으로 명시했다 |
| AC-5 | 중복이 아닌 경우의 잘못된 차단을 배제하지 않는다. 「폴더명만 보는 구현은 통과한다」는 부수 주장이라 검증되지 않는다 | **수용.** 부수 문장을 지우고 양방향 fixture 로 바꿨다 — 중복 fixture 에서 인쇄되고, `title` 만 같은 fixture 에서 인쇄되지 않는다 |
| AC-6 | 인자 없는 실행이 다른 경로를 볼 수 있다 | **수용.** 검사한 루트와 대조한 id 개수를 인쇄하고, 그 루트가 실행의 작업 디렉터리임을 요구한다 |
| AC-7 | 「추가 없음」과 「집합이 같다」의 범위가 다르고, id 보존과 후보 출력 두 요구가 섞여 있다 | **수용.** 후보 출력을 AC-8 로 분리했고, AC-7 은 승인 커밋 시점과의 집합 동일만 요구한다 |
| AC-7 | `check("` 표기만으로 종료 판정 목록을 대표할 수 있는지 불명확하다 | **미수용.** `romeo/close.py` 의 판정 등록 창구는 `check(` 하나다(`romeo/close.py:296` 의 지역 함수). 표기가 아니라 창구라 대표성이 성립한다 |
| AC-7 | id 집합이 같아도 판정 조건이 바뀌어 동작이 달라질 수 있다 | **미수용.** 판정 조건의 동작 보존은 이 단위의 요청 밖이고 회귀 방지 검사(check-4·check-5)가 겨눈다. AC 로 옮기면 §12 범위를 넘는다 |
| AC-8 | 실행 단계가 있어도 실패를 무시하는 설정을 허용한다 | **수용.** AC-9 에 `continue-on-error` 와 `|| true` 부재를 더했다 |
| AC-2 | id 일치가 「무엇을 막는지」의 정확성까지 보증하지 않는다 | **부분 수용.** 수준(`error`/`warning`)까지 대조하도록 넓혔다. 설명 산문의 정확성은 기계가 판정할 수 없어 검토자의 몫으로 남긴다 |
