### AC-1
- 반례: 방어 검사 기록 세 개가 빠졌는데, 첫 번째 누락 라벨만 경고에 표시한다. 봉인과 종료 코드는 유지하므로 문구는 충족하지만, 사용자는 나머지 누락을 알지 못한다.
- 검토 시점: 확인 가능한 명제다. 다만 “종료 코드는 경고 때문에 바뀌지 않는다”는 비교 기준이 불명확하다. 다른 오류가 함께 있는 실행에서 무엇과 비교해야 하는지 정해져 있지 않다.
- 표현: “하나라도”는 경고 발생 조건을 정하지만, **빠진 라벨 모두를 표시해야 하는지**는 정하지 않는다. “종료 검사가 판정에 쓰는 방어 검사”가 상황별로 달라지는지도 문장만으로는 알 수 없다.

### AC-2
- 반례: 없음. 실제로 동일한 목록을 공유하고 한 곳의 변경이 경고에도 반영되며 중복 정의가 없다면, 목록의 중복 관리를 없애려는 의도를 직접 충족한다.
- 검토 시점: 확인 가능한 명제다. “바꾸면”은 과거 작업 순서를 요구하지 않고, 완성된 코드에서 변경의 영향을 확인할 수 있는 조건이다.
- 표현: “목록 그 자체”가 **전체 후보 목록인지, 해당 run에 적용되는 목록인지** 불명확하다. 종료 검사가 조건에 따라 라벨을 선택한다면 두 집합이 달라질 수 있다. 중복 금지는 여집합 관점에서 별도 목록 정의의 존재 여부로 확인할 수 있지만, 목록의 동일성을 판단할 기준은 필요하다.

### AC-3
- 반례: 계약 파일의 `base_sha`는 제대로 읽지만, 계약 sha256은 파일 안에 적힌 오래된 해시 문자열을 그대로 복사한다. 두 값 모두 “그 파일에서 읽은 값”이고 별도 인자도 없지만, 브리프의 해시는 실제 계약 파일을 식별하지 못한다.
- 검토 시점: 확인 가능한 명제다. 계약 내용을 달리한 입력에 대한 출력과 인자 정의를 검토할 수 있다. 다만 해시의 계산 대상이 불명확하면 정확성을 판단할 기준이 없다.
- 표현: **파일에 저장된 해시 값과 파일 자체를 계산한 해시**가 구분되지 않는다. `base_sha` 변경에 따른 출력 변화만 명시되어 있어, 다른 계약 내용이 바뀌었을 때 해시가 어떻게 달라져야 하는지도 빠져 있다.

### AC-4
- 반례: `fill_brief.py`라는 문자열이 직접 들어 있는 런북과 코드는 모두 수정한다. 그러나 경로를 변수로 전달받아 실행하는 공용 실행 코드는 예전 인자를 계속 붙인다. 검색으로 얻은 집합에서는 AC를 충족하지만, 실제 호출 하나는 실패한다.
- 검토 시점: 저장소의 특정 상태에서는 확인 가능하다. 다만 검색 대상·제외 규칙과 간접 호출을 추적할 범위가 없어 검토자마다 다른 집합을 얻을 수 있다.
- 표현: **문자열 검색 결과와 실제 호출 자리 전체가 같다는 전제**가 숨어 있다. 사람이 읽는 런북도 “실제로 실행하는 자리”에 포함되어 용어가 혼재한다. 여집합으로 인터페이스 불일치 호출을 찾으려 해도, 먼저 호출 자리의 범위가 확정되어야 한다.

### AC-5
- 반례: fixture에 `하네스`라는 유효한 선언을 넣고, 실행 코드는 계속 부착 대상 저장소를 검사한다. 선언 없는 fixture에는 id를 포함한 문제를 내므로 문구는 충족하지만, 선언과 실제 검사 대상은 어긋난다.
- 검토 시점: 확인 가능한 명제다. 선언 유무와 누락 시 출력은 관찰할 수 있다. 그러나 **선언이 실제 검사 대상을 결정하는지**는 요구하지 않는다.
- 표현: “충돌 fixture”의 대상 집합이 명시되지 않았다. “하나라도”는 문제 발생 조건일 뿐, 누락된 fixture의 id를 전부 알려야 하는지는 불명확하다. 선언이 없는 경우 외에, 허용되지 않은 선언 값도 다루지 않는다. 전칭 요구를 위반 fixture의 존재 여부로 확인하려면 대상 집합과 유효한 선언의 기준이 필요하다.

### AC-6
- 반례: 대상에 `core/`가 없을 때만 하네스 코어로 돌아가 검사하고, 대상에 `core/`가 있으면 대상 코어를 검사한다. 명시된 조건에서는 금지 패턴을 발견하지만, 하네스를 검사한다고 선언한 c7의 실제 대상은 상황에 따라 바뀐다.
- 검토 시점: 확인 가능한 조건부 명제다. 다만 “findings가 나온다”만으로는 **심은 금지 패턴 때문에 해당 위치의 문제가 검출됐는지** 구별하지 못한다. 다른 문제로 나온 findings도 조건을 만족할 수 있다.
- 표현: `core/`가 없는 경우만 다루며, 있는 경우는 요구 범위 밖에 남는다. 이는 그 자체로 모순은 아니지만, AC-5의 선언과 실제 대상의 일치를 보장하기에는 부족하다. “그 코어”의 하네스 위치와 “금지 패턴”의 범위도 문장 안에서는 특정되지 않는다.

## 요약

- **AC-1:** 누락 라벨 전체 표시 여부와 종료 코드 비교 기준이 불명확하다.
- **AC-2:** 공유해야 하는 목록이 전체 후보인지 해당 run의 적용 목록인지 불명확하다.
- **AC-3:** 파일 내부의 해시 문자열과 실제 파일의 해시를 구분하지 않는다.
- **AC-4:** 문자열 검색에서 빠지는 간접 호출은 예전 인터페이스를 유지해도 통과한다.
- **AC-5:** 검사 대상 선언과 실제 실행의 일치를 요구하지 않는다.
- **AC-6:** 대상에 `core/`가 있는 경우와 검출 결과가 심은 패턴에 대응하는지를 다루지 않는다.
## 반영 (2026-09-13)

반박은 판정이 아니라 입력이다. 여섯 지적을 전부 읽고 확인란의 문장을 고쳤다.

| AC | 지적 | 어떻게 고쳤나 |
| --- | --- | --- |
| AC-1 | 첫 누락 라벨만 표시해도 문구를 충족한다 · 종료 코드 비교 기준이 없다 | 「빠진 라벨을 **모두** 이름으로 말한다」로 좁히고, 비교 대상을 「같은 봉투를 방어 검사가 전부 있는 run 에 기록했을 때」로 못 박았다 |
| AC-2 | 「목록 그 자체」가 전체 후보인지 run 적용 목록인지 불명확 | 「목록의 **정의가 저장소에 하나뿐**이고 경고가 그 정의를 읽는다」로 바꿨다 — 동일성이 아니라 정의의 유일성을 요구한다 |
| AC-3 | 계약 파일 **안에 적힌** 해시 문자열을 복사해도 충족한다 | 「그 파일의 **바이트에서 계산한** 값」으로 명시하고, 파일 내용 변경 → sha256 변경 / `base_sha` 필드 변경 → 브리프 `base_sha` 변경을 각각 요구했다 |
| AC-4 | 경로를 변수로 받아 실행하는 간접 호출은 문자열 검색에서 빠진다 | 요구를 **검색 집합에서 스크립트 쪽으로** 옮겼다 — 없어진 인자를 넘기는 호출은 어디서 오든 0 이 아닌 종료 코드로 거부된다. 검색으로 얻은 두 자리는 그다음 문장이 따로 요구한다 |
| AC-5 | 선언을 넣어 두고 실행 코드가 다른 루트를 검사해도 충족한다 · 허용 밖 값을 다루지 않는다 | 「`check_conflicts` 는 **그 선언이 정한 루트**를 그 fixture 의 검사에 넘긴다」를 요구에 넣고, 문제 조건에 「허용 목록 밖의 값」을 더했다 |
| AC-6 | 대상에 `core/` 가 있는 경우가 빠졌다 · findings 가 심은 패턴 때문인지 구별 못 한다 | 「`core/` 가 **있든 없든**」으로 양쪽을 덮고, findings 가 **그 파일의 경로**를 가리킬 것과 「대상 코어에만 심으면 findings 가 나오지 않는다」는 반대 방향을 함께 요구했다 |

**반영하지 않은 것:** 없음. AC-2 의 「반례: 없음」은 지적이 아니라 확인이다.

**남은 `AC_UNIVERSAL` 경고 2건은 의도한 것이다.** AC-1 의 «전부» 는 유한한 라벨 목록에 대한 비교 기준이고,
AC-6 에 뜬 «하나라도» 는 AC-6 문장이 아니라 그 뒤 「위험과 되돌리기」 절의 낱말이다 —
`romeo/validate.py` 의 `ac_items` 가 **마지막 AC 의 경계를 문서 끝까지** 잡는 결함이며, 이 단위 범위 밖이라 `open-questions.md` 에 연다(§12).
