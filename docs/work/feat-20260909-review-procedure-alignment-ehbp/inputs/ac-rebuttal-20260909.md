아래 반례는 확인란 문구를 기준으로 구성한 **가상 산출물**입니다.

### AC-1

- **반례:** 라벨은 정본에서 읽고, 명령은 `"review"`와 `"record"`를 각각 고정해 실제 파서의 등록 항목을 찾아오는 검사. 금지한 문자열 리터럴은 0건이지만 명령 이름은 검사에도 중복된다. 이름을 바꾸면 안내의 누락을 보고하는 대신 등록 항목을 찾다가 오류가 난다.
- **검토 시점:** 코드에서 값을 가져오는 방식과 문자열 개수는 확인 가능하다. 다만 향후 명령 변경에도 안내 불일치를 지목한다는 성질까지 이 조건으로 확인되지는 않는다.
- **표현:** `0건`의 범위는 명확하지만, 이름을 나누어 고정하는 경우는 포함하지 않는다. 등록된 명령 중 무엇을 봉인 명령으로 식별하는지도 정해져 있지 않다.

### AC-2

- **반례:** 문서 셋의 「사용하지 말아야 할 예시」에 정확한 라벨과 봉인 명령이 들어 있는 산출물. 문자열 존재 검사는 충족하지만 독자에게 전달하는 지시는 반대다.
- **검토 시점:** 현재 문서와 검사의 동작으로 확인 가능한 명제다.
- **표현:** 문서 집합은 세 개로 열거되어 있고, 누락 쌍이라는 여집합도 제시되어 있다. 문제는 「나타난다」가 실행 지시·부정 예시·주석을 구별하지 않는다는 점이다.

### AC-3

- **반례:** 라벨 비교는 정본을 따르지만 봉인 명령을 찾는 경로는 현재 이름에 고정된 검사. 제시한 라벨 삭제·복원·바꿔치기 결과는 모두 만족하면서, 명령 이름이 바뀌면 안내의 누락을 지목하지 못한다.
- **검토 시점:** 「지금 문서」가 확인란 작성 시점인지 구현 완료 시점인지 불명확하다. 앞의 문제 설명대로 현재 안내에 라벨이 없다면, 라벨 줄 삭제와 원문 `0쌍`의 기준 상태가 성립하지 않는다.
- **표현:** 「다른 값」에는 이미 문서에 있는 값도 포함된다. 그런 값으로 바꾸면 정상 검사도 누락 쌍을 내지 않을 수 있다. 「전부」는 AC-2의 세 문서로 범위가 닫혀 있어 여집합을 특정할 수 있다.

### AC-4

- **반례:** 명령·라벨·전후 순서를 정확히 안내하지만, 봉투 기록 예시와 방어 검사 예시가 서로 다른 run을 대상으로 하는 문서. 요구한 내용은 들어 있어도 증거가 다른 실행에 나뉘어 문서대로 수행한 실행의 종료를 뒷받침하지 못한다.
- **검토 시점:** 문서가 해당 지시를 담았는지는 확인 가능하다. 「전후」는 안내할 실행 순서이므로, 작성자가 과거에 무엇을 먼저 했는지 증명하라는 요구는 아니다.
- **표현:** 문서 셋의 범위는 명확하다. 다만 필요한 문구의 존재와 실행 예시 사이의 일관성이 구분되지 않는다. C-C6 해설과 기존 implement 사례는 결과 조건과 별개의 근거 문장이다.

### AC-5

- **반례:** 검토자 계약을 만들 때 기존 회차의 시작 시각을 새 시각으로 덮어쓰는 구현. 새 회차를 열지 않고 제시된 모든 개수 조건도 만족하지만, 관통 시작 이력이 검토자 재실행 시각으로 바뀐다.
- **검토 시점:** 두 생성 순서는 입력 상태와 결과를 남겨 확인할 수 있다. 다만 「지금도 그렇다」는 변경 전 상태에 관한 주장이라 완료본만으로는 확인되지 않는다.
- **표현:** 「해당 run에 회차가 없음」과 「전체 기록이 비어 있음」은 다른 조건이다. 다른 run의 회차가 이미 있는 상태는 본문의 적용 범위에 들어가지만 판별 예에는 없다. 회차 개수 유지와 기존 기록 보존도 같은 뜻이 아니다.

### AC-6

- **반례:** `reviewer_runs:`를 run별 최신 상태 목록으로 구현해, 같은 run으로 검토자 계약을 다시 만들면 기존 항목의 시각을 덮어쓰는 산출물. 매번 run과 시각을 남기고 `gate()`도 유지하지만 앞선 재실행 이력은 사라진다.
- **검토 시점:** 기록 전후의 상태와 반환값은 확인 가능하다. 다만 유한한 횟수의 실행 결과만으로 「몇 번 만들어도」 전체를 확인할 수는 없다.
- **표현:** 목록이 계약별 이력인지 run별 최신 상태인지 정해져 있지 않다. 「몇 번 만들어도」는 횟수와 초기 이력 상태의 범위가 열려 있다. 반환값이 달라지는 사례라는 여집합은 잡을 수 있지만, 비교할 상태 집합이 빠져 있다.

### AC-7

- **반례:** 분할 전 AC-2를 충실히 반박한 1차 파일과 다른 AC를 반박한 2차 파일을 합쳐, 내용이 달라진 현재 AC-2도 반박된 것으로 처리하는 구현. 연결된 파일의 절을 모두 합치지만 현재 요구에 대한 반박은 없다.
- **검토 시점:** 연결된 파일과 절의 합집합은 확인 가능하다. 번호가 일치한다는 사실만으로 현재 AC 문장을 반박했다는 사실까지 확인되지는 않는다.
- **표현:** 「접두」의 실제 값과 파일명·전체 경로 중 어느 것에 적용하는지가 없다. 「합집합」의 원소도 AC 번호인지 절 내용인지 불명확하다. 「모든」의 여집합을 정하려면 먼저 대상 파일과 집합의 원소가 확정되어야 한다.

### AC-8

- **반례:** 여러 파일의 반박을 합친 뒤 기존 경고 목록을 초기화하고 미반박 AC 경고만 반환하는 구현. 제시된 짝과 목록 밖 파일 제외는 만족하지만, 반박과 무관한 다른 경고도 사라진다.
- **검토 시점:** 입력 파일·연결 목록·출력이 남아 있으면 확인 가능한 명제다. 실제 개발 순서를 증명할 필요는 없다.
- **표현:** 「경고 0건」이 반박 경고만 뜻하는지 전체 경고인지 불명확하다. 또한 목록 밖 파일이 이미 반박된 AC만 담으면, 잘못 읽더라도 합집합이 같아져 제외 여부를 구별하지 못한다.

### AC-9

- **반례:** 없음. 실제 명령의 성공과 두 경로의 갱신을 모두 요구하는 것으로 읽으면, 생성본 동기화라는 이 AC의 의도를 배신하는 별도 반례는 없다. 잘못된 안내가 그대로 복제되는 문제는 AC-4의 내용 문제다.
- **검토 시점:** 검토 대상 버전에 연결된 명령 출력·종료 코드와 생성본으로 확인 가능하다.
- **표현:** 두 경로가 열거되어 있다. 「함께」를 두 경로 모두의 현재 갱신 상태로 읽으면 별도의 시간 순서나 열린 전칭 범위 문제는 없다.

## 요약

- **AC-1:** 금지 문자열을 나누어 고정하면 정본 중복을 피하지 못한다.
- **AC-2:** 문자열 존재만으로 올바른 실행 지시인지 구별하지 못한다.
- **AC-3:** 기준 문서의 시점과 바꿔칠 값이 불명확하고, 명령 변경에 대한 판별이 빠져 있다.
- **AC-4:** 필수 문구가 있어도 실행 예시끼리 어긋날 수 있다.
- **AC-5:** 회차 개수가 유지돼도 기존 이력이 훼손될 수 있으며, 판별 상태가 본문보다 좁다.
- **AC-6:** 재실행 이력의 보존 단위와 반환값을 비교할 상태 범위가 정해져 있지 않다.
- **AC-7:** 대상 접두·합집합의 원소·현재 AC와 반박 내용의 대응이 불명확하다.
- **AC-8:** 경고의 범위와 목록 밖 파일 제외를 구별할 조건이 부족하다.
## 반영 (2026-09-09 · 1차)

여덟 지적을 전부 읽었다. 통과 가능한 구멍은 **정본이 하나로 정해지지 않은 것**과 **이력을 덮어쓰는 구현**이었다.

**반영.**

- AC-1: 「명령 이름을 `"review"`+`"record"` 두 조각으로 나눠 고정하면 리터럴 0건이면서 중복이다」 ·
  「등록된 명령 중 무엇을 봉인 명령으로 식별하는지 정해져 있지 않다」 → **정본을 만들었다.**
  `romeo/close.py` 에 `SEAL_COMMAND` 를 둔다 — 그것을 요구하는 것이 종료 검사이므로 요구가 사는 자리에 함께 둔다.
  금지 리터럴도 조각까지 열거했다(`record` · `"review"` 단독 포함). 변경 범위에 `romeo/close.py` 를 넣었다.
- AC-2: 「부정 예시에 정확한 라벨이 들어 있으면 통과한다」 → **절반만 반영했다.**
  백틱으로 감싼 것만 세도록 조여 산문 언급과 실행 지시를 가른다. 「~하지 말라」는 문장 안의 백틱까지 가르는 것은
  자연어 판정이라 이 단위가 감당할 크기가 아니다 — 아래 「반영하지 않은 것」에 남긴다.
  대신 `SEAL_COMMAND` 가 **CLI 파서에 실제 등록됐는지**를 먼저 보게 해서, 정본이 실재하지 않는 이름을 가리키는 경우를 막았다.
- AC-3: **가장 정확한 지적이다** — 「지금 안내에 라벨이 없으므로 「라벨 줄 삭제」의 기준 상태가 성립하지 않는다」.
  기준을 **구현이 끝난 뒤의 안내 문서**로 못박고, 「다른 값」을 「안내 문서 셋 어디에도 나타나지 않는 값」으로 조였다.
  `SEAL_COMMAND` 를 바꿔치는 세 번째 짝도 넣었다 — 명령 이름 변경에 대한 판별이 빠져 있다는 지적을 닫는다.
- AC-4: 「봉투 기록 예시와 방어 검사 예시가 서로 다른 run 을 대상으로 하는 문서」 →
  요구에 「그 셋이 **같은 run** 에 들어가야 한다」와 「손으로 복사하면 봉인이 서지 않는다」를 더해 넷으로 만들었다.
- AC-5: 「기존 회차의 시작 시각을 덮어쓰는 구현」 → 기존 항목이 **바이트로 그대로** 남을 것을 요구에 넣었다.
  「지금도 그렇다」는 변경 전 상태 주장이라 뺐고, 판별 상태를 셋으로 열거했다(빈 상태 · 다른 run 의 회차가 있는 상태 · 같은 run 의 회차가 있는 상태).
- AC-6: 「`reviewer_runs:` 를 run별 최신 상태로 구현하면 앞선 이력이 사라진다」 →
  **덮어쓰지 않는 이력**임을 명시하고, 같은 run 을 다시 만들 때 항목이 늘지도 시각이 바뀌지도 않는다는 것까지 적었다.
  「몇 번 만들어도」를 「서로 다른 두 run 으로」로 유한하게 바꿨고, `gate()` 반환값 **세 요소**로 비교 대상을 못박았다.
- AC-7: 「접두를 파일명에 적용하는지 경로에 적용하는지」 · 「합집합의 원소가 번호인지 내용인지」 →
  「`inputs:` 목록의 각 항목 **문자열이** `rebuttal_prefix` 로 시작하는」 · 「합집합의 원소는 **AC 번호**」로 명시했다.
- AC-8: 「기존 경고 목록을 초기화하고 미반박 경고만 반환하는 구현」 · 「경고 0건이 반박 경고만인지」 →
  「**그 함수가 내는** `AC_UNREBUTTED` 경고」로 범위를 좁히고 「다른 경고 경로는 건드리지 않는다」를 적었다.
  목록 밖 파일 케이스도 조였다 — 그 파일이 담은 AC 는 1차 파일이 담지 않은 것이라야 잘못 읽었을 때 드러난다.

**반영하지 않은 것.**

- AC-2 의 「부정 예시」 전체 — 문서가 「이렇게 쓰지 말라」의 예로 정확한 라벨을 적는 경우까지 가르려면
  자연어 판정이 필요하다. 백틱 규칙까지가 이 단위의 크기다. 실제로 그런 문서를 쓰는 것은 사람의 오작성이고,
  검토자가 읽는다.
- AC-7 의 「번호가 같다고 현재 AC 문장을 반박했다는 뜻은 아니다」 — 옳지만 **이 검사의 원래 성질**이다.
  `romeo/docs.py` 의 docstring 이 「절의 **존재**만 본다 — 내용이 값어치 있는지는 사람이 읽는다」고 이미 적는다.
  내용 판정을 넣는 것은 이 단위의 요청이 아니다(§12).
- `AC_UNIVERSAL` 이 AC-2 의 「하나라도」, AC-3·AC-7 의 「전부」를 경고한다. 고치지 않는다 —
  전자는 여집합 표현이고 후자는 **유한하게 열거된 세 문서**를 가리킨다. 경고이고 종료 코드를 바꾸지 않는다(K-31).
