Worker는 `$repo-archive`가 discovery 목록에 없으면 해당 절대 경로의 `SKILL.md`를 읽어 같은 절차를 수행한다. 절대 경로도 읽을 수 없으면 `BLOCKED_SKILL_UNAVAILABLE`로 실패 보고한다.\n\n   Shell에서 작업 설명을 만들 때 `$repo-archive`의 `$`가 변수로 확장되지 않도록 단일 인용부호 또는 `\\$repo-archive`를 사용한다. 작업 설명에는 GitHub 읽기 전용, worker worktree의 `archive/<owner>-<repo>/` 작성, 고정 SHA·생성 경로·근거 공백·완료 상태를 `worker_done`으로 보고한다는 조건도 포함한다.\n7. 아래 기본 실행을 사용한다. `--model`과 `--effort`를 생략해 현재 Orca 계정의 기본 Codex 모델을 사용한다. Orca가 사람이 읽는 `sol` 별칭이 아니라 계정별 opaque provider ID를 요구하므로, 검증하지 않은 모델 이름을 넣어 실행을 막지 않는다.\n\n```bash\norca orchestration worker-start \\\n  --run <run-id> \\\n  --task <task-id> \\\n  --worktree new-child \\\n  --agent codex \\\n  --name repo-<owner>-<repo> \\\n  --repo id:<current-worktree-repoId> \\\n  --setup inherit \\\n  --timeout-ms 3600000 \\\n  --json\n```\n\n8. `orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json`로 대기한다. 질문·실패·시간 초과를 성공으로 간주하지 않는다.\n9. 성공한 worker의 `archive/<owner>-<repo>/`만 현재 워크트리의 같은 위치로 복사한다. 이미 승인한 `--replace`인 경우에만 기존 대상 전체를 교체한다.\n10. `bash scripts/validate-repo-archive.sh archive/<owner>-<repo>`를 실행한다. 실패하면 생성물은 `미검증`으로 보고하고 성공으로 말하지 않는다.\n11. 검증 결과와 worker 출력이 보존된 뒤 `orca orchestration worker-release --dispatch <dispatch-id> --json`으로 정확히 그 완료 worker 터미널만 해제한다. 통과했을 때만 경로·SHA·문서 수·미확인을 보고한다.\n\n## 대형 레포의 선택적 모델 분리\n\n`--staged`가 명시되고 각 단계의 **검증된 provider model ID**가 제공된 경우에만 이 경로를 사용한다. 기본값을 세 모델 파이프라인으로 바꾸지 않는다. 후보가 40개 이상이거나 다중 패키지 레포일 때 다음처럼 순차 실행한다.\n\n1. `luna`: `_staging/discovery.md`만 작성한다. 읽기·경로 분류·근거 위치 수집만 한다.\n2. `sol`: discovery artifact와 원문 근거를 다시 열어 중요도 판별 및 `00`, `02`, `04`, `05` 문서를 작성한다.\n3. `terra` 또는 `luna`: 확정된 번역 파일만 작성한다.\n\n세 작업은 같은 워크트리에서 순차로 실행하거나, 이전 산출물을 다음 작업자에게 명시적으로 전달해야 한다. 별도 병렬 워크트리에 같은 `archive/`를 쓰게 하면 결과가 자동 합쳐지지 않는다. 실제 provider ID가 확인된 경우에만 각 `worker-start` 호출에서 `--model`과 `--effort`를 다르게 준다. 하나라도 확인되지 않았으면 기본 Codex 작업자 한 명으로 실행한다.\n\n### scripts/validate-repo-archive.sh ###\n#!/usr/bin/env bash\nset -euo pipefail\n\narchive_dir=${1:?\"usage: validate-repo-archive.sh <archive-dir>\"}\n\nrequired_files=(\n  \"_source.md\"\n  \"00-exploration.md\"\n  \"02-workflow-summary.md\"\n  \"04-components-table.md\"\n  \"05-pm-harness-notes.md\"\n  \"06-source-evidence.md\"\n)\n\nrequired_dirs=(\"01-docs\" \"03-components\")\n\nif [[ ! URL의 브랜치/경로가 있으면 그 ref를 사용한다.\n- `gh` CLI가 설치되고 해당 레포에 읽기 권한이 있는지 먼저 확인한다. private 레포도 현재 `gh` 인증 범위에서 읽기만 허용한다.\n- 분석은 GitHub API 또는 raw 파일 읽기로 수행한다. 기본적으로 clone, issue/PR 작성, 설정 변경, secret 조회, 배포를 하지 않는다.\n- 기존 `archive/<owner>-<repo>/`는 보존한다. `--replace`는 교체 의도 표시일 뿐이므로, 대상 경로와 복구 방법을 보여준 뒤 현재 대화에서 재승인받은 경우에만 해당 대상 전체를 교체한다. 실패 시 기존 아카이브는 건드리지 않는다.\n- 사실, 추론, 미확인 항목을 분리한다. 코드나 설정을 열지 못한 내용은 추측으로 채우지 않는다.\n\n## 모델과 단계\n\n기본값은 현재 Orca 계정의 **기본 Codex 작업자 한 명**이다. 파일 근거와 해석을 한 컨텍스트에서 유지하므로 보통 가장 정확하고 운영도 단순하다. 이는 논리 역할로서의 `sol`에 해당하지만, Orca가 검증하지 않은 provider model ID를 추정해 넣지는 않는다.\n\n대형 레포에서만 두 단계로 나눈다.\n\n| 단계 | 담당 | 산출물 | 사용 조건 |\n| --- | --- | --- | --- |\n| 인벤토리 | `luna` 역할 | `_staging/discovery.md` | 후보 파일이 40개 이상이거나 여러 언어/패키지가 섞인 경우 |\n| 판별·서술 | `sol` 역할 | 최종 아카이브 | 항상 |\n| 번역 보조 | `terra` 또는 `luna` 역할 | 확정 문서의 번역 초안 | 번역 문서가 많을 때만 |\n\n모델 분리는 독립 작업자 간 파일을 자동 공유하지 않는다. 따라서 단계형 실행에서는 이전 단계의 `_staging/` 산출물을 다음 작업자가 읽을 수 있는 동일 워크트리에 두거나, 오케스트레이터가 파일을 전달해야 한다. 세 모델을 동시에 실행해 같은 아카이브 경로에 쓰게 하지 않는다.\n\n## 절차\n\n### 1. 소스 고정\n\n1. URL에서 owner, repo, ref를 파싱한다.\n2. ref가 없으면 `gh api repos/<owner>/<repo>`에서 `default_branch`를 얻는다.\n3. `gh api repos/<owner>/<repo>/commits/<ref> --jq .sha`로 분석 커밋 SHA를 고정한다.\n4. `_source.md`에 URL, ref, SHA, 분석 시각, 접근 실패 항목을 기록할 준비를 한다.\n\n브랜치 이름만 기록하면 이후 내용이 바뀌어 재현할 수 없다. SHA는 이 아카이브가 어떤 시점의 레포를 설명하는지 보장하는 기준점이다.\n\n### 2. 파일 인벤토리와 후보 선정\n\n`gh api repos/<owner>/<repo>/git/trees/<sha>?recursive=1`으로 경로 목록만 얻는다. 전체 clone이나 전체 파일 다운로드를 하지 않는다.\n\n다음 순서로 후보를 고르고, 각 항목의 선정 이유를 `00-exploration.md`에 남긴다.\n\n1. 안내와 에이전트 정의: `README*`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING*`, `SKILL.md`, `.claude/agents/**`, `.claude/skills/**`, `.agents/skills/**`.\n2. 실행 계약: package manager manifest, lockfile, `Makefile`, `justfile`, `docker-compose*`, `Dockerfile`, `*.yaml` CI/workflow, `*.toml`/`*.json` 설정, `.env.example`.\n3. 실제 진입점: manifest scripts가 가리키는 파일, `src/main.*`, `src/index.*`, `app.*`, `cmd/**/main.*`, 서버/CLI/worker 엔트리.\n4. 핵심 흐름을 증명하는 코드: API/CLI handler, orchestration/agent runner, 저장소 adapter, 권한·네트워크·queue 경계, 주요 테스트 fixture와 integration test.\n5. 제한된 `docs/` 문서: 사용법·아키텍처·운영 설명만. 생성물, 전체 API reference, lockfile, vendor/build output은 제외한다.\n\n후보가 많으면 문서만 남기지 말고 실행 경로별로 최소 한 개의 진입점과 한 개의 검증 또는 설정 근거를 남긴다. 40개를 넘으면 중복 문서를 합치고 제외한 경로와 이유를 기록한다.\n\n### 3. 내용 확보와 교차 검증\n\n후보만 `gh api repos/<owner>/<repo>/contents/<path>?ref=<sha>` 또는 raw URL로 읽는다. 큰 파일은 필요한 함수/섹션만 읽고 이 제한을 기록한다.\n\n다음 질문을 코드 근거로 답한다.\n\n- 사용자는 무엇을 입력하고, 시스템은 어떤 출력 또는 상태 변경을 만드는가?\n- [Basecamp의 Pitch 구성](https://basecamp.com/shapeup/1.5-chapter-06?utm_source=chatgpt.com)\n\n### 이 값들은 합산 점수로 만들지 않는 것이 중요합니다\n\n`총점 12점이므로 Large PRD` 같은 방식은 권하지 않습니다.\n\n축마다 역할이 다르기 때문입니다.\n\n- 불확실성이 높다 → Discovery를 먼저 한다.\n- 범위가 넓다 → Initiative와 Feature로 문서를 나눈다.\n- 영향이 크다 → 전략 연결과 성과 측정을 강화한다.\n- 위험이 높다 → 승인·롤백·감사 문서를 강제한다.\n- 조율이 복잡하다 → 의존성과 마일스톤 문서를 추가한다.\n\n다음 항목들은 합산 점수와 관계없이 **Hard Gate**로 처리해야 합니다.\n\n- 결제·정산·가격\n- 개인정보·보안·권한\n- 법무·규제·약관\n- 운영 데이터 삭제\n- 데이터 마이그레이션\n- 외부 공개 API\n- 되돌리기 어려운 정책 변경\n- 서비스 중단 가능성\n\n버튼 문구 한 줄이라도 결제 약관에 관련되면 기획 강도가 올라가야 합니다. 반대로 코드 전체를 리팩터링하더라도 사용자 동작과 제품 정책이 그대로라면 제품 PRD는 얇아도 됩니다.\n\n이 때문에 **제품 기획 강도와 기술 구현 강도는 반드시 별도로 분류**해야 합니다. 사용자가 정한 “모든 구현에 기술 스펙을 작성한다”는 원칙과도 잘 맞습니다.\n\n---\n\n## 2. 분류에 따라 문서 양식이 달라져야 하는가\n\n동의합니다. 다만 독립된 PRD 템플릿을 계속 추가하는 방식은 추천하지 않습니다.\n\n가장 좋은 구조는 다음입니다.\n\n> 공통 코어 문서\n>\n> - 작업 유형별 기본 모듈\n> - 조건에 따라 붙는 오버레이 모듈\n\n### 모든 구현 기획에 공통으로 들어갈 최소 코어\n\n- 배경과 문제\n- 대상 사용자와 사용 상황\n- 기대하는 사용자·사업 결과\n- 범위와 비범위\n- Acceptance Criteria 또는 의사결정 기준\n- 주요 가정과 열린 질문\n- 문서 오너와 상태\n- 상위 목표·근거·관련 문서\n- 기술 스펙 링크\n\n그 위에 필요한 모듈만 추가합니다.\n\n\n|               |                                   |\n| ------------- | --------------------------------- |\n| 조건추가할 모듈      |                                   |\n| 문제·시장 불확실성 높음 | Discovery / Research / Validation |\n| 실험이 목적        | Hypothesis / Experiment Design    |\n| 핵심 지표에 영향     | Measurement / Analytics           |\n| 여러 사용자 흐름 변경  | Journey / Story Map               |\n| 결제·개인정보·법무    | Risk / Approval / Compliance      |\n| 기존 사용자·데이터 전환 | Migration / Rollback              |\n| 여러 팀·시스템 참여   | Dependency / Stakeholder          |\n| 외부 출시         | GTM / Launch                      |\n| 운영 절차 변경      | Support / Operations              |\n| 장기간 영향을 주는 결정 | Product Decision Record / ADR     |\n\n\n문제가 충분히 검증되지 않았다면 상세 PRD를 크게 작성하는 것이 아니라, Discovery 문서로 먼저 라우팅해야 합니다. GOV.UK의 서비스 개발 방식도 Discovery의 목적을 “무엇을 만들지 상세화”가 아니라 사용자·제약·문제를 파악하고 다음 단계로 진행할지 결정하는 것으로 구분합니다. [GOV.UK Discovery 가이드](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works?utm_source=chatgpt.com)\n\n### 추천 문서 패키지\n\n\n|                      |                                                      |\n| -------------------- | ---------------------------------------------------- |\n| 분류기본 패키지             |                                                      |\n| Change               | Change Brief + Tech Spec                             |\n| Feature              | Feature PRD + Tech Spec                              |\n| Experiment           | Experiment Brief + Measurement Plan + 필요 시 Tech Spec |\n| Initiative           | Initiative Charter + 하위 Feature PRD들 + Tech Spec들    |\n| Product / Strategy   | Product Strategy + Research + Initiative Map         |\n| Platform / Migration | 얇은 Product Brief + Tech Spec + Migration·Rollback    |\n| GTM / Operation      | GTM·Operations Brief + 제품 변경이 있으면 관련 PRD             |\n\n\n기존 방식 중 “큰 PRD 하나와 마일스톤별 구현계획”도 여전히 유효합니다. 다만 역할을 명확히 해야 합니다.\n\n- `Initiative Charter`는 왜 하는지, 어떤 성과를 원하는지, 무엇을 하지 않는지를 소유합니다.\n- `Feature PRD`는 사용자 행동, 비즈니스 규칙, 예외 상태, Acceptance Criteria를 소유합니다.\n- `Milestone Plan`은 구현 순서, 의존성, 컷라인, 검증 시점을 소유합니다.\n- `Tech Spec`은 구현 방식과 기술적 계약을 소유합니다.\n\n마일스톤 계획서는 하위 PRD 내용을 복사한 또 다른 PRD가 아닙니다.\n\n하나의 문서로 합쳐도 되는 조건은 다음과 같습니다.\n\n- 단일 사용자 문제\n- 단일 오너\n- 단일 출시\n- 단일 성공지표\n- 하나의 의사결정으로 종료\n\n다음 중 하나라도 나타나면 분리하는 편이 좋습니다.\n\n- 독립적으로 배포할 수 있다.\n- 오너나 승인자가 다르다.\n- 대상 사용자나 성공지표가 다르다.\n- 여러 마일스톤에 걸친다.\n- 병렬로 개발된다.\n- 별도 법무·보안·운영 검토가 필요하다.\n\n실제로 성숙한 기술 프로젝트도 모든 변경에 동일한 절차를 적용하지 않습니다. Rust는 일반적인 변경, 주요 변경 제안, 더 무겁고 논쟁적인 RFC 절차를 구분합니다. [Rust의 Major Change Process](https://rust-lang.github.io/rfcs/2904-compiler-major-change-process.html?utm_source=chatgpt.com)\n\n---\n\n## 3. 한 프로젝트 안에서 문서 레이어는 어떻게 구분해야 하는가\n\n문서 체계를 하나의 폴더 트리로만 보면 안 됩니다. 다음 세 축을 따로 봐야 합니다.\n## 3. 한 프로젝트 안에서 문서 레이어는 어떻게 구분해야 하는가\n\n문서 체계를 하나의 폴더 트리로만 보면 안 됩니다. 다음 세 축을 따로 봐야 합니다.\n\n\n|       |                                                              |\n| ----- | ------------------------------------------------------------ |\n| 축구조   |                                                              |\n| 범위    | Product → Initiative → Feature / Change → Task               |\n| 문서 성격 | Strategy / Evidence / Product / Technical / GTM / Operations |\n| 생명주기  | Discovery → Decision → Delivery → Launch → Outcome           |\n\n\n전략·리서치·마케팅·기술은 단순한 부모·자식 관계가 아닙니다.\n\n```\n\n```\n\n예를 들어 하나의 사용자 인사이트가 여러 Initiative를 뒷받침할 수 있고, 하나의 ADR이 여러 Feature에 영향을 줄 수 있습니다. GTM 계획은 Feature 아래가 아니라 Initiative 또는 Release와 병렬로 연결되는 경우가 많습니다.\n\n따라서 폴더는 사람이 찾기 쉬운 기본 경로만 제공하고, 실제 관계는 `문서 ID + 메타데이터 + 링크`가 담당해야 합니다.\n\n### 범위 계층의 추천 명칭\n\n\n|                     | 덮어쓰면 당시 왜 그런 결정을 했는지가 사라집니다. 반대로 출시 PRD만 보존하면 현재 제품이 어떻게 동작하는지 오래된 PRD 수십 개를 뒤져야 합니다.\n\n그래서 다음 구조를
