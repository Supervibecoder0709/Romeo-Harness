## 결론

**복잡함의 원인은 런타임 조합이 아니라 판정 구조에 있다.** 하네스가 자기 자신을 대상으로 돌기 때문에
새로 만든 규칙이 그 규칙을 만든 작업 자신을 즉시 판정하고, 그 작업이 자기를 막는다.

opencode 포팅은 이 문제를 해결하지 않는다 — 런타임을 바꿔도 판정 구조는 그대로 따라온다.
**권고: 포팅을 보류하고, 판정하는 하네스와 판정받는 하네스를 리비전으로 분리한다.**

## 1. opencode 포팅 검토 — 조건부 보류

### 바뀌는 것은 3층이고 대부분 선언이다

`romeo/compile.py:103` 이 `adapters/*/adapter.yaml` 을 글롭으로 열거하므로
**어댑터 추가에 컴파일 코드 수정이 필요 없다.**

| 층 | 내용 | 비용 |
| --- | --- | --- |
| 선언 | `adapters/opencode/adapter.yaml` + 워크플로 매핑 4종 | 반나절 |
| 코드 | `romeo/doctor.py:28-29`(런타임 프로브 목록) · `romeo/run_unit.py:202-203`(`codex exec -s read-only` 리터럴) | 2곳 |
| 관측 | `.harness/bindings.yaml` 의 `enforcement_observed` 4칸 재측정 | **여기가 실제 비용** |

### opencode 어댑터 값 (공식 문서 기준 — 실행 미관측)

| 어댑터 키 | 값 |
| --- | --- |
| `instructions_file` | `AGENTS.md` (+ `instructions` 배열로 분리 가능) |
| `settings_file` | `opencode.json` — `permission` 키 |
| `agents_dir` | `.opencode/agents/` (md frontmatter: `mode` · `permission` · `model`) |
| 검토자 강제 | frontmatter `permission: {edit: deny, bash: deny}` |
| 비대화형 기동 | `opencode run --agent <이름> --model <provider/model> --format json` |

출처: <https://opencode.ai/docs/config/> · <https://opencode.ai/docs/agents/> · <https://opencode.ai/docs/cli/>
(문서 기준이며 이 저장소에서 실행으로 확인하지 않았다 — K-51)

### opencode 가 실제로 메우는 구멍 2개

1. **codex 는 `settings_file: null`** 이라 권한 상한이 지침 인쇄로만 강제된다.
   opencode 는 저장소에 커밋되는 `opencode.json` 의 `permission` 이 기계 강제다.
2. **codex 는 `agents_dir: null`(미확인)** 이라 검토자 읽기 전용을 저장소 파일로 못 박았다.
   opencode 는 agent frontmatter 한 줄로 선언된다.

### 그럼에도 보류하는 이유

포팅은 §3~§5 가 지목한 판정 구조를 건드리지 않는다. 옮겨도 같은 봉착이 새 런타임에서 반복된다.
**하게 된다면** 세 번째 어댑터 추가가 아니라 **검토자 런타임 codex → opencode 교체**를 권한다 —
어댑터 수는 2개로 유지되면서 미관측 강제 칸 2개가 기계 강제로 바뀐다.
**추천이 뒤집히는 조건:** M5 attach 대상 프로젝트가 opencode 를 쓰는 경우.

## 2. 복잡함의 원인 4가지 (실측)

### 원인 1 — 이미 취소된 목표를 위한 구조가 남아 있다

원래 목표는 "Claude·Codex 두 실행이 같은 판정을 내면 합격"(동등성 게이트)이었다.
2026-08-29 재현성 측정에서 **같은 산출물·같은 런타임에 3회를 돌려 PASS 1 · FAIL 2** 가 나왔고,
그 일치를 합격 조건으로 두면 게이트가 유한하게 닫히지 않는다는 것이 확인되어 **D-76 으로 목표를 내렸다**
(`romeo/parity.py` 의 D-76 절).

**남은 것:** `.harness/bindings.yaml` 의 4칸 매트릭스 · `parity_swap` · 어댑터 이중화 · `fixtures/parity/`.

**미해소 모순 (이 세션의 발견 ①):**
`romeo/compile.py:181` 이 지침 파일에 매 컴파일마다 인쇄한다 —
*"교체 실행에서도 같은 판정이 나와야 동등성 게이트를 통과한다."*
그러나 `romeo/parity.py` 는 D-76 이후 판정 역할의 자유 서술 판정을 `advisory` 로만 인쇄하고 **세지 않는다.**
두 런타임이 폐기된 규칙을 읽으며 일한다. §11(요구하는 자리와 보는 자리) 위반의 모양이다.
→ **고치지 않았다. Q 로도 열지 않았다** — 사용자 판단 대기(§12).

### 원인 2 — 규칙 하나 추가 = 파일 10개 (의도된 비용)

최근 `feat`·`fix` 커밋 8건의 변경 파일 수: **8~15개, 중앙값 10~11.**

하나의 규칙이 네 자리에 나뉜다: `core/`(무엇을 요구하나) · `adapters/`(이 도구에선 어떻게) ·
`.harness/bindings.yaml`(누가 맡나) · `romeo/*.py` + `tests/`(31개, 실제 집행).

이것은 §11 이 만든 값이다 — 차단을 정책표에 적고 집행 코드를 잊어 "차단이라 인쇄되면서 아무것도 안 막은" 사고의 재발 방지.
**안전을 얻고 속도를 잃은 것이며, 지금 단계에서 풀 것을 권하지 않는다.**

### 원인 3 — 분류 눈금이 촘촘하다

`core/policy/classification.yaml`: 단위 4 · 모드 3 · 의도 5 · **facet 23** · hard gate 8 · 5요인.
`core/policy/packages.yaml`: 절 12종 · 블록 5종 · 예산 5종.
매 요청마다 앞단에 붙는 고정 비용이다. 줄일 여지는 있으나 라우터 재설계 규모다.

### 원인 4 — 하네스가 하네스를 고친다 (구조적)

하네스 변경도 하네스 절차(계획 → 승인 → 구현 → 검토 → close)를 밟는다.
§10 동결로 관통 중에는 못 고치므로 정비 창이 관통 **사이**로 제한된다.
이 규칙 자체는 옳다 — 풀면 판정이 무엇의 결과인지 말할 수 없어진다.
**§3 이 이 원인을 다시 다룬다.**

## 3. 실험 설계 결함 — 판정 자리가 안에 있다

사용자 제기: *"하네스를 만드는 도중에 하네스 규칙을 적용받게 할 게 아니라,
제3의 시선으로 고친 다음 데모 프로젝트에서 점검해야 하는 것 아닌가."*

### 제기를 뒷받침하는 실측 3건

**① 하네스가 원인 분리 불가를 스스로 적어 두었다.**
`AGENTS.core §10`: *"실패 원인 분류(산출물·하네스·목표)는 기록만 하고 차단 판정에는 쓰지 않는다.
원인 오판이 그 반복을 만들었으므로 자동 분류를 신뢰하지 않는다."*
→ 해결한 것이 아니라 **구분 시도를 포기**해 우회했다.

**② §10 동결은 자기적용의 세금이다.** 외부 대상이면 이 규칙이 필요 없다.

**③ 검사 케이스의 대부분이 지어낸 것이다.**
fixture 38건 중 4건이 `source.kind: authored` 다. 68개 프로젝트 세션 로그 597MB 를 훑어도
`legal` · `ops-data-deletion` · `public-api` · `irreversible-policy` 네 게이트에 해당하는 실제 요청이 없었고,
hard gate 8종 중 실제 요청 유래는 **payment 1건**뿐이다(Q-50).

### 다만 축이 다르다

**자기적용 자체가 무효인 것은 아니다.** `run-unit merge-check` 는 자기 통합 과정에서
**두 번 `exit 1` 로 실제 사고를 막았다**(회차 기록이 사라지는 것을 지목). 자기적용이 아니었으면 못 잡았다.

**authored fixture 문제는 자기적용이 아니라 실사용 부재에서 왔다.** 밖에서 설계해도 실사용이 없으면 같은 결과다.

**따라서 정확한 처방은 「고치는 자리」가 아니라 「재는 자리」를 밖으로 빼는 것이다.**

| | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 고치는 곳 | 이 저장소 | 이 저장소 (그대로) |
| **판정하는 곳** | **이 저장소** | **외부 대상 또는 이전 리비전** |
| 실패 원인 분리 | 불가능 → 포기 선언 | 가능 |
| §10 동결 | 필요 | 대부분 불필요 |

   이 규칙이 `core/policy/packages.yaml` 에서 `add_parts: [superpowers]` 를 한다
3. **적용 기록이 없다** — `docs/work/` 29단위 전체에서 `test-driven-development` ·
   `systematic-debugging` · `requesting-code-review` · `using-git-worktrees` 이름이 나오는 파일은 2개이고,
   둘 다 BMAD 설치 관측 때 만든 **파일 해시 목록**이다

## 6. 권고 — 당장 할 것 3가지 (순서대로)

### 1. 판정하는 하네스와 판정받는 하네스를 리비전으로 분리한다

**문제의 자리:** `close` · `validate` · `route` 가 **현재 작업 트리의** `bin/romeo` 로 돈다.
§10 동결은 이것을 막지 못한다 — 그 단위의 존재 이유가 하네스를 바꾸는 것이기 때문이다.

**해결:** 판정을 `base_sha` 시점의 하네스로 돌린다. 새 규칙은 **다음 단위부터** 적용된다.

**이미 있는 재료:**
- `--root` — M2·M3 에서 남의 저장소를 판정하려고 만든 것. 옛 리비전이 현재 트리를 판정하는 데 그대로 쓰인다
- `base_sha` — 작업 계약과 증거에 이미 기록된다
- `orca worktree` — 옛 리비전 체크아웃

**선행 조건 2건:** Q-66(`--root` 를 준 실행에서 위치 인자가 호출한 쪽 cwd 로 해석된다) ·
Q-67(git 이력 없는 루트에서 스택 트레이스로 죽는다).

**새 규칙의 판별력은 어디서 보나:** §11 이 이미 요구한다 —
*"새 검사는 기존 상태에서 실패하고 가상 완료 상태에서 성공하는 것을 승인 전에 양쪽으로 보인다."*
**판별은 승인 전 프로브가, 판정은 옛 리비전이** 맡는다.

**선례:** 컴파일러 부트스트랩과 같은 구조다 — 이전 버전으로 다음 버전을 만들고, 다음 버전은 그다음부터 쓴다.

### 2. 사본을 읽기로 바꾼다 — 규칙으로 승격

처방은 이미 두 번 발견됐으나 개별 적용만 됐다.

- 정비 5회차: "라벨을 정책표에서 **읽어** 대조하는 검사"
- gate coverage 단위: "게이트 id 를 `classification.yaml` 에서 **읽어** 대조" —
  반례까지 확인했다(*id 를 하드코딩한 구현은 개명된 정책표에서 그냥 통과한다*)

`AGENTS.core §11` 에 한 줄 추가를 권한다:
**"같은 사실을 두 자리에 적지 않는다. 두 번째 자리는 첫 자리를 읽는다."**

이것이 §2 의 원인 2(규칙 하나 = 파일 10개)도 같이 줄인다.

### 3. 자가봉착을 계측한다

지금 단위당 Q 생성률 2.4 가 **어디에도 기록되지 않는다.**
Q-02(*하네스 자체 성공 지표 8종을 언제부터 계측하는가*)가 그 자리이며 미결이다.
최소 두 개는 세야 한다 — **단위당 Q 생성률 · 단위당 회차 수.**

**Q 68건을 번호순으로 처리하는 것.** 6회차 동안 한 일이고 끝나지 않았다.

### 한계

**권고 1 자체가 자기적용이다.** 이번에도 봉착할 수 있다.
그러므로 **권고 1 을 자기적용의 마지막 라운드로 둔다** — 성립하면 그다음부터
판정 리비전이 판정받는 리비전보다 항상 앞선다. 그 전까지는 §10 동결과 반복 중단으로 버틴다.

## 7. 이 문서가 만들지 않은 것

- **작업 단위를 만들지 않았다.** `/plan` 을 돌리지 않았고 승인 절차를 밟지 않았다.
- **결함을 고치지 않았다.** 발견 ①(`compile.py:181` ↔ `parity.py`)과
  발견 ②(superpowers 집행 관측 지점 부재)는 **Q 로도 열지 않았다** — 사용자 판단 대기(§12).
- **테스트 계획을 세우지 않았다.** 사용자가 보류를 지시했다.
- **opencode 값을 실행으로 확인하지 않았다.** §1 의 표는 공식 문서 기준이다(K-51).
- **Q 분류(§5)는 이 세션의 판단이다.** 저장소에 기록된 분류가 아니며 집행에 쓰이지 않는다.
