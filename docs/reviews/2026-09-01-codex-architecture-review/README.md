## 결론

전체 방향은 M3 본류로 돌아왔다. 다만 분석 시점의 Charter·discovery 작업은 그대로 완료시키기보다,
명세를 보완해 재승인한 뒤 다시 실행하는 것이 안전한 상태였다.

반복 비용의 주원인은 Claude의 구현 속도가 아니라 구현 전에 승인된 목표·검사·하네스가 충분히

권고 판정은 다음과 같다.

- 거시 방향: 적합 — Charter, discovery 차단, 시나리오 3은 M3 계획과 일치한다.

## 분석 시점의 M3 방향 판정

거시 방향은 맞았다. Charter, discovery 차단, 시나리오 3은
`docs/planning/implementation-plan.md`에 명시된 M3 사용자 가치다.

다만 `86c17ef`의 승인 명세와 당시 작업 중 구현에는 다음 공백이 있었다.

### 1. 단계 순환

Tech Spec 승인이 `SPEC_READY`를 만드는 구조인데 승인 전에 `discovery-result`까지 요구했다.
조사·spike 작업이 결과를 만들기도 전에 결과를 요구하면, 결과를 만드는 작업 자체가 시작되지 못한다.

### 2. 입력 문서 소유권 불일치

계획은 조사 결과를 Brief 또는 Charter의 `inputs:`에 연결하도록 한다. 당시 작업 중 구현은
`spec.md`에서 읽은 frontmatter만 검사했다. 테스트도 문자열이 비어 있지 않은지만 보아 존재하지
않는 경로는 통과하고, 올바른 Brief·Charter 링크는 거부될 수 있었다.

### 3. 시나리오 3의 spike 조건 누락

원 계획은 첫 마일스톤이 spike여야 한다고 명시하지만, 승인된 수용 기준은 `inputs:`와 Charter의
마일스톤 존재만 검사하고 spike 집행을 명시하지 않았다.

### 4. `approval-gate` 의미 혼합

당시 구현은 위험·백업·복구 설명이 있는지를 확인했다. 그러나 실제 외부 실행 승인은 배포·결제·외부
쓰기 직전에 별도로 확인해야 한다. 계획 문서의 준비 상태와 되돌리기 어려운 행동의 실행 승인을 같은
이름으로 묶으면 잘못된 단계에서 차단될 수 있다.

추천 단계 배치는 다음과 같다.

| 차단 항목 | 주 차단 시점 | 정본 입력 |
| --- | --- | --- |
| `spec-ready` | Tech Spec 승인 후 구현 위임 직전 | 승인된 Tech Spec |
| `milestone-plan` | T2 계획 승인 시 | 채워진 Charter 마일스톤 |
| `discovery-result` | 조사 완료 후 일반 구현 위임 직전 | Brief/Charter의 실제 결과 링크와 go/stop 판단 |
| `approval-gate` | 배포·결제·외부 쓰기 같은 되돌리기 어려운 실행 직전 | 별도의 승인 기록과 실행 guard evidence |

close 단계는 관련 차단 상태를 보고할 수 있지만, 앞 단계의 의미를 새로 정의해서는 안 된다.

## 우선 적용할 규칙

### P0 — 재관통을 직접 줄이는 규칙

1. **승인 전 검사 가능성 증명**
   새 required check는 기존 상태에서 실패하고 가상 완료 상태에서는 성공해야 한다. 정확한 AC-check
   연결, 여러 evidence, 여러 줄 명령, 파일 순서, 잘못된 경로 반례를 포함한다. 양쪽 증명이 없으면
   관통을 시작하지 않는다.

2. **재실행 변화량 게이트**
   재실행 전에 `failure_class`, 변경된 입력 SHA 또는 외부 상태, 이전 실패가 이제 발생하지 않는다는
   최소 preflight를 기록한다. 변화가 없으면 재실행하지 않는다. `operator_close`나
   `agent_prompt_stalled` 같은 운송 실패는 새 full run이 아니라 동일 산출물 recovery로 분리한다.

3. **목표·하네스 실패 시 전체 관통 금지**
   첫 실패가 `goal` 또는 `harness`이면 구현·리뷰·종료를 처음부터 반복하지 않는다. spec과 검사만
   정적·반례 검증하고 재승인한 뒤 새 base에서 실행한다.

4. **block별 단계·입력 문서 선언**
   각 block은 하나의 주 전환과 정본 입력 문서를 선언한다. `[approve, close]` 같은 일괄 배치를 금지하고,
   계획 승인·구현 위임·외부 실행 승인을 분리한다.

5. **마일스톤 정비 예산**
   현재 마일스톤 수용 기준을 직접 막거나 매 실행에서 반복되는 결함만 즉시 처리한다. `v1 이후`로
   park된 항목은 사람이 다시 승격하지 않는 한 닫지 않는다. 마일스톤 기능 단위 사이의 정비 단위는
   최대 한 개로 제한한다.

6. **worker당 하나의 event wait**
   동시에 유효한 wait는 하나만 둔다. `check --wait --types worker_done,escalation,question`이 끝나기
   전에는 peek와 sleep을 사용하지 않는다. timeout·question·done 때만 다음 호출을 하고 delivery는
   한 번 처리한 뒤 ack한다.

### P1 — 문맥과 운영 비용을 줄이는 규칙

7. **한 세션·한 작업 단위 또는 한 run**
   승인 변경이나 run 종료 뒤에는 생성된 handoff로 새 문맥을 시작한다. 수십만 토큰 문맥으로 여러
   회차를 계속하지 않는다.

8. **`지금 상태` 예산**
   30줄 또는 2KB 안에 기준 SHA, active unit/run/task, 현재 단계, blocker, 다음 행동 1~3개, 최신 CI
   한 건만 둔다. 회차 서사는 작업 단위와 archive로 이동한다.

9. **동일 문서 구간 한 번 읽기**
   동일 SHA의 같은 문서 section은 세션당 한 번만 읽는다. 재독 전에 기록된 section cursor나 요약을
   사용한다. 서로 독립인 `rg`·`sed`·Git·CI 조회는 한 번의 병렬 조회로 묶는다.

10. **RUNBOOK 자동화 임계값**
    같은 coordinator 명령 템플릿이 두 작업 단위에서 반복되면 RUNBOOK 설명을 늘리지 않는다.
    run/task 생성, brief 채우기, id binding, wait/ack, evidence 수집을 결정론적 CLI로 옮긴다.

11. **검색 범위 기본 제한**
    `docs/source-context/**`, archive, evidence 원시 로그는 기본 검색에서 제외한다. 인덱스와 목차를
    먼저 보고 필요한 파일·구간만 연다.

12. **완료 단위의 상태 정리**
    단위 close 시 과거 `ready`·`pending`·`blocked` task를 사유와 함께 `superseded` 처리한다.
    다음 세션에는 active run id 하나만 노출한다.

13. **스키마 변경 전 과거 계약 재생**
    envelope 필드를 삭제하거나 의미를 바꾸기 전에 모든 추적된 완료 단위의 계약을 재생성하고 기존
    앵커와 호환되는지 확인한다.

14. **저가 모델 worker 재사용**
    동일 세션의 Git·문서 이동·기계적 커밋 작업은 일회성 worker 여러 개 대신 하나를 재사용하거나
    의미 있는 체크포인트 단위로 묶는다. push는 계속 별도 승인 대상으로 둔다.
