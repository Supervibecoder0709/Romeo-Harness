1. 최종 판정

주요 수정 후 구현 가능

얇은 정책 척추, Orca와의 소유권 경계, 두 런타임의 공통 계약이라는 핵심 구조는 유지해야 한다. 다만 M2를 v1 합격선으로 부르면서 정본의 v1 필수인 Charter·부착 상태·shadow mode를 M3~M5에 둔 완료 기준 충돌이 있다.

같은 M2의 migration 성격 작업보다 승인 가드가 늦고, reviewer read-only와 작업 트리 변경 후 stale 판정도 아직 강제되지 않는다. 이 경계와 설치·업데이트 복구 계약을 먼저 고치면 전체 구조를 다시 설계할 필요는 없다.

3. 발견 사항

MAJORF-01 · v1 합격선과 v1 필수 산출물의 시점이 모순된다
근거
정본 V-0~V-10에는 Charter, 부착 상태, shadow 20건이 포함된다(v1-scope.md:30-45). PLAN은 M2를 “v1 유일 합격 기준”으로 부르면서 이들을 M3~M5에 둔다(PLAN:260-270,421-463).
실제 영향
PM·구현자·리뷰어가 서로 다른 완료 정의를 쓰고 문서 승인과 구현 완료가 다시 섞인다.
최소 수정
M2를 core parity gate로 바꾸고, V-0~V-10 충족을 v1 release gate 한 곳에 둔다. M2를 v1로 삼으려면 정본 범위를 먼저 승인 변경한다.
확신도
높음
MAJORF-02 · migration payload보다 위험 승인 gate가 늦다
근거
M2가 18개 문서 backfill을 migration facet으로 분류하지만(PLAN:260-269), 실제 gate-create 집행은 M3다(PLAN:432-441). K-50은 실행 전 영향·복구·승인을 요구한다.
실제 영향
게이트 대상이라고 스스로 분류한 변경을 게이트가 없는 단계에서 실행한다.
최소 수정
최소 execution guard를 M2 앞으로 옮기거나 M2 payload를 hard gate 없는 T1로 바꾼다. 8종 전체 시나리오는 M3에 남긴다.
확신도
높음
MAJORF-03 · reviewer read-only가 사후 git status 비교에 의존한다
근거
C-D2는 read-only를 v1 필수로 둔다. PLAN은 Orca가 강제하지 못한다고 인정하고 전후 상태 비교로 완화한다(PLAN:506-515). 현재 CLI에는 Codex -s read-only와 Claude 도구 허용·거부 옵션이 존재한다.
실제 영향
ignored 파일·외부 서비스·브라우저 세션 변경은 git 상태가 같아도 놓칠 수 있다.
최소 수정
Codex reviewer는 read-only sandbox, Claude reviewer는 명시적 읽기 도구 목록으로 실행한다. 상태 비교는 보조 방어로만 둔다.
확신도
높음
MAJORF-04 · evidence stale 판정이 작업 트리 변화를 완전히 묶지 못한다
근거
C-E2는 HEAD 또는 작업 트리 변경을 stale로 요구한다. PLAN 다이어그램에는 dirty hash가 있지만 M1 합격 테스트는 HEAD를 한 커밋 움직이는 경우가 중심이다(PLAN:410-419).
실제 영향
같은 HEAD에서 tracked·staged·untracked 변경이 생겨도 검증한 바이트를 재현하지 못할 수 있다.
최소 수정
base_sha, head_sha, dirty_tree_hash, 포함·제외 경로와 정규화 규칙을 필수화하고 세 종류 작업 트리 변화 테스트를 넣는다.
확신도
높음
MAJORF-05 · attach/update 복구가 clean·tracked Git 상태를 과도하게 가정한다
근거
PLAN은 3-way hash와 dry-run을 제안하지만 실패 복구는 “git 추적 → git checkout” 중심이다(PLAN:454-463). 새 untracked 파일, dirty 대상, 중간 실패 원자성은 정의되지 않았다.
실제 영향
부분 설치와 사용자 설정 손실이 남을 수 있고 git checkout만으로 새 파일을 복구하지 못한다.
최소 수정
대상·branch·dirty·hash preflight, 파일별 승인, 임시 staging 후 원자 교체, 성공 뒤 상태 갱신, 생성 파일까지 포함한 백업 복원을 명세한다.
확신도
높음
MINORF-06 · M0 수평 산출물이 첫 종단 흐름보다 크다
근거
M0는 정책표·스키마·템플릿·CLI·tests·provenance·NOTICE를 한 번에 만든다(PLAN:399-408). 유일한 합격 기준은 실제 관통 흐름이다.
실제 영향
파일과 단위 테스트가 늘어도 /plan → 실행 → evidence → close의 연결 실패가 늦게 드러난다.
최소 수정
M0의 최소 정책·Tech Spec·dry-run 결과를 즉시 M1 입력으로 연결하고, 소비자가 없는 provenance·범용 명령은 늦춘다.
확신도
중간
MINORF-07 · M0를 막는 결정의 설명이 문서 안에서 다르다
근거
M0 본문은 profile·상태 모델만 필요하고 라이선스는 막지 않는다고 하나(PLAN:403-405), 마지막 프롬프트는 라이선스·profile·상태·적용 범위를 모두 확정값으로 요구한다(PLAN:568-577).
실제 영향
가역적인 M0까지 불필요하게 중단될 수 있다.
최소 수정
frontmatter schema와 profile 표현만 blocking으로 두고 나머지는 UNKNOWN/NEEDS_DECISION으로 기록한다.
확신도
높음
MINORF-08 · 첫 T0 payload의 rg 환경 근거가 이미 바뀌었다
근거
PLAN은 ChatGPT 앱 내부 경로를 기록했지만 현재 probe는 Codex standalone 0.147.0 경로의 ripgrep 15.2.0을 반환했다. 스크립트가 rg에 의존하는 사실은 유지된다.
실제 영향
첫 실제 작업이 낡은 환경 관찰을 고치는 일로 고정된다.
최소 수정
M1에서 경로와 CI를 다시 probe하고 실제 실패가 없으면 일반 T0 후보로만 둔다.
확신도
높음

5. 구현 순서 검사

판단: M1에서 최소 흐름을 처음 완성하는 방향은 맞지만, M0의 수평 산출물이 크고 M2의 완료 명칭이 정본·안전 gate와 맞지 않는다. 전면 재작성 없이 아래 단계 이동만 필요하다.

요청 입력
작업 깊이 판단
워크플로우 선택
계획·실행 결정
결과 검증
상태·증거 기록

앞당겨야 할 단계

  • 최소 execution guard와 승인 evidence를 M2 전으로.
  • reviewer read-only 강제와 dirty-tree stale를 M2 선행 합격 조건으로.
  • 정본 v1 유지 시 Charter·최소 부착 상태·shadow 20건을 v1 선언 전으로.

늦춰야 할 단계

  • 소비자가 없는 provenance·NOTICE 골격은 첫 외부 자산 채택 시점으로.
  • 범용 doctor·metrics·디자인·OpenWiki는 관찰 트리거 뒤에 유지.

합쳐야 할 단계

  • M0의 최소 정책·Spec·dry-run을 같은 fixture의 M1 종단 흐름으로 즉시 연결.
  • status·approved_at·Orca 실행 상태·계산된 stale의 소유권을 하나의 계약 절로.

제거·V1 이후

  • 낡은 관찰에 고정된 rg payload는 probe 기반 후보로.
  • full updater·metrics·디자인·파생 지식은 트리거 뒤로. V-8 최소 상태 파일만 v1에 유지.

6. 최종 수정 목록

구현 전에 반드시 수정

  1. M2 parity gate와 V-0~V-10 v1 release gate를 분리한다.
  2. M2 payload를 바꾸거나 최소 승인 가드를 앞당긴다.
  3. reviewer read-only를 런타임 권한으로 강제한다.
  4. dirty-tree 정규화와 stale 테스트를 확정한다.
  5. attach/update에 preflight·파일별 승인·원자 적용·완전 복구를 넣는다.

구현하면서 검증 가능

  • profile 임계·표시명, 3-tier 충분성, 템플릿 cap.
  • 정책 정확도, 경로 불변 탐색성, rg portability.
  • Orca 안정성, native projection, 모델·effort 바인딩.
  • OpenWiki·디자인·MCP·자동 라우팅은 트리거 뒤 실험.

변경하지 않아도 됨

  • 얇은 정책 척추와 세 축 분리.
  • LLM 제안 / 사람 확정 / 정책 강제.
  • Romeo 계약 / Orca 실행 상태 경계.
  • 계약 중심 runtime parity.
  • 역할 둘로 시작하고 확장을 늦추는 결정.
