버튼 문구 한 줄을 바꾸는 일이라도 결제 약관에 관련되면 여기 걸립니다. 반대로 코드를 전부 리팩터링해도 사용자 동작과 제품 정책이 그대로면 제품 PRD는 얇아도 됩니다. 이 때문에 제품 기획 강도와 기술 구현 강도는 반드시 따로 분류해야 합니다.

기획은 크기가 아니라 두 층으로 분류합니다

이 표가 매번 참조할 판단 기준입니다. 1층에서 무엇을 기획하는지를 정하고, 2층에서 얼마나 깊이 할지를 정합니다.

1층 · 무엇을 기획하는가 — 같은 "기능 요청"도 종류가 다릅니다
Change기존 동작의 국소적인 변경Change Brief + 기술 스펙
Feature하나의 사용자 문제를 종단 간 해결Feature PRD + 기술 스펙
Discovery · Experiment구현보다 학습과 의사결정이 목적Experiment Brief + 측정 계획

Uncertainty문제·고객가치·시장·해결책 중 무엇이 불명확한가높으면 PRD보다 Discovery를 먼저

Reversibility쉽게 되돌릴 수 있는가. 법무·돈·데이터 문제가 있는가승인·감사·롤백·마이그레이션 문서 추가
Coordination몇 개 팀·시스템·외부 업체가 관여하는가이해관계자·의존성·마일스톤·출시조정 추가
보조값 · 판단의 근거와 한도

appetite이 문제에 최대 얼마까지 투자할 의향이 있는가해결책 범위를 먼저 제한. 공수 추정이 아님

"총점 12점이므로 Large PRD" 방식을 쓰지 않는 이유는 축마다 처방이 다르기 때문입니다. 불확실하면 Discovery를 먼저 하고, 범위가 넓으면 문서를 나누고, 영향이 크면 측정을 강화하고, 위험하면 승인·롤백을 강제하고, 조율이 복잡하면 의존성 문서를 추가합니다. 이것들은 서로 대체되지 않습니다.

저장 구조가 분류 체계보다 먼저입니다

원문은 분류 → 양식 → 레이어 → 저장 순서로 전개되지만, 실제로 먼저 정해야 하는 것은 저장입니다. 분류를 아무리 정교하게 만들어도 산출물이 한 폴더에 쌓이면 6개월 뒤에 "왜 이렇게 결정했는지"를 아무도 답할 수 없습니다.

이 문서에서 제일 헷갈리는 곳입니다. 폴더 이름은 비슷해 보이지만 시간적 성격이 다릅니다. current/는 계속 갱신되고, work/는 끝나면 동결되고, decisions/는 덮어쓰지 않고 새 결정으로 대체되고, evidence/는 원본을 보존한 채 해석만 버전 관리합니다. 이 구분을 건너뛰면 나머지 체계가 전부 무너집니다.

무엇을 current/로 올릴지는 제품 판단입니다. 신규 가격 정책이나 여러 기능이 공유하는 인증 규칙은 올리고, 특정 캠페인 문구나 일회성 UI 배치 결정은 올리지 않습니다. 기준은 하나입니다 — 다른 작업이 앞으로 다시 참조해야 하는가.

이름이 익숙해서 오히려 잘못 읽히는 것들

PRD는 제품 설명서다. 제품이 바뀌면 최신 상태로 갱신한다.
실제로는
PRD는 그 시점의 변경 의도입니다. 덮어쓰면 왜 그렇게 결정했는지가 사라집니다.

6개월 뒤 같은 영역을 다시 손댈 때. 현재 동작은 알 수 있지만 제약이 왜 생겼는지 아무도 답하지 못합니다.

문서 이름이 소유하는 것

같은 내용을 여러 문서에 복사하지 않으려면, 각 문서가 무엇을 소유하는지가 먼저 정해져야 합니다.

이름이 체계에서 소유하는 것오해하기 쉬운 점
Initiative Charter 왜 하는지, 어떤 성과를 원하는지, 무엇을 하지 않는지 "큰 PRD"가 아닙니다. 요구사항과 AC는 여기 없습니다
Feature PRD 사용자 행동, 비즈니스 규칙, 예외 상태, Acceptance Criteria Charter 내용을 다시 적으면 그 순간 중복이 생깁니다
Milestone Plan 구현 순서, 의존성, 컷라인, 검증 시점 하위 PRD를 요약한 또 다른 PRD가 아닙니다
Discovery Brief 무엇을 만들지가 아니라 진행할지 말지의 판단 근거 상세 PRD의 축소판이 아닙니다. 목적이 다릅니다
Change Brief 국소 변경의 이유·범위·검증 방법 작다고 생략하면 안 됩니다. 하드 게이트에 걸리면 강도가 올라갑니다

원문은 Project PRD라는 이름을 피하라고 권합니다. 프로젝트가 제품 전체인지, 특정 Initiative인지, 실행 기간인지 사람마다 다르게 읽기 때문입니다.

문서를 하나로 합쳐도 되는 조건당신이 정할 것

다섯 가지를 모두 만족할 때만 합칩니다 — 단일 사용자 문제 · 단일 오너 · 단일 출시 · 단일 성공지표 · 하나의 의사결정으로 종료.

반대로 아래 중 하나라도 나타나면 분리합니다. 독립적으로 배포할 수 있다 · 오너나 승인자가 다르다 · 대상 사용자나 성공지표가 다르다 · 여러 마일스톤에 걸친다 · 병렬로 개발된다 · 별도 법무·보안·운영 검토가 필요하다.

아래는 실행 방식입니다. 결론은 각 제목에 담았습니다.
문서 양식은 템플릿을 늘리지 말고 코어 + 오버레이로 조립한다원문 2절

모든 구현 기획의 공통 코어: 배경과 문제 · 대상 사용자와 사용 상황 · 기대하는 사용자·사업 결과 · 범위와 비범위 · Acceptance Criteria 또는 의사결정 기준 · 주요 가정과 열린 질문 · 문서 오너와 상태 · 상위 목표·근거·관련 문서 · 기술 스펙 링크.

그 위에 조건이 맞을 때만 모듈을 붙입니다. 문제·시장 불확실성이 높으면 Discovery/Research/Validation, 실험이 목적이면 Hypothesis/Experiment Design, 핵심 지표에 영향이 있으면 Measurement/Analytics, 여러 사용자 흐름이 바뀌면 Journey/Story Map, 결제·개인정보·법무면 Risk/Approval/Compliance, 기존 사용자·데이터 전환이면 Migration/Rollback, 여러 팀이 참여하면 Dependency/Stakeholder, 외부 출시면 GTM/Launch, 운영 절차가 바뀌면 Support/Operations, 장기 영향이 있는 결정이면 Product Decision Record 또는 ADR.

성숙한 기술 프로젝트도 모든 변경에 같은 절차를 적용하지 않습니다. Rust는 일반 변경, 주요 변경 제안, 더 무거운 RFC 절차를 구분합니다.

문서 체계는 폴더 트리 하나가 아니라 서로 독립인 세 축이다원문 3절

세 축은 범위(Product → Initiative → Feature/Change → Task), 성격(Strategy / Evidence / Product / Technical / GTM / Operations), 생명주기(Discovery → Decision → Delivery → Launch → Outcome)입니다.

전략·리서치·마케팅·기술은 단순한 부모·자식 관계가 아닙니다. 하나의 사용자 인사이트가 여러 Initiative를 뒷받침할 수 있고, 하나의 ADR이 여러 Feature에 영향을 줍니다. GTM 계획은 Feature 아래가 아니라 Initiative나 Release와 병렬로 붙는 경우가 많습니다.

그래서 폴더는 사람이 찾기 쉬운 기본 경로만 제공하고, 실제 관계는 문서 ID와 메타데이터, 링크가 담당해야 합니다.

덧붙여 Task는 장기 기획 문서가 아닙니다. 실행이 끝났다고 모든 이슈를 지식 문서로 승격시키지 않습니다.

문서 상태와 작업 상태를 분리해야 셋 다 어긋난 상황을 표현할 수 있다원문 5절

본문은 Markdown, 하네스가 읽을 정보는 YAML frontmatter로 관리합니다. id, type, owner, parent, supports, informed_by, related_specs, target_release, last_reviewed, supersedes 같은 항목입니다.

doc_status와 work_status를 나누는 이유는 이런 상황이 실제로 생기기 때문입니다.

  • PRD는 승인됐지만 개발은 시작되지 않을 수 있습니다
  • 기능은 출시됐지만 성과 측정은 안 끝났을 수 있습니다
  • 문서는 대체됐지만 실제 제품은 아직 이전 버전일 수 있습니다

종결 상태도 구분합니다. completed(구현과 결과 확인 완료) · superseded(새 결정이 대체) · abandoned(전략·비용 문제로 중단) · archived(활성 관리 대상에서 제외).

중요한 결정은 과거 문서를 수정해 지우지 않고 새 결정으로 대체합니다. 이력과 대체 관계를 남기는 방식은 AWS의 ADR 지침과 같습니다.

SSOT는 "문서가 하나"가 아니라 "사실마다 기준 장소가 하나"라는 뜻이다원문 6·7절

제품 방향과 정책은 Git 문서, 담당자·일정은 이슈 트래커, 실제 구현 상태는 코드와 PR, 실제 배포 상태는 배포 플랫폼, 지표 값은 분석 시스템에 있습니다. 같은 내용을 여러 PRD에 복사하지 말고 기준 문서에 링크합니다.

사용자 리서치 원본에는 개인정보가 들어갈 수 있으므로 Git에는 연구 ID, 목적, 요약 인사이트, 근거 수준, 수행 날짜, 원본 위치 링크, 접근 권한 책임자만 둡니다.

하네스 저장소와 프로젝트 산출물도 분리합니다. 하네스에는 라우팅 규칙·스키마·템플릿·오버레이·검증기만 두고, 실제 기획 산출물은 각 프로젝트가 소유합니다. 그래야 하네스 버전을 바꾸거나 Claude와 Codex를 교체해도 프로젝트 지식이 종속되지 않습니다.

하네스의 첫 출력물은 PRD 본문이 아니라 무엇을 만들고 무엇을 뺐는지의 선언이다원문 8절

하네스가 처음 내놓아야 하는 것은 Planning Package Manifest입니다. 무엇으로 분류했는지, 어떤 문서를 지금 만들고 무엇을 검증 후로 미루는지, 어떤 오버레이가 필요하고 무엇을 생략했는지, 상위 문서와 어떻게 연결되는지, 다음 단계로 넘어가는 조건이 무엇인지를 먼저 선언합니다.

그 뒤 순서는 이렇습니다. 기존 문서 카탈로그 확인 → 새 문서가 필요한지 기존 문서 수정인지 판단 → 필요한 문서만 생성 → 상하위 연결 → 기술 스펙·실행계획 연결 → 출시 후 결과 검증 → Current 갱신과 Archive.

생략한 것을 명시적으로 기록하는 것이 핵심입니다. 무엇을 안 만들었는지가 기록되지 않으면, 나중에 그것이 빠뜨린 것인지 의도적으로 뺀 것인지 구분할 수 없습니다.
